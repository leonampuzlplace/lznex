LzNex

Query builder, schema builder e migrations para Lazarus/FPC, com API fluente e encadeável sobre a camada DBC do ZeosLib — sem TDataset.

MySQL / MariaDB · pronto PostgreSQL · SQL e DDL Firebird · arquitetura aberta FPC 3.2.2 instalável por Boss pronto para multi-thread

Toda a API é construída sobre interfaces COM com contagem de referência: quem usa o LzNex nunca escreve try/finally Free. Uma query é montada como árvore (AST) e só então compilada para texto + binds pelo dialeto ativo. Isso dá três coisas de graça: o mesmo código gera SQL diferente por banco, valor nenhum é interpolado no SQL, e o SQL pode ser inspecionado sem conexão. 

uses LzNex, LzNex.Client.MySQL;

var
  Db: ILzNex;
  Rows: ILzNexResult;
begin
  Db := Connect(NewConfig
    .Client('mysql').Host('mysql').Database('app')
    .User('root').Password('secret')
    .LibraryLocation('/usr/lib/x86_64-linux-gnu/libmariadb.so.3')
    .Pool(2, 10));

  Rows := Db.Table('users')
            .Where('active', True)
            .WhereOpen
              .Where('role', 'admin')
              .OrWhere('role', 'owner')
            .WhereClose
            .OrderBy('name')
            .Limit(10)
            .Get;

  while Rows.Next do
    Writeln(Rows.Field('name').AsString);
end;
SQL gerado
select * from `users` where `active` = ? and (`role` = ? or `role` = ?) order by `name` asc limit ?

binds: True | admin | owner | 10

Decisões de projeto

Algumas escolhas da API surpreendem quem vem de query builders de outras linguagens. Todas têm motivo:

DecisãoPor quê
Grupos de predicado com WhereOpen … WhereClose, sem callbackO FPC 3.2.2 não tem função anônima. O grupo é mantido numa pilha e ToSQL levanta se sobrar grupo aberto.
OnColumns e OnValue separados no joinComparar com uma coluna e comparar com um valor são operações distintas. Um método só para as duas transformaria on('ativo', True) numa comparação com o identificador True, sem erro visível.
Terminais explícitos (Get, First, Count…)Não existe await em Pascal: a execução precisa ser uma chamada visível, nunca um efeito colateral de usar o objeto.
Insert preserva a ordem das colunas informadasA ordem que você escreveu é a que aparece no SQL e no log. Ordenar alfabeticamente dificultaria a conferência.
Timestamps gera TIMESTAMP, não DATETIMEÉ o tipo com semântica de instante nos dois dialetos suportados.
A ordem das seções do SQL é virtual por dialetoBanco cuja sintaxe muda a ordem (ou proíbe uma seção num verbo) sobrescreve só isso, em vez de duplicar o compilador inteiro.
TLzNexFragment carrega texto e bindsFecha a janela em que o texto e a lista de binds andam separados e saem de sincronia.
OnConflict devolve um tipo que só tem Merge/IgnoreEsquecer de completar a cláusula vira erro de compilação, não de execução.
Grupo aninhado é compilado sem o prefixoCompilePredicates devolve só o corpo dos predicados. Nenhum lugar do código recorta SQL por posição de caractere.
Lista de operadores fechadaOperador vindo de entrada do usuário não vira injeção: fora da lista, levanta.

Instalação

Instalável por Boss em qualquer projeto Lazarus, inclusive os que usam Horse.

Pelo Boss

// boss.json do seu projeto
{
  "dependencies": {
    "github.com/leonampuzlplace/lznex": "^1.0.0"
  }
}
boss install

O ZeosLib vem junto, como dependência transitiva. O Boss cria as pastas em modules/<host>_<org>_<repo> (pontos e barras viram _), e é esse nome que entra nos unit paths do seu .lpi.

ℹ
Coordenada

O boss.json do repositório ainda aponta para github.com/CHANGEME/lznex e github.com/CHANGEME/zeoslib. Enquanto o pacote não for publicado, os Dockerfiles montam modules/ com o mesmo layout que o Boss produziria. O fork do Zeos precisa ter boss.json: o Boss aborta se uma dependência não tiver manifesto.

O uses mínimo

uses
  LzNex,                 // a facade: Connect, NewConfig, ILzNex, ILzNexQuery...
  LzNex.Client.MySQL;    // o dialeto. Sem esta linha, Connect levanta.
⚠
Armadilha estrutural do Pascal

O linker do FPC descarta unit que ninguém referencia em uses. Unit descartada não executa seu initialization — e é ali que o dialeto se registra no registry. O sintoma é Requested database driver was not found em tempo de execução, sem erro de compilação. A mesma regra vale para migrations e seeds escritas em Pascal.

Programa com threads

Em Unix, programa que usa threads precisa de cthreads no início do uses do .lpr — antes de qualquer outra unit: 

uses
  {$IFDEF UNIX}{$IFDEF UseCThreads}
  cthreads,
  {$ENDIF}{$ENDIF}
  SysUtils, Horse, LzNex, LzNex.Client.MySQL;

Pela IDE

O lznex.lpk na raiz do repositório é o caminho para quem usa a IDE do Lazarus: abra o pacote, compile e adicione como dependência do seu projeto. O ZeosLib precisa estar instalado separadamente nesse caminho.

Conexão

Connect valida a configuração, resolve o dialeto e abre o pool. O que ele devolve — ILzNex — é o ponto de entrada para tudo. 

var
  Db: ILzNex;
begin
  Db := Connect(NewConfig
    .Client('mysql')
    .Host('mysql')
    .Port(3306)
    .Database('app')
    .User('root')
    .Password('secret')
    .Charset('utf8mb4')
    .LibraryLocation('/usr/lib/x86_64-linux-gnu/libmariadb.so.3')
    .Pool(2, 10)
    .AcquireTimeout(30000));
  try
    // ... use Db ...
  finally
    Db.Shutdown;
  end;
end;

Uma instância por processo é o padrão: a facade é dona do pool, e é o pool que serializa o acesso concorrente. Não crie ILzNex por requisição HTTP.

⚠
LibraryLocation

No Ubuntu 26.04 só existe libmariadb.so.3, e o auto-load do Zeos não a encontra. Informar LibraryLocation (ou a variável LZNEX_LIBRARY) é, na prática, obrigatório. Sem isso o sintoma é um erro de biblioteca ao conectar.

Dialetos registrados

UnitClient(…)DialectName
LzNex.Client.MySQL'mysql', 'mariadb'mysql
LzNex.Client.Postgres'postgresql', 'postgres'postgresql

Nome não registrado levanta ELzNexConfig. Para checar antes: IsClientRegistered('mysql'), de LzNex.Client; RegisteredClients devolve a lista do que está disponível.

Ciclo de vida

  • Connect abre o pool já com o mínimo de conexões configurado;
  • cada query pega uma conexão emprestada e devolve sozinha ao terminar;
  • Shutdown fecha as conexões ociosas e marca o pool como encerrado;
  • depois do Shutdown, qualquer Acquire levanta ELzNexPool.

Configuração

Três caminhos de entrada, do mais explícito ao mais automático — e eles se compõem.

  1. NewConfig.Client('mysql').Host(…) — em código;
  2. LoadConfigFile('database/lznex.json', 'development') — arquivo, por ambiente;
  3. ApplyEnvOverrides(Cfg) — variáveis LZNEX_* do processo.

O caminho do arquivo já aplica as LZNEX_* por cima do que leu. É isso que faz a mesma imagem de container servir para dev, CI e produção.

Arquivo JSON

A chave default escolhe o ambiente quando ninguém informa; cada ambiente é um objeto no primeiro nível. Um arquivo que tenha client ou connection na raiz é tratado como configuração única, sem ambientes. 

{
  "default": "development",
  "development": {
    "client": "mysql",
    "connection": {
      "host": "mysql",
      "port": 3306,
      "database": "lznex",
      "user": "root",
      "password": "secret",
      "charset": "utf8mb4",
      "libraryLocation": "/usr/lib/x86_64-linux-gnu/libmariadb.so.3"
    },
    "pool": { "min": 2, "max": 10, "acquireTimeout": 30000 },
    "migrations": { "table": "migrations", "directory": "database/migrations" },
    "seeds": { "directory": "database/seeds" },
    "props": { "timezone": "UTC" }
  },
  "test": {
    "client": "mysql",
    "connection": { "host": "mysql", "database": "lznex_test", "user": "root", "password": "secret" },
    "pool": { "min": 1, "max": 4 }
  }
}

As chaves de conexão podem ficar dentro de connection ou soltas no nó do ambiente — o leitor procura primeiro no aninhado, depois na raiz do ambiente. Chave desconhecida em props é repassada ao driver sem a config ter que conhecê-la. 

// o ambiente vem do parametro, de LZNEX_ENV, da chave "default" ou 'development'
Db := ConnectFromFile('database/lznex.json', 'test');

// ou, separando leitura de conexao:
Cfg := LoadConfigFile('database/lznex.json', '');
Cfg.Pool(1, 4);
Db := Connect(Cfg);

Ambiente inexistente levanta ELzNexConfig listando as chaves de primeiro nível do arquivo.

Validação

Connect chama Validate antes de abrir qualquer coisa. Levanta ELzNexConfig se faltar client, host ou database, se a porta não for positiva, se o máximo do pool for menor que 1, se o mínimo passar do máximo, ou se o timeout for negativo.

ILzNexLogger recebe cada query executada, com os binds e o tempo. O logger de console pronto escreve em stdout com flush. 

uses LzNex, LzNex.Config;

Db := Connect(NewConfig

  .Logger(TLzNexConsoleLogger.New(True)));   // False silencia so LogQuery

Por que o flush importa

stdout redirecionado — container, pipe, CI — é bufferizado. Sem flush, o log de um processo que morre no meio simplesmente desaparece. O logger de console e o CLI já dão flush a cada linha.

Logger próprio

type
  TMyLogger = class(TInterfacedObject, ILzNexLogger)
  public
    procedure LogQuery(const ASQL: string; const ABindings: TLzNexBindings;
      const AElapsedMs: Int64);
    procedure LogError(const ASQL: string; const AError: string);
    procedure LogWarning(const AMessage: string);
    procedure LogInfo(const AMessage: string);
  end;

ABindings.Describe devolve os valores com a tag de cada um (integer(7), string('ana')) — é descrição para humano, nunca SQL executável. O mesmo vale para Query.ToSQLString e Client.EscapeForLog: existem para log, e não devem ser enviados ao banco.

Query builder

Cada chamada acumula um statement na árvore e devolve a própria query. Nada vai ao banco até um terminal.

Db.Table('users') devolve um ILzNexQuery. Tudo encadeia; a execução só acontece em terminais — Get, First, Count, Insert, Update, Delete… — ou em ToSQL, que compila sem executar. 

// montar sem conexao: so precisa de um dialeto
Fragment := Db.Table('users').Where('id', 7).ToSQL;
Writeln(Fragment.Text);              // select * from `users` where `id` = ?
Writeln(Fragment.Bindings.Count);    // 1

Ordem das chamadas

A ordem entre grupos de cláusula nunca importa — Where antes ou depois de OrderBy dá o mesmo SQL, porque quem decide a ordem das seções é o dialeto. A ordem dentro de um grupo importa sempre: dois Where saem na sequência em que foram chamados, e os binds acompanham o texto.

Fonte e colunas

De onde a query lê e o que ela projeta.

Tabela e fonte

Sub := Db.Query.Table('logs').Select(['user_id']).Where('level', 'error');

⚠
Alias obrigatório

Subquery como fonte exige alias: compilar sem ele levanta ELzNexCompile mencionando alias. É restrição do SQL, não do LzNex.

Db.Query cria uma query sem tabela — é assim que se monta uma subquery para passar a FromSub, WhereInSub, JoinSub ou Union. AsAlias define o alias que a query usa quando é consumida como subquery.

DistinctOn

O builder consulta a capacidade do dialeto na hora da chamada: o erro aparece onde o método foi escrito, não no fim, quando a query compila.

Where e grupos

Valor entra sempre como bind. Números, strings e booleanos convertem sozinhos.

Comparação

Dois overloads: sem operador (assume =) e com operador explícito.

Db.Table('users').Where('id', 1)
Db.Table('users').Where('age', '>=', 18)
Db.Table('users').Where('a', 1).Where('b', 'x')        // and
Db.Table('t').Where('a', 1).OrWhere('b', 2).Where('c', 3)
Db.Table('t').WhereNot('a', 1)
SQL
select * from `users` where `id` = ?
select * from `users` where `age` >= ?
select * from `users` where `a` = ? and `b` = ?
select * from `t` where `a` = ? or `b` = ? and `c` = ?
select * from `t` where not `a` = ?
ℹ
O OR não contamina o resto

O conector é parâmetro de cada statement, não um estado do builder: OrWhere afeta só o predicado que ele introduz, como mostra o quarto exemplo acima.

Grupos de predicado

Como o FPC 3.2.2 não tem função anônima, o parêntese é aberto e fechado explicitamente. O builder mantém uma pilha de grupos. 

Db.Table('users')
  .Where('active', True)
  .WhereOpen
    .Where('role', 'admin')
    .OrWhere('role', 'owner')
  .WhereClose
SQL
select * from `users` where `active` = ? and (`role` = ? or `role` = ?)

binds: True | admin | owner

Grupos aninham, e um grupo pode abrir a cláusula:

Db.Table('t').Where('a', 1)
  .WhereOpen
    .Where('b', 2)
    .OrWhereOpen.Where('c', 3).Where('d', 4).WhereClose
  .WhereClose;

Db.Table('t')
  .WhereOpen.Where('a', 1).OrWhere('b', 2).WhereClose
  .Where('c', 3);
SQL
select * from `t` where `a` = ? and (`b` = ? or (`c` = ? and `d` = ?))
select * from `t` where (`a` = ? or `b` = ?) and `c` = ?

⚠
Grupo mal formado levanta

ToSQL exige OpenGroupCount = 0: grupo aberto e não fechado levanta ELzNexBuilder. WhereClose sem WhereOpen correspondente levanta na hora da chamada. Nenhum dos dois casos chega ao banco como SQL quebrado.

Joins

Join devolve ILzNexJoin, que herda ILzNexQuery: dá para encadear as cláusulas On* e continuar a query na mesma expressão. 

Db.Table('posts')
  .Join('users').OnColumns('posts.user_id', '=', 'users.id')
  .LeftJoin('tags').OnColumns('tags.post_id', '=', 'posts.id')
  .Where('posts.published', True)
  .Get;
SQL
select * from `posts`
  inner join `users` on `posts`.`user_id` = `users`.`id`
  left join `tags` on `tags`.`post_id` = `posts`.`id`
 where `posts`.`published` = ?

OnColumns ou OnValue

⚠
Dois métodos, não um

OnColumns compara identificadores (sem bind) e OnValue compara com valor (com bind). Um método único para os dois casos teria que adivinhar, e on('tags.active', '=', True) acabaria virando comparação com uma coluna chamada True — erro que não aparece nem na compilação nem no resultado. 

Db.Table('posts').LeftJoin('tags').OnValue('tags.active', '=', True)

Valores e binds

Todo dado do usuário entra na query como TLzNexValue e sai como bind. Nunca como texto.

Um record com tag

TLzNexValue é um record com um discriminante explícito (Kind: TLzNexValueKind) e um campo por representação. Não há Variant no meio: a conversão é decidida em tempo de compilação, o record cabe na pilha e cada leitura sabe exatamente o que tem na mão. 

V: TLzNexValue;

V := 42;                       // Kind = vkInteger
V := 'ana';                    // Kind = vkString
V := TLzNexValue.Null;         // Kind = vkNull
Writeln(V.Describe);           // NULL

Os quinze valores de TLzNexValueKind são vkUnset, vkNull, vkBoolean, vkInteger, vkInt64, vkFloat, vkCurrency, vkString, vkBytes, vkDate, vkTime, vkDateTime, vkIdentifier, vkRaw e vkSubQuery.

// P[0].Name = 'name' | P[1].Name = 'age' — a ordem e a do SQL

Vals(['only-the-key']);
// ELzNexBuilder: Vals: expected column/value pairs, got 1 items

ValueOf mapeia nil para TLzNexValue.Null e uma interface para TLzNexValue.Raw. Ponteiro não nulo levanta — é quase sempre um @ esquecido virando argumento de query.

A restrição do array of const

array of const transporta TVarRec, e TVarRec não tem caso para record. Ou seja: você não consegue passar um TLzNexValue dentro de Vals([...]) ou ValueList([...]). A tentativa não compila, ou levanta com o VType no texto. 

// ELzNexBuilder: TLzNexValue: unsupported type in array of const (VType=..).
// Remember: a record cannot be passed in an array of const.

O contorno é montar a lista com os tipos simples e sobrescrever a posição depois. Os dois arrays são arrays de verdade, então indexar e atribuir funciona: 

V := Vals(['name', 'ana']);
V[0].Value := TLzNexValue.Raw(Db.Raw('upper(?)', ['ana']));
Db.Table('users').Insert(V);
SQL
insert into `users` (`name`) values (upper(?))

binds: ana — o do raw, na posição da coluna

Para acrescentar um par que não cabe no array of const, estenda o array:

V := Vals(['name', AName, 'batch', ABatch]);
SetLength(V, 3);
V[2].Name  := 'migration_time';
V[2].Value := TLzNexValue.FromDateTime(Now);
Db.Table('migrations').Insert(V);

Para listas de string, StringsToValues evita o assunto por completo: WhereIn('status', StringsToValues(['a', 'b'])).

Segurança

O valor nunca é interpolado no SQL. Independente do que vier dentro da string, o compilador emite ? e guarda o conteúdo na lista de binds — quem monta a instrução no banco é o driver, com parâmetro ligado. 

Db.Table('users').Where('name', '''; drop table users; --').ToSQL;
SQL
select * from `users` where `name` = ?

binds: 1 — o bind é a string inteira, ponto e vírgula incluso

O que não é bind é identificador, e identificador é escapado dobrando o caractere de quote do dialeto: 

Db.Client.WrapIdentifier('we`ird')
Saída
`we``ird`

a crase dentro do nome vira crase dobrada

Db.Client.WrapIdentifier('we"ird')
Saída
"we""ird"

a aspa dentro do nome vira aspa dobrada

WrapQualified aplica o mesmo tratamento parte por parte em nomes com ponto, então u.name sai com cada segmento quotado individualmente. * e nome vazio passam sem quote.

⚠
O que sobra fora do bind

Valor e identificador estão cobertos. O que ainda depende de você é o texto que você mesmo escreve: o template de SQL cru e o nome de coluna que você repassa de uma entrada externa. Operador está protegido por lista fechada — veja operadores aceitos.

SQL cru

Um template com marcadores. O valor continua indo como bind, o identificador sai quotado pelo dialeto, e o resto do texto é seu.

A gramática do template

São seis marcadores, e só eles. Qualquer outro caractere passa intacto para o SQL final.

MarcadorConsomeSai comoGera bind
?um argumento posicional?sim
??um argumento posicionalidentificador quotadonão
\?nada? literalnão
:nomeo valor nomeado nome?sim
:nome:o valor nomeado nomeidentificador quotadonão
\:nada: literalnão

Nome de parâmetro aceita letra, dígito e _, e casa sem distinguir caixa. O mesmo :nome pode aparecer várias vezes: cada ocorrência vira um bind próprio, com o mesmo valor. Um : que não é seguido de caractere de nome passa como literal, sem virar marcador.

Posicional e nomeado não se misturam no mesmo template: o construtor escolhido define qual dos dois você está usando.

Os três construtores

Posicional

LzNexRaw('select * from t where id = ?', [7]).Build(Db.Client);

binds: 7

O marcador literal existe porque ? aparece em SQL legítimo — caminho de JSON, por exemplo:

binds: v — o \? não consumiu argumento nenhum

Template sem marcador nenhum é válido e devolve zero bind:

Nomeado

Nomeado paga a si mesmo quando o template é grande ou quando o mesmo valor aparece em mais de um lugar: você informa o valor uma vez e o LzNex gera um bind por ocorrência. 

LzNexRawNamed('select * from :table: where id = :id and owner_id = :id',
  Vals(['table', 'users', 'id', 42])).Build(Db.Client);
SQL
select * from `users` where id = ? and owner_id = ?

binds: 42 | 42 — :table: virou identificador, sem bind

⚠
O cast :: do PostgreSQL colide com :nome

Em id::text, o segundo : é seguido de letra e o parser entende :text como parâmetro nomeado — o Build levanta Raw: parameter ":text" was not given. Escreva id:\:text para escapar, ou use cast(id as text), que não tem o problema. Vale também em template posicional: o parser de nomeado roda sempre.

Build devolve texto e binds juntos

ILzNexRaw é um template guardado, não SQL pronto: ele só sabe o texto final depois de receber um dialeto. Daí a assinatura.

function Build(const AClient: ILzNexClient): TLzNexFragmentResolve os marcadores contra o dialeto e devolve o fragmento. nil levanta ELzNexBuilder.
function Template: stringO SQL original, com os marcadores. Útil em log e mensagem de erro.

TLzNexFragment carrega os dois lados em um só record — é o que impede texto e parâmetro de se separarem no caminho: 

F := Db.Raw('age > ? and city = ?', [18, 'Recife']).Build(Db.Client);
Writeln(F.Text);                // age > ? and city = ?
Writeln(F.Bindings.Count);      // 2
Writeln(F.Bindings.Describe);   // [integer(18), string('Recife')]

Concatenar fragmentos (Concat, Wrap, Prefix) junta os binds na mesma ordem do texto. O compilador do query builder é construído sobre isso, e é a razão pela qual um raw no meio de uma query grande não desalinha os parâmetros.

Contagem validada antes de montar

Build conta os marcadores posicionais do template e compara com a quantidade de argumentos antes de emitir um caractere. Discrepância nos dois sentidos levanta ELzNex, com os dois números e o template na mensagem. 

LzNexRaw('? and ?', [1]).Build(Db.Client);
// ELzNexBuilder: Raw: the template expected 2 positional argument(s) and got 1.
// Remember that "\?" is a literal and does not consume an argument. SQL: ? and ?

LzNexRaw('?', [1, 2]).Build(Db.Client);
// ELzNexBuilder: Raw: the template expected 1 positional argument(s) and got 2. ...

No caso nomeado, a checagem é por nome, nas duas direções:

LzNexRawNamed('id = :id', Vals(['other', 1])).Build(Db.Client);
// ELzNexBuilder: Raw: parameter ":id" was not given (1 named value(s) received).
// SQL: id = :id

LzNexRawNamed('id = :id', Vals(['id', 1, 'extra', 2])).Build(Db.Client);
// ELzNexBuilder: Raw: named parameter ":extra" does not appear in the template.
// SQL: id = :id

Valor nomeado sobrando é erro de propósito: quase sempre significa nome digitado diferente dos dois lados, e o silêncio sairia como um filtro que nunca foi aplicado.

ℹ
Dois momentos de erro

Argumento de tipo não suportado levanta já na construção, em LzNexRaw — é a conversão de array of const reclamando (um ponteiro, um record). Contagem e nome errados levantam no Build, que é quando o template é lido. Veja a restrição do array of const.

Raw dentro de raw

Um ? que recebe um valor de kind vkRaw não gera bind: o template interno é construído na hora e o texto dele entra no lugar, com os binds dele acrescentados na posição certa da lista. É o que permite compor um pedaço de SQL reaproveitável. 

Inner := LzNexRaw('coalesce(??, ?)', ['x', 0]);
R := LzNexRawValues('select ? + ?',

binds: nenhum

O cursor

ILzNexResult é uma casca fina sobre o IZResultSet do ZeosLib: avança para frente, uma linha por vez, sem buffer de todas as linhas em memória e sem componente visual. Na abertura ele lê a metadata uma única vez — nome e tipo de cada coluna — e usa isso em toda leitura seguinte.

O cursor fecha sozinho quando a interface é liberada: o destrutor chama Close. Variável local de escopo curto já é suficiente; Close explícito serve para encerrar antes do fim do escopo. Chamar duas vezes não faz mal.

Coluna que não existe

Field levanta ELzNexQuery e a mensagem lista as colunas que existem — é o que transforma um erro de digitação em dois segundos de depuração em vez de dez minutos. 

Rows := Db.Table('users').Select(['id', 'name']).Get;
Rows.Next;
Rows.Field('nome');
// ELzNexQuery: Column "nome" does not exist in the result. Columns: id, name

A busca tenta primeiro o nome exato e depois sem distinguir caixa, então Field('NAME') acha name. Em ILzNexRow o comportamento é o mesmo, com in the row no texto.

Quando a coluna é opcional — select que varia, por exemplo — use TryField:

if Row.TryField('deleted_at', V) and not V.IsNull then
  Writeln('removido em ', V.AsDateTime);

TryField existe só em ILzNexRow. No cursor, a pergunta equivalente é varrer FieldName até FieldCount - 1, ou materializar a linha com CurrentRow e perguntar lá.

O empréstimo da conexão

⚠
O resultado segura a conexão, não a variável de conexão

Um resultado vindo do pool carrega dentro dele o empréstimo da conexão. O empréstimo termina no fim da vida do resultado — não no fim do escopo onde a conexão foi pedida, e nem no Close: Close fecha o resultset do driver, mas a conexão só volta ao pool quando a última referência ao ILzNexResult é liberada.

Por isso Db.Fetch(…) e .Get funcionam sem você segurar nenhum ILzNexConnection: o resultado faz isso por você. E por isso guardar um ILzNexResult em variável global, campo de objeto ou cache é vazamento de conexão disfarçado. 

// errado: Rows e campo do objeto, a conexao fica emprestada indefinidamente
FRows := Db.Table('users').Get;

// certo: variavel local, o emprestimo acaba com o escopo
procedure Handle;
var
  Rows: ILzNexResult;
begin
  Rows := Db.Table('users').Get;
  while Rows.Next do
    ...;
end;

// certo: devolver o emprestimo antes do fim do escopo
Rows := Db.Table('users').Get;
List := Rows.ToRows;
Rows := nil;              // aqui a conexao volta ao pool
Process(List);            // as linhas sao copias, nao precisam do cursor

Com o pool esgotado, Acquire espera o timeout configurado e levanta ELzNexPool — a mensagem termina em Either max is too low, or some ILzNexConnection is being kept alive beyond the request scope, que é exatamente este sintoma. Veja pool de conexões.

ℹ
Terminal que materializa não deixa cursor aberto

First, Value, Scalar, Pluck, Count, Exists e Aggregate consomem o cursor internamente e devolvem dado copiado — nenhum deles prende conexão. Só Get e Db.Fetch devolvem o cursor em si.

CreateTable e Table devolvem ILzNexTable

Os dois devolvem a mesma interface, mas em modos diferentes: CreateTable em tmCreate e Table em tmAlter. O modo é verificado método a método, então uma operação de alter em modo create levanta ELzNexSchema na hora da chamada — não na compilação. 

T := Db.Schema.CreateTable('x');
T.DropColumn('y');       // ELzNexSchema: DropColumn só vale em alter table

T := Db.Schema.Table('x');
T.Engine('InnoDB');      // ELzNexSchema: Engine só vale em create table

Para o que é exclusivo do alter, veja Alterar tabela.

WithSchema

Db.Schema devolve um builder novo a cada chamada, e WithSchema guarda o nome nesse objeto. Guarde a referência, ou o qualificador se perde no caminho. 

Sch := Db.Schema.WithSchema('reports');
T := Sch.CreateTable('q');
T.Int('a');
DDL
create table `reports`.`q` (`a` int null)

O modificador cai na última coluna

O FPC 3.2.2 não tem função anônima, então não existe um objeto "coluna" para encadear à parte: NotNull, Default_, Unique, References e companhia aplicam-se sempre à última coluna adicionada ao builder. 

T.Str('email', 191).NotNull.Unique;   // os dois caem em email
T.Str('name');
T.NotNull;                            // cai em name, não em email

A ordem em que você chama os modificadores não muda nada: quem define a ordem das palavras no DDL é o dialeto. 

T := Db.Schema.CreateTable('mods');
T.Int('n').Default_(7).Unsigned.NotNull.Comment('qtd').Collate('utf8mb4_bin').After('id');
DDL
create table `mods` (`n` int unsigned not null default 7 comment 'qtd' collate 'utf8mb4_bin' after `id`)

chamar os seis na ordem inversa dá exatamente o mesmo texto

⚠
DropColumn e RenameColumn zeram a última coluna

Os dois não produzem uma coluna encadeável, então limpam o ponteiro interno. Um modificador depois deles levanta ELzNexSchema em vez de grudar na coluna anterior — o erro aparece na compilação do seu código de migration, não em produção. 

T := Db.Schema.CreateTable('x');
T.NotNull;    // ELzNexSchema: o modificador age na ÚLTIMA coluna adicionada

A lista completa de modificadores está em Modificadores.

Alguns pontos do exemplo: Increments já traz not null auto_increment primary key no próprio tipo; Timestamps adiciona duas colunas de uma vez; Engine e Charset só existem no create e saem depois do parêntese, na cláusula de opções da tabela. A tradução de cada tipo está em Tipos de coluna.

O plano de DDL

ToSQL devolve um TLzNexDdlPlan: um record com três listas de fragmentos, não uma string. DDL não cabe num comando só — um create table com índice e FK são vários comandos que precisam rodar em ordem.

Pre: TLzNexFragmentsO que tem de rodar antes do corpo. Reservado no contrato; nenhum dos dialetos atuais o usa, então vem vazio.
Statements: TLzNexFragmentsO corpo: o create table (sempre 1) ou os comandos de alter agregados (adições, alterações, drops e cada rename).
Post: TLzNexFragmentsO que depende da tabela já existir: índice, unique, FK, drop de índice e — fora do MySQL — os comment on.
function All: TLzNexFragmentsAs três listas concatenadas na ordem Pre → Statements → Post. É o que Execute roda.
function Count: IntegerTotal de comandos no plano, sem montar o array.

Os fragmentos do plano não carregam bind nenhum: em DDL o default é interpolado e escapado no texto, porque o banco não aceita parâmetro em definição de coluna.

ToSQL inspeciona, Execute roda

ToSQL compila e devolve — não toca na conexão. É o que você usa em teste, em revisão de migration ou para imprimir o DDL antes de aplicar. 

var
  T: ILzNexTable;
  P: TLzNexDdlPlan;
  Cmds: TLzNexFragments;
  I: Integer;
begin
  T := Db.Schema.CreateTable('users');
  T.Increments('id');
  T.Str('email', 191).NotNull.Unique;
  T.Str('name').Index;

  P := T.ToSQL;
  Writeln(P.Count);                 // 3
  Writeln(Length(P.Statements));    // 1
  Writeln(Length(P.Post));          // 2

  Cmds := P.All;
  for I := 0 to High(Cmds) do
    Writeln(Cmds[I].Text);
end;

Execute compila o mesmo plano, roda All comando por comando na conexão e devolve quantos comandos rodaram — não quantas linhas foram afetadas, que em DDL não quer dizer nada. 

N := T.Execute;   // 3, os mesmos 3 comandos do plano acima
ℹ
Cada um exige uma coisa diferente

ToSQL precisa de um ILzNexClient (o dialeto); Execute precisa também de um ILzNex. Um builder montado em modo só-SQL compila mas não executa: Execute levanta ELzNexSchema dizendo exatamente isso.

⚠
O plano não é atômico

Execute roda os comandos em sequência, um por vez. Se o terceiro falhar, os dois primeiros já foram aplicados — e em MySQL cada DDL faz commit implícito, então envolver tudo numa transação não desfaz o estrago. Plano que falha no meio pede correção manual ou um down que tolere tabela parcialmente criada.

Índice e FK nunca entram no create table

Só a primary key sai inline. Todo o resto — Index, Unique, References — vira comando separado no Post, um por índice. A razão é prática: a sintaxe de índice e de FK inline divergem entre os bancos (e em PostgreSQL o create index nem é parte do create table), enquanto o alter table ... add é igual nos dois. 

T := Db.Schema.CreateTable('pk1');
T.Int('a').NotNull;
T.Int('b').NotNull;
T.Primary(['a', 'b']);
DDL
create table `pk1` (`a` int not null, `b` int not null, primary key (`a`, `b`))

1 comando: PK composta é inline, o Post fica vazio

Os nomes de índice e de constraint são derivados da tabela e das colunas quando você não dá um — posts_slug_unique, posts_user_id_foreign. A regra de formação, o ConstraintName e as ações de FK estão em Índices e chaves.

Tipos de coluna

O tipo que você declara é lógico. Quem traduz para o tipo real é o dialeto — a mesma migration roda nos dois bancos.

O tipo é lógico

T.Str('email', 191) não diz varchar nem character varying: diz "texto curto com limite". O compilador de schema do dialeto é que escolhe o tipo nativo. É por isso que T.Bool('active') sai como tinyint(1) no MySQL e como boolean no PostgreSQL sem você mudar uma linha. 

T := Db.Schema.CreateTable('f');
T.Bool('active');
create table `f` (`active` tinyint(1) null)
create table "f" ("active" boolean null)

A consequência é que o DDL dos dois bancos é diferente de propósito, e o seu código não precisa saber qual está do outro lado. Veja Dialetos para o que mais muda entre eles.

Increments e BigIncrements

Os dois declaram a chave primária auto-incremento numa linha. O nome da coluna é opcional e vale id. 

T := Db.Schema.CreateTable('users');
T.Increments;
create table `users` (`id` int unsigned not null auto_increment primary key)
create table "users" ("id" serial primary key)
T := Db.Schema.CreateTable('events');
T.BigIncrements('uid');
create table `events` (`uid` bigint unsigned not null auto_increment primary key)
create table "events" ("uid" bigserial primary key)

Note que a chave primária sai no próprio tipo, não como índice: o plano de DDL fica com um único comando, sem nada no Post.

⚠
Modificador em coluna auto é ignorado em silêncio

O texto desses dois tipos já é completo, então o compilador não anexa nenhum modificador neles: T.Increments.Nullable.Default_(1) compila e produz o mesmo DDL de T.Increments. Se precisar de um inteiro comum, use Int ou BigInt e declare a PK à parte.

Decimal

Decimal já vem com precisão 8 e escala 2 — dinheiro é o caso comum. Os dois dialetos escrevem igual. 

T := Db.Schema.CreateTable('items');
T.Decimal('price');
T.Decimal('rate', 10, 4);
DDL
create table `items` (`price` decimal(8, 2) null, `rate` decimal(10, 4) null)

precisão zero ou negativa sai como decimal sem parâmetro

Timestamps

Timestamps adiciona created_at e updated_at de uma vez. Por padrão as duas saem not null com CURRENT_TIMESTAMP. 

T := Db.Schema.CreateTable('posts');
T.Timestamps;
DDL
create table `posts` (`created_at` timestamp not null default CURRENT_TIMESTAMP, `updated_at` timestamp not null default CURRENT_TIMESTAMP)

Com False, as duas ficam null e sem default — é o que você quer quando a aplicação grava os dois valores explicitamente. 

T := Db.Schema.CreateTable('posts');
T.Timestamps(False);
DDL
create table `posts` (`created_at` timestamp null, `updated_at` timestamp null)

O tipo é TIMESTAMP, não DATETIME, mesmo no MySQL — e isso é deliberado. TIMESTAMP tem semântica de instante: o MySQL guarda em UTC e converte na timezone da sessão, então o mesmo registro lido de dois servidores em fusos diferentes aponta para o mesmo momento. DATETIME é data-hora literal, sem fuso: muda de significado conforme quem lê. Para auditoria, o instante é o que importa. Em PostgreSQL os dois caem em timestamp, então lá a distinção não aparece no DDL.

Enum

Enum exige pelo menos um item — lista vazia levanta ELzNexSchema antes de a coluna ser criada. A implementação é bem diferente nos dois bancos. 

T := Db.Schema.CreateTable('orders');
T.Enum('status', ['new', 'done']);
create table `orders` (`status` enum('new', 'done') null)
create table "orders" ("status" text null check ("status" in ('new', 'done')))

No MySQL o enum é tipo de coluna, então a declaração se resolve sozinha. O PostgreSQL tem enum nativo, mas ele é um tipo do banco: exigiria um create type ... as enum antes do create table e um drop type correspondente no rollback — dois comandos que o contrato atual do plano de DDL não expressa, já que TLzNexDdlPlan descreve comandos de uma tabela, não o ciclo de vida de um tipo. Daí o caminho de text com check: dá a mesma garantia de domínio, aceita rollback trivial e não deixa tipo órfão no schema.

ℹ
Trocar o conjunto de valores

No MySQL é um modify da coluna; no PostgreSQL é derrubar e recriar o check. Enquanto isso não tem atalho no builder, o caminho é Db.Schema.Raw na migration. Se você já depende do enum nativo do PostgreSQL, declare a coluna com Specific('status', 'order_status') e crie o tipo por Raw.

Binary e Blob

Binary com tamanho vira varbinary(n) no MySQL; sem tamanho cai em blob. O PostgreSQL tem um só tipo binário de tamanho variável, então os três casos colapsam em bytea. 

T := Db.Schema.CreateTable('files');
T.Binary('hash', 16);
T.Binary('payload');
T.Blob('raw');
create table `files` (`hash` varbinary(16) null, `payload` blob null, `raw` blob null)
create table "files" ("hash" bytea null, "payload" bytea null, "raw" bytea null)
⚠
O MySQL não aceita default em tipo grande

Em text, mediumtext, longtext, blob e json o MySQL recusa DEFAULT literal. O compilador omite a cláusula em vez de gerar DDL que o banco rejeita — T.Text('t').Default_('x') sai como create table `txt` (`t` text null). Binary com tamanho é a exceção: como vira varbinary(n), o default sobrevive. Veja Modificadores.

Uuid

O PostgreSQL tem tipo uuid de 16 bytes, com comparação e indexação próprias. O MySQL não tem, e a coluna cai em char(36) — a forma textual com hífens. 

T := Db.Schema.CreateTable('tokens');
T.Uuid('id');
create table `tokens` (`id` char(36) null)
create table "tokens" ("id" uuid null)

A diferença importa na prática: no MySQL a comparação é textual e sensível ao formato gravado (caixa dos dígitos hexadecimais, presença dos hífens), e o índice custa 36 bytes por entrada. Normalize na aplicação, ou use Specific('id', 'binary(16)') se o volume justificar.

Specific

Specific é a saída para o que o builder não cobre: o texto vai cru para o lugar do tipo, e os modificadores normais continuam valendo depois dele. 

T := Db.Schema.CreateTable('places');
T.Specific('area', 'geometry').NotNull;
DDL
create table `places` (`area` geometry not null)
⚠
O texto não é validado

Nada inspeciona o que você passa: é interpolado como está, então nunca monte esse argumento com entrada de usuário. Texto vazio (ou só espaço) levanta ELzNexSchema na hora da chamada — é a única verificação. E a coluna fica amarrada a um banco: o mesmo Specific em outro dialeto quebra na execução, não na compilação.

Por que Char_ tem sublinhado

char é um tipo predefinido do Pascal. Um método chamado Char dentro da interface esconderia o tipo da linguagem para todo o corpo que usasse o builder, e qualquer Char escrito ali passaria a referir-se ao método. O sublinhado no fim resolve sem apelido nem prefixo: Char_.

O mesmo motivo vale para Default_ (Default é intrínseco em {$MODE DELPHI}, usado como Default(T)). Fora esses dois, nenhum método do builder carrega sublinhado — e os tipos cujo nome não colide ficam com o nome natural: Text, Date, Time, DateTime.

Str é um caso diferente: não há colisão, o nome é curto de propósito porque é o tipo mais usado numa migration. Ele é o varchar(n), com 255 de padrão.

Modificadores

Cada modificador age sobre a última coluna adicionada. Quem decide a ordem de emissão é o dialeto, não a ordem em que você chamou.

Os modificadores

function Nullable: ILzNexTableVolta a permitir nulo (é o estado inicial de toda coluna). Sai null.
function Unsigned: ILzNexTableNumérico sem sinal. Emitido no MySQL; ignorado em silêncio no PostgreSQL.

⚠
Modificador sem coluna levanta

Todos agem sobre a última coluna adicionada. Chamar qualquer um antes de ter coluna levanta ELzNexSchema com a mensagem apontando a forma correta (T.Str('email', 191).NotNull). Não há modificador "solto" acumulando estado no builder.

A ordem é do dialeto, não da chamada

O builder só registra quais modificadores a coluna tem. Na compilação, o dialeto percorre a sua lista fixa (ModifierOrder) e emite cada pedaço na posição onde aquele banco aceita. As duas chamadas abaixo saem byte a byte idênticas: 

T := Sch.CreateTable('mods');
T.Int('n').Default_(7).Unsigned.NotNull.Comment('qtd').Collate('utf8mb4_bin').After('id');

T2 := Sch.CreateTable('mods');
T2.Int('n').After('id').Collate('utf8mb4_bin').Comment('qtd').NotNull.Unsigned.Default_(7);
SQL
create table `mods` (`n` int unsigned not null default 7 comment 'qtd' collate 'utf8mb4_bin' after `id`)

o mesmo texto para as duas, em qualquer ordem de chamada

A ordem de emissão de cada dialeto:

DialetoOrdem
MySQLunsigned → null/not null → default → comment → collate → after
PostgreSQLnull/not null → default

Seguir a ordem de chamada geraria DDL inválido: int not null unsigned ou int default 7 not null são erro de sintaxe no MySQL, que exige unsigned colado no tipo e default depois da nulidade. É por isso que a ordem não é negociável — e por isso a lista do PostgreSQL é curta: o que aquele banco não tem como modificador de coluna simplesmente não entra na lista e nunca é emitido.

⚠
Em Increments nenhum modificador sai

Increments e BigIncrements já carregam o texto completo do tipo (int unsigned not null auto_increment primary key no MySQL, serial primary key no PostgreSQL). O compilador pula o laço de modificadores nessas colunas, então um .NotNull ou .Default_(1) encadeado ali não levanta e também não aparece no DDL.

Nulidade sempre explícita

Coluna nasce Nullable, e o DDL sempre escreve qual dos dois é — nunca deixa a decisão para o default do servidor: 

T := Sch.CreateTable('nul');
T.Int('a').Nullable;
T.Int('b').NotNull;
SQL
create table `nul` (`a` int null, `b` int not null)

Defaults

DDL não tem bind. O valor é interpolado e escapado pelo cliente do dialeto; Bindings.Count do statement é zero. DefaultRaw entra cru, sem quote nenhum, para o caso em que o padrão é expressão do banco. 

T := Sch.CreateTable('def');
T.Str('s', 10).Default_('abc');
T.Bool('b').Default_(TLzNexValue.FromBoolean(True));
T.Timestamp('ts').DefaultRaw('CURRENT_TIMESTAMP');
SQL
create table `def` (`s` varchar(10) null default 'abc', `b` tinyint(1) null default 1, `ts` timestamp null default CURRENT_TIMESTAMP)

binds: nenhum

Como o valor vai para dentro do texto, Default_ é o único ponto do schema builder onde entrada de usuário não passa por bind. Não monte default a partir de string vinda de fora; se o padrão é dinâmico, prefira preencher no insert.

ℹ
DEFAULT em TEXT, BLOB e JSON é omitido no MySQL

O MySQL rejeita default literal nesses tipos com o erro 1101 (BLOB, TEXT, GEOMETRY or JSON column can't have a default value) e derrubaria a migration inteira. O compilador do MySQL então descarta o default em silêncio em text, tinytext, mediumtext, longtext, blob, json e jsonb. Binary(n) com tamanho vira varbinary(n) e aceita default; sem tamanho vira blob e não aceita. 

T := Sch.CreateTable('txt');
T.Text('t').Default_('x');
SQL
create table `txt` (`t` text null)

o default não aparece, e nada é levantado

Diferenças por dialeto

Unsigned é a diferença que mais morde: o PostgreSQL não tem o conceito, e levantar ali travaria toda migration escrita para MySQL. A escolha foi ignorar em silêncio para a migration continuar rodando nos dois bancos. 

T.Int('n').Unsigned.NotNull;
create table `u` (`n` int unsigned not null)
create table "u" ("n" integer not null)

se o domínio exige não-negativo, use Specific com um check

T.Str('email', 191).Comment('login of the user');

Índices e chaves

Índice e constraint saem como comando próprio no Post do plano. A exceção é a primary key, que vai inline no create table.

Por que fora do create table

O create table é um único statement com as colunas. Todo índice, unique e chave estrangeira vira um comando separado na lista Post do plano DDL — um comando por índice. Isso mantém a mesma montagem funcionando em create e em alter, e faz um índice que falha não levar o create table junto. 

T := Sch.CreateTable('users');
T.Increments('id');
T.Str('email', 191).NotNull.Unique;
T.Str('name').Index;
P := T.ToSQL;
SQL
create table `users` (`id` int unsigned not null auto_increment primary key, `email` varchar(191) not null, `name` varchar(255) null)
alter table `users` add unique `users_email_unique`(`email`)
alter table `users` add index `users_name_index`(`name`)

Statements: 1 · Post: 2 · P.Count = 3

O nome automático

Sem ConstraintName, o nome é <tabela>_<colunas>_<tipo>: a tabela, cada coluna na ordem, e o sufixo do tipo (index, unique, primary, foreign). Tudo em caixa baixa, com . e - trocados por _ para o nome continuar sendo um identificador simples. Quem monta é IndexName no compilador do dialeto, e dá para chamar direto: 

Cmp := Db.Client.NewSchemaCompiler;
Cmp.IndexName('t', StringsToValues(['c']), ixUnique)         // t_c_unique
Cmp.IndexName('My.Tbl', StringsToValues(['A-B']), ixIndex)   // my_tbl_a_b_index

Unique e index

As formas de uma coluna (Unique, Index sem argumento) agem sobre a última coluna adicionada. As formas com lista montam índice composto, e o nome une as colunas na ordem em que você passou. 

T := Sch.CreateTable('comp');
T.Int('a').NotNull;
T.Int('b').NotNull;
T.Unique(['a', 'b']);
T.Index(['b', 'a']);
SQL
alter table `comp` add unique `comp_a_b_unique`(`a`, `b`)
alter table `comp` add index `comp_b_a_index`(`b`, `a`)

a ordem das colunas muda o nome e muda o índice

A sintaxe do comando difere por banco:

alter table `users` add unique `users_email_unique`(`email`)
alter table `users` add index `users_name_index`(`name`)
alter table "users" add constraint "users_email_unique" unique ("email")
create index "users_name_index" on "users" ("name")

unique é constraint; index comum é create index

Primary key

A primary key é a única que vai inline no create table, como cláusula primary key (…) depois das colunas. Não gera comando extra: índice de PK criado depois do fato custaria uma reescrita da tabela. 

T := Sch.CreateTable('pk1');
T.Int('a').NotNull;
T.Int('b').NotNull;
T.Primary(['a', 'b']);
SQL
create table `pk1` (`a` int not null, `b` int not null, primary key (`a`, `b`))

Post: 0 comandos

Primary sem argumento também compõe: a segunda chamada acrescenta a coluna à PK que já existe em vez de criar uma segunda. 

T := Sch.CreateTable('pk2');
T.Int('a').NotNull.Primary;
T.Int('b').NotNull.Primary;
SQL
create table `pk2` (`a` int not null, `b` int not null, primary key (`a`, `b`))

Increments e BigIncrements já embutem primary key no próprio tipo, então não precisam (nem devem) de Primary em cima.

Chave estrangeira

No MySQL, unique também é índice

O MySQL implementa unique como índice único, e drop index remove os dois. DropUnique e DropIndex portanto geram o mesmo comando — a única diferença é o sufixo do nome procurado (_unique contra _index). Primary e foreign key têm sintaxe própria (drop primary key, drop foreign key).

Alterar tabela

Db.Schema.Table(nome) entra em modo alter. O builder agrega as operações do mesmo tipo num comando só, em vez de emitir um alter table por coluna.

O que o builder agrega

Na compilação, as colunas do alter são separadas em três baldes e cada balde vira um statement. Rename de coluna sai em comando próprio, e índice vai para o Post como em create:

BaldeVira
todas as adições1 statement com os add separados por vírgula
todas as colunas marcadas com Change1 statement com os modify/alter column
todos os DropColumn1 statement com os drop
cada RenameColumn1 statement por rename
índices, uniques, FKs e drops delescomandos no Post

Agregar importa porque cada alter table no MySQL pode reescrever a tabela inteira: três comandos custam três reescritas, um comando custa uma. 

T := Sch.Table('users');
T.Str('nick', 50);
T.Int('age').NotNull;
T.Text('bio').Change;
T.DropColumn('old1');
T.DropColumn('old2');
T.RenameColumn('a', 'b');
T.Index(['nick']);
T.DropIndex(['age']);
P := T.ToSQL;
SQL
alter table `users` add `nick` varchar(50) null, add `age` int not null
alter table `users` modify `bio` text null
alter table `users` drop `old1`, drop `old2`
alter table `users` rename column `a` to `b`
alter table `users` add index `users_nick_index`(`nick`)
alter table `users` drop index `users_age_index`

Statements: 4 · Post: 2 — os dois últimos são o Post

A ordem dos statements é sempre essa: adições, alterações, drops, renames. Não é a ordem das chamadas — declarar o DropColumn antes do Str dá o mesmo plano.

Prefixos por dialeto

A diferença entre os dois bancos no alter é só o prefixo de cada operação. O MySQL usa a forma curta; o PostgreSQL exige a palavra column:

T.Int('age').NotNull;

T := Sch.Table('users');

alter table `users` drop `legacy`

RenameColumn usa a mesma forma nos dois: alter table … rename column … to ….

⚠
DropColumn e RenameColumn zeram a última coluna

Os dois não deixam coluna "atual" no builder — não haveria sentido em aplicar NotNull a uma coluna que está sendo removida ou renomeada. Um modificador encadeado depois deles levanta ELzNexSchema, a mesma exceção de modificador sem coluna anterior. É erro em tempo de montagem, não DDL torto chegando no banco. 

T := Sch.Table('x');
T.Int('a');
T.DropColumn('a');
T.NotNull;            // ELzNexSchema: nao ha coluna para aplicar

T := Sch.Table('x');
T.RenameColumn('a', 'b');
T.Nullable;           // ELzNexSchema: a mesma coisa

Um alter sem operação nenhuma também levanta na compilação: ToSQL de um Table(…) vazio é erro, não plano vazio.

Opções de tabela

Engine, Charset, TableCollate e TableComment valem só em create table — em alter levantam ELzNexSchema. No MySQL elas formam a cláusula depois do fecha-parênteses: 

T := Sch.CreateTable('opt');
T.Increments;
T.Engine('InnoDB').Charset('utf8mb4').TableCollate('utf8mb4_bin').TableComment('oi');
SQL
create table `opt` (`id` int unsigned not null auto_increment primary key) engine = InnoDB default character set utf8mb4 collate utf8mb4_bin comment = 'oi'
ℹ
No PostgreSQL a cláusula sai vazia

Nada de engine, character set ou collate de tabela existe lá, então a cláusula de opções é string vazia e as três chamadas são ignoradas em silêncio — a mesma escolha de Unsigned, para a migration rodar nos dois bancos. TableComment é a exceção: volta como comment on table "opt" is 'oi' no Post.

Migrations

Histórico versionado do schema, em Pascal ou em .sql, com lock de processo concorrente e rollback por batch.

O modelo

Cada migration tem um Id (o timestamp) e um nome completo (<id>_<descricao>). O Id ordena; o nome é o que vai para a tabela de controle e o que decide se já rodou.

batchToda chamada de Latest grava as migrations que aplicou com o mesmo número de batch (o maior já gravado + 1). É isso que dá sentido a "desfazer o último deploy".
comparação por nomeAplicada ou não é uma busca de string na coluna name. Não há checksum do corpo da migration: editar uma migration já aplicada não é detectado, e o LzNex não vai reaplicá-la.
rollbackRollback pega o maior batch e desfaz as linhas daquele batch na ordem inversa de aplicação. RollbackAll desfaz tudo, também de trás para frente.
ℹ
Sem checksum, por escolha

Guardar e conferir um hash do corpo significaria quebrar o deploy por uma mudança de espaço em branco, e o hash de uma migration em Pascal só existiria depois de compilada. A regra é mais simples: migration aplicada é imutável. Mudou de ideia? Nova migration.

Duas fontes, um histórico

O migrator junta as fontes, ordena tudo pelo Id e trata a lista como uma só. Uma migration em Pascal de janeiro roda antes de uma .sql de fevereiro, e as duas vão para a mesma tabela migrations. Id repetido entre fontes levanta ELzNexMigration — se dois Ids são iguais, não existe ordem.

Pascal →

Uma classe com Up/Down. Usa o schema builder, tem tipo e é compilada. Precisa de rebuild.

.sql →

Um par up/down no disco, lido em tempo de execução. Sem rebuild, sem portabilidade entre dialetos.

A fonte .sql sai do diretório de migrations.directory na config e é opcional: diretório ausente não é erro, fica só a fonte de código. Veja configuração.

Id e MigrationName são métodos de classe

Repare no class function. O registry precisa ordenar a lista e detectar Id duplicado no momento do RegisterMigration, que roda no initialization da unit — antes de existir qualquer banco. Sendo métodos de classe, isso é feito sem instanciar nada. A instância só nasce quando o migrator vai de fato aplicar a migration. 

// no initialization: ordena e valida sem criar objeto

// na hora de aplicar: ai sim instancia
Mig := CreateMigration(TCreateUsers);
Mig.Up(Db);

A convenção de nome é o contrato

O descobridor varre o diretório e só olha arquivos terminados em .up.sql. O nome da migration é o que sobra depois de tirar esse sufixo, e o Id é o prefixo até o primeiro _. Qualquer outro arquivo no diretório (um leiame.txt, por exemplo) é ignorado.

ArquivoPapel
20261025090000_add_phone.up.sqlObrigatório. Define a migration. Sem ele não há migration nenhuma — o .down.sql sozinho é invisível.
20261025090000_add_phone.down.sqlOpcional. Sem ele a migration é irreversível: Down levanta ELzNexMigration.

alter table `users` add `phone` varchar(20) null after `name`;
-- 20261025090000_add_phone.down.sql

ℹ
Irreversível levanta; down vazio é pior

Faltando o .down.sql, o Down não roda nada e levanta dizendo qual arquivo criar. A alternativa — aceitar um .down.sql vazio — daria um rollback que reporta sucesso, apaga a linha da tabela de controle e não desfez nada. Falhar alto é o comportamento honesto.

Um arquivo, vários comandos

O arquivo é quebrado em comandos pelo ;, mas o splitter entende o texto em volta: ponto e vírgula dentro de literal (', ", `), dentro de --, de # ou de /* */ não separa nada. Cada comando vai ao banco sozinho, e o erro diz qual deles falhou (statement 2 of 4) com o SQL inteiro anexado. 

create table a (
  id int,
  nota varchar(50) default 'ponto; e virgula'
);

/* bloco; com ; dentro */
insert into a (id, nota) values (1, 'a;b');
# comentario de cerquilha;
update a set nota = 'c' where id = 1;
;

3 comandos: o create, o insert e o update — o ; solto do fim não gera comando vazio

Literal aberto sem par, ou /* sem */, levanta ELzNexMigration e nada é executado: sem saber onde um comando termina, não há palpite seguro.

A marca nosplit

Corpo de procedure, function ou trigger tem ; interno que pertence ao corpo, não ao script. Com a marca lznex:nosplit em qualquer lugar do arquivo (num comentário, por convenção na primeira linha), o arquivo vai ao banco inteiro, como um único comando. 

-- lznex:nosplit
create procedure p() begin select 1; select 2; end

1 comando. É tudo ou nada: a marca vale para o arquivo todo, então deixe um objeto por arquivo.

O lock é um UPDATE condicional

Antes de mexer no histórico, o migrator roda um único comando e olha quantas linhas ele afetou: 

Db.Table('migrations_lock').Where('is_locked', 0).Update(Vals(['is_locked', 1]));
SQL
update `migrations_lock` set `is_locked` = ? where `is_locked` = ?

binds: 1 | 0 — pegou o lock se, e só se, afetou exatamente 1 linha

Afetar exatamente 1 é o teste inteiro. Quem chegou primeiro virou o 0 em 1 e levou; quem chegou depois não casa o where, afeta 0 linhas e levanta ELzNexMigrationLock. Não há leitura seguida de escrita, logo não há janela entre checar e marcar: o próprio banco serializa o update. E como é só update com where, funciona igual em qualquer banco — sem get_lock, sem advisory lock, sem nada específico de dialeto. 

Db.Table('migrations_lock').Update(Vals(['is_locked', 0]));
SQL
update `migrations_lock` set `is_locked` = ?

binds: 0 — o que Unlock e o migrate:unlock fazem

⚠
Quem falha ao pegar o lock não o solta

O Unlock só é chamado por quem conseguiu o lock — no fim do trabalho ou no except do próprio trabalho. O processo que perdeu a disputa sai pela exceção antes disso e não encosta no lock, senão liberaria o lock de outro processo que está migrando agora. No CLI essa disputa tem exit code próprio: 

lznex migrate:latest; echo $?
saída
lock error: The migrations table is already locked (migrations_lock affected 0 rows, expected 1).
Another process is migrating right now, or a previous process died holding the lock. If you are sure no migration is running, run "migrate:unlock".
3

exit 3 só para o lock; 1 para erro de migration, 2 para uso errado do comando

Exit code 3 existe para o script de deploy distinguir "outro nó já está migrando, pode seguir" de "a migration quebrou, pare tudo". Lock preso por processo morto só sai com migrate:unlock, de propósito: não há timeout que consiga adivinhar se o outro processo morreu ou está num alter table de duas horas.

Dois jeitos de se machucar

⚠
No MySQL, DDL não é transacional

create, alter e drop fazem commit implícito: a transação que o migrator abriu termina ali, e o rollback depois disso não desfaz o DDL já executado — pode até deixar a linha da tabela de controle fora de sincronia com o schema. Quando o dialeto é assim, o migrator loga um aviso. Escreva a migration como um passo estrutural só e deixe-a reentrante (DropTableIfExists em vez de DropTable, checar HasColumn antes de adicionar), para que rodar de novo depois de um erro no meio funcione. PostgreSQL faz DDL dentro de transação e não tem esse problema.

⚠
Linha aplicada sem migration é corrupção

Toda operação compara a tabela de controle com as fontes. Linha em migrations cujo name não existe em nenhuma fonte faz o migrator levantar ELzNexMigration listando as órfãs — e não roda nada. Ele não pode seguir: não existe Down para desfazer aquilo, e ignorar silenciosamente daria um rollback que pula migrations. As três causas são sempre as mesmas: arquivo renomeado depois de aplicado, arquivo apagado, ou a unit tirada do uses agregador. Restaure a migration, ou apague a linha na mão.

Seguindo: seeds para popular dados, transações para o que o migrator usa por baixo, e erros para a hierarquia de exceções.

Seeds

Popular dados. Sem histórico, sem lock e sem transação — a idempotência é responsabilidade da própria seed.

⚠
Unit fora do uses: a seed não existe

Mesma armadilha das migrations. Se nenhum uses alcança a unit da seed, o FPC não a linka, o initialization não roda e o RegisterSeed nunca acontece — seed:run reporta 0 seed(s) executed e vai embora feliz. Com --only a mensagem de erro lista as seeds registradas, o que é o jeito mais rápido de confirmar o diagnóstico:

A cura é um agregador, igual ao das migrations: uma unit Seeds.All cujo uses lista todas as seeds, e o programa dá uses Seeds.All.

ℹ
seed:make cria .sql, mas seed:run não lê .sql

Deixar o arquivo lá e esperar que rode é o erro mais fácil de cometer aqui. Passe o SQL para dentro de um Run (ADb.Execute resolve, se for SQL cru mesmo) e registre a classe.

Transações

Uma transação fixa uma conexão do pool e devolve o empréstimo no Commit ou no Rollback — não no destrutor.

Abrir, usar, concluir

Db.Transaction tira uma conexão do pool e a mantém fixada até a transação terminar. Tudo que sai dessa transação — query, Execute, Fetch — vai para aquela conexão, e só para ela.

ILzNexTransaction herda ILzNex: o objeto da transação responde à API inteira da facade. Não existe objeto "transação" separado com métodos próprios de escrita; é a mesma facade, amarrada a uma conexão. 

Trx := Db.Transaction;
try
  Trx.Table('accounts').Where('id', 1).Decrement('balance', 100);
  Trx.Table('accounts').Where('id', 2).Increment('balance', 100);
  Trx.Commit;
except
  on E: Exception do
  begin
    if not Trx.IsCompleted then
      Trx.Rollback;
    raise;
  end;
end;
SQL
update `accounts` set `balance` = `balance` + ? where `id` = ?
update `accounts` set `balance` = `balance` + ? where `id` = ?

binds: -100 | 1 · 100 | 2 — Decrement é um counter com delta negativo

procedure RollbackDesfaz e conclui. Solta a conexão na hora.
function Savepoint: ILzNexTransactionAbre um bloco interno na mesma conexão. Em transação concluída, levanta.
function IsCompleted: BooleanTrue depois de Commit ou Rollback. É o que o except consulta antes de desfazer.
function Level: Integer1 na raiz, 2 no primeiro savepoint, e assim por diante.
ℹ
O destrutor desfaz, e nunca levanta

Se a interface morrer sem Commit, o destrutor faz rollback — inclusive quando a saída foi por exceção, e inclusive para savepoint abandonado. Se esse rollback de emergência falhar (conexão já caiu, por exemplo), o erro vai para o logger e não é propagado: destrutor que levanta perderia a exceção original e vazaria o objeto. O resultado prático é que não fica transação aberta nem conexão vazada, mesmo com raise no meio do bloco.

Por que Commit solta a conexão na hora

Commit e Rollback não só terminam a transação no banco: eles soltam a referência da conexão imediatamente, devolvendo o empréstimo ao pool ali mesmo. O caminho natural em Pascal seria deixar isso para o destrutor — e seria errado aqui.

No FPC 3.2.2, o temporário de interface que uma função devolve só é liberado no fim do procedimento. Ou seja: Trx := nil não destrói o objeto, porque o compilador ainda segura uma referência escondida ao resultado de Db.Transaction até o end do seu procedimento. Com o empréstimo preso ao destrutor, um laço de trabalho com N threads e pool de tamanho N prenderia uma conexão por thread pelo resto do procedimento — e a próxima thread a pedir conexão esperaria até o acquireTimeout para então levantar ELzNexPool. 

procedure ProcessaLote(const ADb: ILzNex);
var
  Trx: ILzNexTransaction;
  I: Integer;
begin
  for I := 1 to 100 do
  begin
    Trx := ADb.Transaction;
    Trx.Table('jobs').Where('id', I).Update(Vals(['done', True]));
    Trx.Commit;        // conexao volta ao pool AQUI
    Trx := nil;        // nao destroi o objeto: o temporario do FPC ainda o segura
  end;
end;                   // so aqui os temporarios morrem

com a liberação no destrutor, este laço esgotaria o pool na segunda volta

Depois de concluída não tem mais conexão

A consequência direta: a transação concluída fica sem conexão, e qualquer operação que precise de uma levanta ELzNexTransaction. Isso é deliberado. A alternativa seria pegar calada outra conexão do pool e executar fora da transação — o comando funcionaria, o dado seria gravado e o bug só apareceria quando alguém notasse que aquele update não participou do commit de ninguém. 

Trx := Db.Transaction;
Trx.Table('users').Insert(Vals(['name', 'ana']));
Trx.Commit;

Savepoints

Savepoint abre um bloco interno na mesma conexão e no mesmo begin do banco. Desfazer o interno não derruba o externo. 

Trx := Db.Transaction;
try
  Trx.Table('orders').Insert(Vals(['customer_id', 7]));

  Sp := Trx.Savepoint;              // Sp.Level = 2
  try
    Sp.Table('order_items').Insert(Vals(['order_id', 1, 'sku', 'X']));
    Sp.Commit;
  except
    if not Sp.IsCompleted then
      Sp.Rollback;                  // so os itens voltam; a ordem continua
  end;
  Sp := nil;

  Trx.Commit;
except
  if not Trx.IsCompleted then
    Trx.Rollback;
  raise;
end;

Trx.Transaction dentro de uma transação é apelido de Savepoint. A sobrecarga com isolamento, porém, levanta: isolamento é propriedade da transação raiz, um savepoint não tem o seu.

Destruição LIFO é garantida

O savepoint guarda o pai por interface, então o refcount do pai não chega a zero enquanto o filho existir: o pai nunca é destruído antes do filho, mesmo que a variável dele saia de escopo primeiro. E quem solta a conexão de volta ao pool é a transação raiz — o savepoint compartilha a conexão emprestada, não pede outra, e o Commit dele apenas fecha o nível interno.

Concluir a raiz com savepoint aberto levanta, com os dois níveis na mensagem: 

Trx := Db.Transaction;
Sp := Trx.Savepoint;
Trx.Commit;
// ELzNexTransaction: Commit with a savepoint still open: this transaction is
// at level 1 but the connection is at level 2. Complete the inner Savepoint
// (Commit/Rollback) before completing the outer transaction -- savepoints
// must be closed in LIFO order.

Isso é checado contra o nível real da conexão, não contra um contador interno, então vale também para savepoint aberto por outro caminho. Se o dialeto não tiver savepoint, Db.Client.SupportsSavepoints devolve False — MySQL e PostgreSQL devolvem True.

Isolamento

O nível é pedido na abertura e aplicado só na raiz. Banco que recusa o nível faz Db.Transaction levantar ELzNexTransaction com a mensagem do servidor anexada — melhor que seguir num isolamento diferente do pedido. 

Trx := Db.Transaction(ilSerializable);
try
  Saldo := Trx.Table('accounts').Where('id', 1).Value('balance').AsInt64;
  Trx.Table('accounts').Where('id', 1).Update(Vals(['balance', Saldo - 10]));
  Trx.Commit;
except
  if not Trx.IsCompleted then
    Trx.Rollback;
  raise;
end;

Lock pessimista

ForUpdate e ForShare só fazem sentido dentro de uma transação: o lock vive até o commit ou o rollback. Fora de transação, cada comando faz seu próprio commit e o lock morre antes de você usá-lo. 

Trx := Db.Transaction;
try
  Job := Trx.Table('jobs')
    .Where('status', 'pending')
    .OrderBy('id')
    .ForUpdate
    .SkipLocked
    .First;

  if Job <> nil then
    Trx.Table('jobs').Where('id', Job.Field('id')).Update(Vals(['status', 'running']));
  Trx.Commit;
except
  if not Trx.IsCompleted then
    Trx.Rollback;
  raise;
end;
SQL
select * from `jobs` where `status` = ? order by `id` asc limit ? for update skip locked

binds: pending | 1 — a cláusula de lock é sempre a última

function ForShare: ILzNexQueryfor share: outros podem ler, ninguém pode escrever.
function SkipLocked: ILzNexQueryskip locked: pula as linhas travadas em vez de esperar. É o que faz N workers pegarem jobs diferentes sem combinar nada.

⚠
Transação não atravessa thread

A conexão fixada é de uma thread. Passar o ILzNexTransaction (ou a conexão dele) para outra thread intercala comandos de duas threads na mesma conexão, e nem o protocolo do banco nem o cache de statements aguentam isso — o resultado vai de bind embaralhado a erro de protocolo. Cada thread abre a sua transação, com a sua conexão do pool. Veja pool.

O migrator usa exatamente isso: cada migration com UseTransaction roda numa transação, e a linha da tabela de controle é gravada dentro dela.

Pool e threads

Uma conexão por operação, emprestada e devolvida sozinha. O que muda quando o código roda dentro de um servidor que atende cada requisição numa thread.

Por que um pool próprio

O LzNex fala com o banco através do Zeos, e uma IZConnection do Zeos não pode ser compartilhada entre threads: o estado de protocolo é um só (statement preparado, resultset corrente, nível de transação). Duas threads usando a mesma conexão embaralham esse estado — o sintoma vai de resultado trocado a erro de protocolo.

Ao mesmo tempo, um servidor HTTP em FPC atende cada conexão numa thread. Ou seja: concorrência não é opcional, é o modo normal de operação. Abrir uma conexão nova por requisição resolveria o isolamento, mas paga TCP, handshake e autenticação a cada chamada.

O pool é a saída: um conjunto de conexões reutilizáveis, cada uma emprestada a uma única thread de cada vez. Quem atende a requisição recebe uma conexão exclusiva pelo tempo da operação e devolve depois.

As duas garantias

Tudo o que o pool promete cabe em duas frases, e as duas são verificadas pela suíte de concorrência.

Devolução automática →

A conexão volta no destrutor do empréstimo. Não existe chamada de devolução para esquecer — nem no caminho de exceção.

Teto respeitado →

Nunca mais que max conexões abertas. Com todas ocupadas, Acquire espera; estourar o timeout levanta ELzNexPool com diagnóstico.

O empréstimo é um ILzNexConnection que embrulha a conexão real. Quando a última referência morre, o destrutor devolve a conexão de dentro ao pool. É só isso: não há Release público para chamar, nem try/finally para montar. Se uma exceção sobe no meio da query, a conexão volta no desempilhamento.

Na devolução, o pool ainda verifica o estado da conexão: se ficou com transação aberta, faz Rollback; se está fechada ou deu erro na verificação, descarta em vez de devolver uma conexão suja ao próximo que pedir. 

ELzNexPool: Pool exhausted: 8 connections in total (max 8), 8 in use.
Waited 30000 ms and none was returned. Either max is too low, or some
ILzNexConnection is being kept alive beyond the request scope.

A mensagem é assim de propósito: diz o tamanho atual, o teto, quantas estão em uso e quanto esperou. Com esses quatro números dá para separar as duas causas possíveis — max baixo para a carga, ou alguém segurando um ILzNexConnection além do escopo da requisição.

No uso normal ninguém toca no pool

Db.Pool existe para diagnóstico e para teste. No código de aplicação você não chama Acquire: cada operação terminal da query pega uma conexão, usa e devolve. Uma conexão por operação. 

// cada linha pega e devolve uma conexao, por conta propria
Db.Table('users').Count;
Db.Table('users').Where('id', 1).Value('name');
Db.Table('users').Insert(Vals(['name', 'Ana']));

InsertGetId é o caso que exige cuidado, e é tratado: ele pega a conexão uma vez e roda o insert e o LastInsertId na mesma conexão. Se fossem duas, o id voltaria de outra sessão — em concorrência, o id de outra thread.

⚠
Cursor aberto segura o empréstimo

Get devolve um ILzNexResult que carrega o empréstimo junto: a conexão só volta ao pool quando o cursor é liberado. Um resultset guardado num campo de classe prende uma conexão pelo tempo de vida do objeto. Consuma o cursor e solte-o (R := nil), ou use ToRows para materializar as linhas e liberar a conexão.

⚠
No FPC 3.2.2 o temporário de interface só morre no fim da rotina

Várias operações dentro de uma mesma rotina acumulam empréstimos: cada temporário de ILzNexConnection só é liberado quando a rotina retorna. O sintoma é InUse subindo num laço longo e, no limite, pool esgotado. A solução é escopo: cada passo numa rotina sua, como no diagnóstico tests/DiagPool.lpr.

Regras para código multi-thread

  • Uma facade por processo. O ILzNex devolvido por Connect é compartilhável entre threads — ele é a porta do pool, não uma conexão. Abrir uma facade por requisição significa abrir um pool por requisição.
  • Nunca uma conexão global compartilhada. Não guarde o resultado de Db.Connection numa variável global, num singleton ou num campo de longa vida: isso é exatamente o IZConnection compartilhado que o pool existe para evitar — e de quebra prende o empréstimo para sempre.
  • Query e transação não atravessam thread. Monte, execute e descarte na mesma thread. Um ILzNexQuery ou ILzNexTransaction passado para outra thread leva consigo a conexão emprestada.
  • cthreads no início do uses em Unix. Sem ela o RTL não inicializa o suporte a threads e a seção crítica do pool não protege nada. Precisa ser a primeira unit do programa.
  • Cursor aberto segura o empréstimo. Vale repetir aqui: um ILzNexResult vivo é uma conexão fora do pool. 
program Api;

{$MODE DELPHI}{$H+}

uses
  {$IFDEF UNIX}{$IFDEF UseCThreads}
  cthreads,
  {$ENDIF}{$ENDIF}
  SysUtils,
  Horse,
  LzNex,
  LzNex.Client.MySQL;

ParallelTransactionsAreIsolated Uma thread abre transação, insere e não commita. A thread principal conta essas linhas e tem que ver zero: dado não commitado não vaza para outra conexão. Depois do Rollback, continua zero.
PoolReleasesEveryConnection Depois de 6 threads de carga, Pool.InUse = 0 e Pool.Size <= 8: nada ficou preso e o teto foi respeitado.
MoreThreadsThanConnectionsStillWorks 12 threads com Pool(2, 3). Todas terminam sem erro e com os ids corretos — a espera limitada funciona. O pool esgotado de verdade levanta ELzNexPool com o diagnóstico acima.
OpenCursorHoldsItsLease Dois Get abertos ao mesmo tempo marcam InUse = 2; anular o primeiro cursor volta para 1, anular o segundo volta para 0.
ℹ
A conexão volta no Commit/Rollback, não no fim do procedimento

O worker do teste abre e fecha uma transação por volta do laço e anula o ILzNexTransaction no finally. Isso importa porque, no FPC 3.2.2, se a devolução dependesse do fim da rotina, um laço de 15 voltas prenderia 15 conexões. Encerrar a transação (Commit ou Rollback) é o que libera.

Servidor: uma facade, uma conexão por requisição

O exemplo em example/api/src/Api.lpr é o molde: a facade é global e aberta uma vez; cada handler usa Db.Table(...) normalmente e cada requisição acaba com uma conexão emprestada e devolvida. 

var
  // uma facade para o processo inteiro -- nunca uma conexao global
  Db: ILzNex;

procedure OpenDatabase;
begin
  Db := Connect(NewConfig
    .Client('mysql')
    .Host(EnvOr('DB_HOST', 'mysql'))
    .Port(StrToIntDef(EnvOr('DB_PORT', '3306'), 3306))
    .Database(EnvOr('DB_NAME', 'lznex'))
    .User(EnvOr('DB_USER', 'root'))
    .Password(EnvOr('DB_PASS', 'secret'))
    .LibraryLocation(EnvOr('DB_LIB', '/usr/lib/x86_64-linux-gnu/libmariadb.so.3'))
    .Charset('utf8mb4')
    .Pool(2, 8));
end;

procedure GetUsers(Req: THorseRequest; Res: THorseResponse);
var
  Rows: ILzNexResult;
begin
  try
    // esta thread pega uma conexao aqui e devolve quando Rows morrer
    Rows := Db.Table('users')
      .Select(['id', 'name', 'email'])
      .OrderBy('id')
      .Limit(20)
      .Get;
    Res.Status(200).ContentType('application/json').Send(Rows.ToJSON);
  except
    on E: Exception do
      Res.Status(500).ContentType('application/json')
         .Send('{"error":' + JsonQuote(E.Message) + '}');
  end;
end;

begin
  OpenDatabase;
  THorse.Get('/users', GetUsers);
  try
    THorse.Listen(9000);
  finally
    Db.Shutdown;
    Db := nil;
  end;
end.

Dimensionar max é um cálculo de banco, não de servidor: ele precisa caber no max_connections do MySQL ou no max_connections do PostgreSQL, somado ao que os outros processos já usam. Threads além de max não falham — esperam.

Shutdown

Shutdown marca o pool como encerrado e fecha as conexões ociosas. As que estão emprestadas naquele instante continuam funcionando até serem devolvidas — e aí são fechadas em vez de voltar para a lista. Depois disso, qualquer Acquire levanta: 

ELzNexPool: Pool already shut down: Acquire after Shutdown

Chame no finally do Listen, como no exemplo. O destrutor da facade também chama Shutdown, mas depender dele significa depender da ordem de finalização das units — explícito é melhor.

CLI

O binário lznex roda migrations e seeds. Por dentro é só um dispatcher sobre ILzNexMigrator e ILzNexSeeder.

O que é o binário

tools/LzNexCli.lpi compila o lznex. Ele não tem lógica de migração nenhuma: lê os argumentos, chama o método correspondente de ILzNexMigrator ou ILzNexSeeder, imprime o resultado e devolve um exit code. Toda a decisão de o que aplicar, em que ordem e sob qual lock está no migrator, que é o mesmo usado por programa.

O dispatcher vive em LzNex.Cli, uma unit separada do .lpr, por duas razões práticas:

  • testável — TLzNexCli.Run(ACommand, AArgs) recebe comando e argumentos como parâmetros, não via ParamStr. Dá para exercitar cada comando e conferir o exit code sem lançar processo;
  • embutível — a sua aplicação pode expor os mesmos comandos (um modo --migrate, um endpoint administrativo) instanciando TLzNexCli.Create(Db). RunFromCommandLine é só o atalho que lê ParamStr e chama Run. 
Cli := TLzNexCli.Create(Db);
try
  ExitCode := Cli.Run('migrate:latest', []);
finally
  Cli.Free;
end;

O lock tem código próprio porque não é a mesma coisa que uma migration quebrada. 3 significa "outro processo está migrando agora" — em deploy com várias instâncias subindo em paralelo, isso é o comportamento correto: uma aplica, as outras recuam. lznex migrate:latest
case $? in
  0) echo "ok" ;;
  3) echo "outro processo esta migrando; seguindo" ;;
  *) echo "falhou"; exit 1 ;;
esac

Como o nome da migration é gerado

O nome é <carimbo>_<slug>. O carimbo tem 14 dígitos no formato YYYYMMDDHHMMSS e é UTC, não hora local. Isso é de propósito: o nome é a chave de ordenação do histórico, e dois desenvolvedores em fusos diferentes criando migrations no mesmo minuto precisam gerar carimbos que ordenem igual em qualquer máquina. Com hora local, a ordem de aplicação dependeria de onde o arquivo nasceu.

A descrição passa por Slugify: caixa baixa, só a-z0-9, qualquer outro byte vira _, sequências de _ colapsam em um e os _ do fim são removidos. O resultado é snake_case ASCII — o que cabe como nome de unit Pascal e de arquivo em qualquer sistema de arquivos. Descrição que esvazia depois do processo vira migration.

Dialetos

Toda diferença entre bancos está num só lugar: o ILzNexClient. O builder não sabe em que banco está.

O que o ILzNexClient concentra

Capacidades

As capacidades não são informativas: o compilador consulta cada uma e, quando o recurso não existe, ou emula ou levanta ELzNexCompile dizendo o que fazer em vez disso. Nunca gera SQL que o banco vai recusar.

SupportsOnConflictWhere não sim Predicado no alvo do upsert (on conflict (…) where …). MySQL resolve conflito com insert ignore into e on duplicate key update, formas que não aceitam condição; o filtro tem de ir para a lógica da aplicação.

A mesma cadeia, dois dialetos

Este é o teste SameQueryCompilesDifferentlyPerDialect: a mesma sequência de chamadas, dois clientes, e três divergências aparecendo de uma vez. 

Q.Table('users').Select(['id', 'name'])
  .Where('active', True)
  .OrderBy('name', odAsc, nlLast)
  .Offset(5)
  .ToSQL
select `id`, `name` from `users` where `active` = ? order by (`name` is null) asc, `name` asc limit 18446744073709551615 offset ?

binds: True | 5

select "id", "name" from "users" where "active" = ? order by "name" asc nulls last offset ?

binds: True | 5

Três diferenças, três mecanismos distintos:

  1. Quoting — acento grave contra aspa dupla. Vem de uma única sobrescrita de QuoteChar; nenhum método do compilador trata disso.
  2. Ordenação de NULL — PostgreSQL diz nulls last; MySQL, que não tem a cláusula, recebe a chave extra (`name` is null) asc antes da coluna. É SupportsNullsOrdering escolhendo entre cláusula nativa e emulação.
  3. Limite artificial — Offset(5) sozinho. MySQL não aceita offset sem limit, então o compilador do dialeto injeta limit 18446744073709551615 (o maior bigint unsigned), que é a forma canônica de dizer "sem limite". PostgreSQL aceita offset sozinho e não ganha nada.

O mesmo vale para DDL: Increments é int unsigned not null auto_increment primary key em MySQL e serial primary key em PostgreSQL. Veja Tipos de coluna.

Implementar um dialeto novo

Um dialeto são duas classes — um TLzNexClientBase e um TLzNexSchemaCompilerBase — mais, se o banco precisar, um TLzNexCompilerBase. Na ordem em que vale atacar:

  1. DialectName e ZeosProtocol. Os dois são abstratos. DialectName é o que aparece nas mensagens de erro; ZeosProtocol é o que entra na URL do Zeos e precisa casar com um driver realmente registrado.
  2. ColumnTypeSQL e ModifierOrder, no compilador de schema. ColumnTypeSQL traduz cada TLzNexColumnType para o tipo nativo; ModifierOrder diz em que sequência os modificadores saem. A ordem importa: MySQL exige mdUnsigned, mdNullable, mdDefault, mdComment, mdCollate, mdAfter; PostgreSQL só reconhece mdNullable, mdDefault e ignora o resto.
  3. As capacidades. Sobrescreva apenas as que diferem dos padrões da base — que são conservadores: sem returning, sem on conflict … where, sem ordenação de NULL, sem distinct on, com savepoint e com DDL transacional.
  4. WrapIdentifier, Alias, Placeholder. Na prática, quase sempre basta sobrescrever o QuoteChar protegido: o WrapIdentifier da base já cita e duplica a aspa interna sozinho. Sobrescreva os métodos inteiros só se a forma do alias ou do placeholder for diferente.
  5. Components e InvalidComponents. Quais seções cada verbo emite, e em que ordem; e quais são proibidas. Veja a seção abaixo.
  6. O resto do compilador de schema. Prefixos do alter table (AddColumnPrefix, ChangeColumnPrefix, DropColumnPrefix — a base usa add column , alter column , drop column ; MySQL encurta para add , modify , drop ), IndexSQL e DropIndexSQL, TableOptionsSQL (vazio na base; MySQL emite engine, default character set, collate, comment) e HasTableSQL/HasColumnSQL se a consulta ao catálogo não for a de information_schema da base.
  7. RegisterClient no initialization. Uma linha por nome aceito. 
initialization
  RegisterClient('postgresql', TLzNexPostgresClient);
  RegisterClient('postgres', TLzNexPostgresClient);
⚠
O registro só acontece se a unit for linkada

RegisterClient roda no initialization, e o FPC não linka unit que ninguém referencia. Se o dialeto não estiver no uses do programa, Connect levanta ELzNexConfig dizendo que o dialeto não está registrado e listando os disponíveis.

Por que Components é virtual

Components devolve, para cada verbo, a lista ordenada de seções que o compilador vai emitir. Para select é cpHints, cpColumns, cpFrom, cpJoin, cpWhere, cpGroup, cpHaving, cpUnion, cpOrder, cpLimit, cpOffset, cpLock; para insert, só cpFrom. O compilador não tem essa ordem escrita em lugar nenhum — ele lê a lista e percorre.

InvalidComponents é o espelho: as seções proibidas naquele verbo. Seção presente na árvore e proibida pelo dialeto levanta ELzNexCompile na compilação, com mensagem dizendo a seção, o verbo e o dialeto.

Os dois são virtuais porque é aqui que mora a classe de diferença mais chata entre bancos: a gramática do verbo. Um banco em que a ordem das seções difere, ou em que um verbo aceita algo que os outros não aceitam, sobrescreve só isso — não precisa duplicar o compilador para mudar uma linha de gramática.

O exemplo real é delete … limit. A base proíbe cpLimit em delete, porque não é SQL padrão. MySQL aceita, então o cliente MySQL sobrescreve InvalidComponents para qmDelete removendo cpLimit da lista de proibidos — e nada mais: 

delete from `users` limit ?

binds: 5

ELzNexCompile: Section "limit" is not valid in delete on dialect postgresql.
Remove the clause or change the verb.

Note que o erro é ELzNexCompile, não ELzNexBuilder: a cadeia de chamadas está coerente, o que falta é suporte no banco. Veja Erros para a distinção.

Erros

Toda falha previsível tem classe própria, e todas descendem de ELzNex. Dá para tratar por categoria sem casar texto de mensagem.

A hierarquia

ELzNex é a base e nunca é levantada diretamente: existe para você capturar "qualquer coisa do LzNex" numa linha. Abaixo dela, cada tipo de falha tem a sua classe — não por burocracia, mas porque a reação é diferente em cada caso. Pool esgotado pede retry; operador inválido pede correção de código; lock de migration pede esperar o outro processo.

A hierarquia é rasa: todas as classes herdam direto de ELzNex, com uma única exceção — ELzNexMigrationLock, que herda de ELzNexMigration, porque disputa de lock é um caso de migração. Todas vivem em LzNex.Exceptions.

ℹ
As mensagens dizem o que fazer

As mensagens são em inglês, como o resto do código, e são escritas para o desenvolvedor: quando existe uma saída, ela está no texto ("set LibraryLocation", "run migrate:unlock", "use LastInsertId or a SELECT afterwards"). Vale ler a mensagem inteira antes de investigar.

As classes

ELzNex = class(Exception) Base de tudo. Não é levantada diretamente. Capture-a como rede final: pega qualquer falha do LzNex e deixa passar o que não é dele.
ELzNexConfig = class(ELzNex) Configuração inválida ou incompleta, antes de qualquer SQL. Exemplos: Connect sem configuração; dialeto não registrado (Dialect "pg" is not registered. Available: mysql, mariadb. — a unit do dialeto ficou fora do uses); Pool min (5) is greater than max (3); JSON malformado; ambiente que não existe no arquivo; valor que deveria ser inteiro e não é.
ELzNexConnection = class(ELzNex) A conexão física. Falha ao abrir (Could not open connection to mysql:3306/lznex: …, com o lembrete de LibraryLocation), uso de conexão já fechada (Connection already closed) e uso de empréstimo já devolvido ao pool (This leased connection was already returned to the pool and cannot be used anymore).

Tratando

Do mais específico para o mais genérico — o FPC avalia os on na ordem escrita, e um on E: ELzNex no topo engoliria todos os outros. 

try
  Db.Table('users').Insert(Vals(['email', Email]));
except
  on E: ELzNexQuery do
  begin
    // o banco recusou: E.SQL tem o texto exato que foi enviado
    Log('SQL recusado: ' + E.SQL);
    Log('motivo: ' + E.Message);
    raise;
  end;
  on E: ELzNexBuilder do
    // bug nosso: a query nem chegou a ser gerada
    Log('query mal montada: ' + E.Message);
  on E: ELzNex do
    // qualquer outra falha do LzNex (config, pool, conexao, transacao...)
    Log('LzNex (' + E.ClassName + '): ' + E.Message);
end;

E.SQL é o que separa "o banco recusou" de "não sei o que foi enviado". A mensagem também contém o SQL, mas na propriedade ele vem limpo, pronto para log estruturado ou para colar num cliente e reproduzir: 

ELzNexQuery: Failed to execute: Duplicate entry 'ana@ex.com' for key 'users.email_unique'
SQL: insert into `users` (`email`) values (?)

Num servidor HTTP, o par útil é ELzNexQuery (vira 4xx ou 5xx, dependendo de ser violação de constraint ou falha de infra) e ELzNexPool (vira 503: o banco não está indisponível, o pool é que não tem conexão livre agora — o cliente pode tentar de novo).

ILzNex

A facade devolvida por Connect: ponto de entrada para query, schema, migrations, transação e pool.

uses LzNex é o único uses obrigatório — a unit reexporta ILzNex, ILzNexQuery, TLzNexValue e os demais tipos do dia a dia, além de Connect, NewConfig e ConnectFromFile (veja Funções). A única unit extra que o programa precisa citar é a do dialeto, para o linker do FPC não descartar o registro — detalhe em Instalação.

ℹ
Ciclo de vida: ninguém escreve try/finally Free

Toda a API é COM com contagem de referência: o objeto morre quando a última referência sai de escopo. Para o contador poder chegar a zero, a referência existe só em um sentido — o filho guarda o pai (a query, o schema e o migrator guardam a facade), e o pai não guarda nenhum filho. Onde o filho precisa chamar o pai para fazer faxina, a referência é de classe, não de interface contada: é assim que a conexão emprestada chama o pool de volta para se devolver, sem que o ciclo se feche.

É por isso que Schema, Migrator e Seeder criam uma instância nova a cada acesso em vez de cachear: guardar a instância no campo da facade fecharia o ciclo facade → filho → facade, e nenhum dos dois seria liberado. Criar é barato (nenhum deles abre conexão no construtor), e o único recurso de verdade — o pool — é da facade e vive enquanto ela vive.

Herda ILzNexQuery inteira: depois das cláusulas On* você continua a query na mesma expressão — Where, OrderBy, outro Join, o terminal. As cláusulas vão sempre para o join corrente, o último aberto por Join, LeftJoin, JoinSub e companhia; um On* sem join antes levanta ELzNexBuilder.

OnColumns compara identificador, OnValue gera bind

OnColumns('posts.user_id', '=', 'users.id') compara duas colunas e não produz nenhum bind; OnValue('tags.active', '=', True) produz on `tags`.`active` = ?. São dois métodos porque um só teria que adivinhar pelo tipo — e True viraria comparação com uma coluna chamada True, erro que não aparece nem na compilação nem no resultado.

Os And* existem só para deixar o encadeamento legível: o conector padrão já é and.

ILzNexOnConflict

OnConflict não devolve ILzNexQuery de propósito: o tipo de retorno só tem estes quatro métodos, então esquecer de completar a cláusula é erro de compilação, não um insert silenciosamente sem o on conflict. Cada um devolve a query de volta, e aí vem o Insert.

Em MergeValues, uma coluna cujo valor é TLzNexValue.Unset não gera bind: ela sai como excluded.coluna (ou values(coluna) no MySQL), isto é, com o valor que veio no Insert. É assim que se mistura, numa chamada só, coluna com valor fixo e coluna copiada do insert.

Resultados

ILzNexResult é o cursor que o banco devolve; ILzNexRow é uma linha já copiada para a memória.

A diferença entre os dois é quem é dono dos dados. O cursor lê a linha corrente direto do driver — avança para frente e nunca volta. A linha é um retrato: copiada no momento em que você pede, ela continua válida depois de o cursor avançar ou fechar.

Cursor forward-only. Next posiciona na próxima linha e devolve False quando acaba — ler coluna antes do primeiro Next levanta ELzNexQuery dizendo exatamente isso.

ToRows e ToJSON partem da posição atual e incluem a linha corrente: se você já chamou Next, aquela linha entra no resultado; se não, eles mesmos avançam. Os dois esvaziam o cursor — um Next depois deles devolve False.

⚠
O cursor segura uma vaga do pool

O ILzNexResult carrega o empréstimo da conexão: enquanto ele vive, a conexão não volta para o pool. Isso é necessário — ler a próxima linha é conversa com o servidor, não leitura de buffer local — mas significa que um cursor guardado em campo de objeto de vida longa tira uma conexão do pool até lá. A devolução acontece no Close ou quando a última referência ao resultado sai de escopo.

Em laço curto, não há o que fazer. Em código que vai segurar os dados, materialize e solte: ToRows (ou First no builder, que já fecha o cursor antes de devolver a linha).

ℹ

Coluna inexistente em Field levanta ELzNexQuery com a lista das colunas que o resultado tem — o erro mais comum é alias esquecido ou errado, e a lista resolve na primeira leitura da mensagem, sem precisar imprimir o SQL. Conexão, pool e transação

As três interfaces que ficam entre o builder e o Zeos: quem executa, quem empresta e quem delimita.

A camada fina sobre o Zeos. Recebe TLzNexFragment — texto mais binds já prontos — e nunca interpola valor. Statements preparados ficam num cache por conexão, e um prepare ou execução que falha remove a entrada do cache antes de propagar o erro.

⚠

Ele roda uma consulta — select last_insert_id(), select lastval() ou select last_insert_rowid(), conforme o DialectName — e o valor só existe na sessão que fez o insert. Lido de outra conexão do pool o resultado não é seu: pegue o id na mesma conexão, ou use InsertGetId, que já cuida disso.

ILzNexPool

Pool fixo com mínimo e máximo. As conexões do mínimo abrem na construção; o resto abre sob demanda até o máximo. Acquire devolve uma conexão emprestada — um invólucro que delega tudo para a conexão real.

function Acquire: ILzNexConnectionPega uma conexão livre, testando com Ping e descartando as mortas; se não houver livre e o máximo não foi atingido, abre uma. Bloqueia até o timeout de aquisição da config e então levanta ELzNexPool.
function Size: IntegerTotal de conexões vivas: as livres mais as em uso.
function InUse: IntegerQuantas estão emprestadas agora.
procedure ShutdownMarca o pool como encerrado e fecha as livres. Acquire depois disso levanta; as emprestadas continuam funcionando e são fechadas, não guardadas, ao voltar.
⚠
A devolução é automática — e é por isso que o pool pode travar

Não existe Release na interface: a conexão volta ao pool no destrutor do invólucro, quando o refcount do ILzNexConnection chega a zero. Na volta, uma transação ainda aberta sofre rollback e uma conexão fechada é descartada em vez de guardada. O efeito prático: guardar a interface num campo de objeto, num singleton ou numa closure mantém a conexão emprestada para sempre e esgota o pool — o erro de exaustão diz exatamente isso. Deixe a variável sair de escopo.

Um ILzNexResult obtido de conexão emprestada também segura o empréstimo: o cursor guarda uma referência à conexão, então o pool só a recupera quando o resultado é liberado. Veja pool para os números medidos e resultados para o ciclo do cursor.

ILzNexTransaction

ILzNexTransaction herda de ILzNex: dentro de uma transação você usa a mesma fachada de sempre — Table, From, Query, Schema, Execute, Fetch — e as queries saem já amarradas nela, sem precisar de Transacting à mão. Os cinco métodos próprios são os de controle.

procedure RollbackDesfaz e encerra, com a mesma checagem de savepoint aberto.
function Savepoint: ILzNexTransactionBloco interno sobre a mesma conexão. Savepoints fecham em ordem LIFO.
function IsCompleted: BooleanVerdadeiro depois de Commit ou Rollback. É o que permite um except fazer rollback só quando ainda há o que desfazer.
function Level: IntegerNível desta transação na conexão, como o driver reportou ao abrir. Cada savepoint sobe um.
⚠
Commit e Rollback soltam a conexão na hora

Os dois zeram a referência interna no mesmo instante, o que devolve o empréstimo ao pool. Depois disso a transação está encerrada: Connection levanta com essa explicação, e Table, Execute ou qualquer outro método de trabalho levantam dizendo em que nível a transação estava. Para continuar, abra outra transação.

Se a transação é liberada sem Commit nem Rollback, o destrutor faz rollback — e, se esse rollback falhar, registra no logger em vez de levantar de dentro do destrutor. Shutdown numa transação levanta de propósito: encerre o bloco e chame Shutdown na fachada. Veja transações para os exemplos.

O que um dialeto precisa responder e as duas interfaces que transformam árvore em texto.

ILzNexClient

O dialeto. Nenhum método aqui toca no banco: é tudo pergunta sobre como escrever SQL. O builder e os compiladores consultam esta interface e nunca testam o nome do banco com if — acrescentar um dialeto é implementar isto, não editar o compilador.

Estrutura da compilação

Em vez de cada verbo ter sua rotina de montagem, o compilador percorre a lista de componentes que o dialeto declara para aquele verbo. Mudar a ordem do limit ou excluir um componente é mexer nestes dois métodos, não no compilador.

function Components(const AMethod: TLzNexQueryMethod): TLzNexComponentsComponentes que o verbo emite, na ordem do texto final. Um select vai de cpHints a cpLock; um insert só tem cpFrom.
function InvalidComponents(const AMethod: TLzNexQueryMethod): TLzNexComponentsComponentes que, se estiverem preenchidos no builder, são erro para aquele verbo. É o que faz um having pendurado num delete levantar ELzNexCompile antes de virar SQL, em vez de ser silenciosamente ignorado.

TLzNexFragment

Um pedaço de SQL com os binds dele dentro. Essa é a decisão central do compilador: texto e parâmetros nunca viajam em variáveis separadas, então não existe o bug clássico de concatenar na ordem errada e deixar os ? desalinhados da lista de valores. Todo Concat move o texto e a lista juntos.

class function Param(const AValue: TLzNexValue): TLzNexFragment; staticTexto ? e exatamente um bind. É o par indissociável.
class function Make(const AText: string; const ABindings: TLzNexBindings): TLzNexFragment; staticTexto e binds já prontos, usado quando o chamador montou os dois lados.

Leitura

function Bindings: TLzNexBindingsOs parâmetros, na ordem dos ? no texto.

Composição

Wrap e Prefix preservam a lista de binds sem mexer em nada: só o texto muda, as posições relativas dos ? continuam as mesmas. 

var A, B, F: TLzNexFragment;

A := TLzNexFragment.Lit('`age` >=').Concat(TLzNexFragment.Param(18));
B := TLzNexFragment.Lit('`active` =').Concat(TLzNexFragment.Param(True));
F := A.Concat(B, ' and ').Prefix('where ');

Writeln(F.Text);                  // where `age` >= ? and `active` = ?
Writeln(F.Bindings.Describe);     // [integer(18), boolean(True)]
Writeln(F.Bindings.Count);        // 2

A convenção de prefixo

Em Pascal, membro de enum não tem escopo próprio: vkNull é um identificador da unit inteira, não TLzNexValueKind.vkNull. Duas enums com um membro de mesmo nome na mesma unit simplesmente não compilam, e o erro aparece em quem usa, não em quem declarou.

Por isso cada enum do LzNex tem um prefixo de duas letras minúsculas, tirado do nome do tipo, e o prefixo é único por enum: sg para StatementGroup, vk para ValueKind, ct para ColumnType. Ler jtLeftOuter já diz de qual tipo ele é.

⚠
md aparece duas vezes

TLzNexColumnModifier e TLzNexMigrationDirection compartilham o prefixo md. Compila porque nenhum membro se repete (mdUnsigned…mdAutoIncrement contra mdUp/mdDown), mas é a única exceção à regra — ao acrescentar membro em qualquer das duas, confira o outro primeiro.

Fachada e configuração

Connect valida a configuração, resolve o dialeto por nome e abre o pool — AConfig = nil levanta ELzNexConfig. ConnectFromFile é só Connect(LoadConfigFile(APath, AEnv)), e é o caminho que o CLI usa. NewConfig e TLzNexConfig.New devolvem a mesma coisa; a primeira existe para quem tem apenas LzNex no uses. TLzNexConsoleLogger.New é o logger de console pronto; com ALogQueries = False ele emite só erro, aviso e info.

ApplyOverrides recebe pares nome/valor e aplica os que reconhece (CLIENT, HOST, PORT, DATABASE, USER, PASSWORD, CHARSET, LIBRARY, POOL_MIN, POOL_MAX, ACQUIRE_TIMEOUT, MIGRATIONS_TABLE, MIGRATIONS_DIR, SEEDS_DIR); qualquer outra chave vira uma prop de conexão em caixa baixa. Valor vazio é ignorado, e não sobrescreve o que já estava lá. EnvOverrideNames devolve as 14 variáveis de ambiente equivalentes, todas com o prefixo LZNEX_, e é o que ApplyEnvOverrides percorre.

LoadConfigJSON já chama ApplyEnvOverrides no fim, e LoadConfigFile delega a ele — então arquivo carregado já veio com as variáveis de ambiente aplicadas. Chamar ApplyEnvOverrides à mão só é necessário sobre uma configuração montada em código.

Registro de dialeto

CreateClient procura o nome num dicionário em caixa baixa e com Trim, e levanta ELzNexConfig listando os nomes disponíveis quando não acha. Os nomes são registrados no initialization da unit do dialeto: LzNex.Client.MySQL registra mysql e mariadb, LzNex.Client.Postgres registra postgresql e postgres.

⚠
O linker do FPC descarta a unit não referenciada

Se a unit do dialeto não aparece no uses de ninguém, o initialization dela nunca roda e CreateClient('mysql') falha com "dialect is not registered" — mesmo que o arquivo esteja no projeto. Inclua LzNex.Client.MySQL (ou .Postgres) explicitamente no programa principal. RegisteredClients devolve <none> quando nenhuma foi linkada, o que é o sintoma mais direto.

Auxiliares de texto

NormalizeOperator baixa a caixa, apara e colapsa espaços repetidos antes de conferir contra LZNEX_OPERATORS; fora da lista, levanta ELzNexBuilder. SplitQualified quebra 'db.schema.col' pelos pontos e apara cada parte. FindAliasSeparator devolve a posição (base 1) do ' as ' — em qualquer caixa — ou 0 se não houver, e é como 'users as u' numa string só é reconhecido.

MigrationIdOf extrai o id de um nome de migração: tudo antes do primeiro _. Sem _, ou com _ na primeira posição, o nome inteiro é o id. MigrationTimestamp produz yyyymmddhhnnss em UTC — não em hora local, para que máquinas em fusos diferentes gerem ids ordenáveis entre si. Slugify baixa a caixa, troca todo caractere fora de a-z0-9 por _ sem repetir underscore, apara os do fim, e devolve 'migration' se nada sobrou. 

Slugify('Create Users Table!');      // create_users_table
Slugify('  ---  ');                  // migration
MigrationFileName('add index', False);  // M20260224183000_add_index.pas
MigrationFileName('add index', True);   // 20260224183000_add_index.up.sql

O nome Pascal é 'M' + timestamp + '_' + slug + '.pas'; o SQL é timestamp + '_' + slug + '.up.sql', e o par .down.sql é criado junto pelo CLI.

Registros globais

Migrações e seeds se registram em variáveis globais pelo initialization da própria unit, o mesmo mecanismo dos dialetos — e com a mesma armadilha de linker. RegisteredMigrationCount/At dão acesso indexado, RegisteredMigrations devolve o array inteiro, e FindMigrationClass casa por MigrationName exato (devolve nil se não achar, não levanta).

ClearMigrations e ClearSeeds existem para teste: zeram o registro global entre casos, para que um não veja o que o outro registrou. Em produção não há motivo para chamá-las.

Resultado e JSON

NewResult embrulha um IZResultSet do Zeos; o parâmetro AOwner é guardado só para manter vivo quem precisa continuar vivo (statement, conexão) enquanto o cursor estiver aberto — é o que evita o resultado sobreviver à conexão que o produziu. LzNexKindOfSQLType mapeia o tipo SQL do Zeos para o TLzNexValueKind correspondente, e é o que o leitor de coluna consulta uma vez por consulta, não por linha.

Os três LzNexJSON* são a serialização usada por ILzNexResult.ToJSON e ILzNexRow.ToJSON: LzNexJSONQuote escapa uma string, LzNexJSONValue converte um valor e LzNexJSONObject monta o objeto a partir de nomes e valores paralelos. No LzNexJSONValue: vkNull e vkUnset viram null, booleano vira true/false, número sai sem quotes, vkBytes sai em base64, data e hora saem como string (yyyy-mm-dd, hh:nn:ss, e datetime em yyyy-mm-ddThh:nn:ss).

Montar SQL sem banco nenhum

NewQuery precisa de um ILzNexClient, e NewSchema aceita nil no lugar do ILzNex. Com isso dá para gerar e inspecionar SQL sem abrir conexão, sem pool e sem servidor rodando — é exatamente assim que as suítes do projeto comparam o SQL por texto exato. 

uses
  LzNex.Types, LzNex.Value, LzNex.Fragment, LzNex.Intf,
  LzNex.Client, LzNex.Query, LzNex.Schema,
  LzNex.Client.MySQL;          // sem esta linha, CreateClient('mysql') falha

var
  Cli: ILzNexClient;
  F: TLzNexFragment;
  T: ILzNexTable;
begin
  Cli := CreateClient('mysql');

  F := NewQuery(Cli)
         .Table('users')
         .Where('id', 1)
         .ToSQL;

  Writeln(F.Text);                     // select * from `users` where `id` = ?
  Writeln(F.Bindings.Count);           // 1
  Writeln(F.Bindings.Describe);        // [integer(1)]

  T := NewSchema(nil, Cli).CreateTable('users');
  T.Increments;
  T.Str('email', 191).NotNull;

  Writeln(T.ToSQL.Statements[0].Text);
  // create table `users` (`id` int unsigned not null auto_increment primary key, `email` varchar(191) not null)
end.

Trocar 'mysql' por 'postgresql' (e incluir LzNex.Client.Postgres) muda o SQL dos dois sem mudar o código do builder: 

select * from `users` where `id` = ?
create table `users` (`id` int unsigned not null auto_increment primary key, `email` varchar(191) not null)
select * from "users" where "id" = ?
create table "users" ("id" serial primary key, "email" varchar(191) not null)
ℹ
Montar sim, executar não

Com NewSchema(nil, Cli), ILzNexTable.ToSQL funciona mas Execute não tem onde rodar. Mesma coisa para a query: ToSQL é puro, enquanto Get, First e Insert precisam de um ILzNex de verdade — use NewBoundQuery ou Db.Table(...) quando a intenção for executar.

Testes e Docker

Tudo roda em container: a suíte sem banco, a suíte com MySQL de verdade, o CLI e a API de exemplo. O docker-compose.yml do repositório é a única configuração necessária.

Os quatro comandos

docker compose run --rm cli migrate:latest

Organização dos testes

Duas camadas: a suíte FPCUnit (um binário, tests/LzNexTests.lpr) e as sondas, programas .lpr independentes que compilam e rodam sozinhos. A sonda existe para isolar um subsistema sem arrastar o resto do framework de teste — quando o linker do FPC reclama, dá para saber de qual unit veio.

Gate de vazamento

scripts/run-tests.sh coleta bin/Probe* e bin/Test*, exporta HEAPTRC=haltonnotreleased (default do script) e roda um por um. Como os binários são compilados com -gh, o heaptrc aborta o processo com exit 203 se sobrar bloco não liberado. Resultado: um único critério — exit != 0 — cobre asserção quebrada e memória não liberada. 

bash scripts/run-tests.sh                    # tudo em bin/
bash scripts/run-tests.sh bin/ProbeCompiler  # um binário só
saída

run-tests: 8 binario(s)

  PASS  ProbeAst                     [gh]
  PASS  ProbeCompiler                [gh]
  LEAK  ProbeSchema                  exit=203
          24 unfreed memory blocks

run-tests: pass=7 fail=0 leak=1
run-tests: FALHOU
  - ProbeSchema (vazamento)

formato do relatório, com um binário vazando — na última execução registrada foram todos PASS

A coluna entre colchetes não é enfeite: o script procura a string Heap dump by heaptrc unit dentro do binário. Não achando, marca SEM -gh e avisa que o gate não vale para aquele binário. É o que impede um verde falso.

⚠
O -gh tem que ir em CustomOptions

A tag <UseHeaptrc Value="True"/> do .lpi é ignorada pelo lazbuild: o binário sai sem heaptrc, o processo nunca retorna 203 e o gate fica inerte — passando sempre, inclusive com vazamento. Por isso o build mode Debug de tests/LzNexTests.lpi traz <CustomOptions Value="-dUseCThreads -gh -gl"/>. Ao criar um novo .lpi de teste, copie essa linha; conferir é só rodar o script e ver se a marca [gh] aparece.

CLI e API no compose

O serviço cli usa a imagem runtime, que é Ubuntu enxuto com libmariadb3 e o binário em /usr/local/bin/lznex. Qualquer subcomando vai depois do nome do serviço: 

docker compose run --rm cli migrate:status
docker compose run --rm cli migrate:latest
docker compose run --rm cli seed:run --only=users
docker compose run --rm cli migrate:rollback --all

A API de exemplo expõe GET /health (ping no banco) e GET /users (20 primeiras linhas). O /health é o teste de fumaça mais barato que existe aqui: se ele responde, a cadeia config → pool → Zeos → libmariadb está inteira. 

docker compose up -d api
curl -s localhost:9000/health
saída
{"status":"ok","dialect":"mysql"}

O que o build faz

O estágio builder instala fpc, lcl-utils, lazarus-src e libmariadb3, baixa o Boss e resolve o ZeosLib. Enquanto a coordenada for o placeholder github.com/CHANGEME/zeoslib, ele clona o espelho direto em modules/<host>_<org>_<repo>, reproduzindo à mão o layout que o Boss produziria; com uma coordenada real, chama scripts/boss-install.sh. Esse script existe porque o Boss imprime ruído de Delphi (rsvars.bat, no Delphi installation) e pode sair com código diferente de zero mesmo tendo instalado: o sucesso é decidido pela linha Installation completed successfully, não pelo exit code.

Depois, lazbuild compila tools/LzNexCli.lpi e tests/LzNexTests.lpi nos dois build modes. O lazarus-src entra mesmo sem nenhum uso de LCL — sem ele o lazbuild para com directory lcl not found.

PostgreSQL nunca rodou contra um banco

O dialeto PostgreSQL está escrito e testado — 66 casos em tests/Test.Postgres.pas, a maioria comparando o texto gerado com o do MySQL para a mesma entrada. Mas a comparação é por texto: o compose só tem MySQL, então conexão, pool e migrator nunca abriram socket com um Postgres. 

select * from `t` limit ? offset ?

conferido contra o banco

select * from "t" limit ? offset ?

conferido contra a string esperada, não contra o banco

Na prática: o SQL que sai é o que se espera, e aspas duplas, returning, distinct on, nulls first/last e on conflict têm asserção. O que ninguém viu funcionar é a camada de baixo — tipo de retorno do driver, mapeamento de TLzNexValue na ida e na volta, comportamento do pool sob carga e o lock da tabela de migrations nesse dialeto.

⚠
Em produção com PostgreSQL, trate como não testado

Teste primeiro o caminho que você vai usar: conectar, uma leitura, uma escrita, uma transação e migrate:latest. O SQL provavelmente está certo; a integração é que não tem prova.

Change gera DDL que o PostgreSQL recusa

O compilador genérico de DDL monta alter column seguido da definição completa da coluna. Funciona no MySQL, onde modify aceita a definição inteira de uma vez. No PostgreSQL não: ele exige alter column ... type ... e set not null como comandos separados. 

T := Db.Schema.Table('users');
T.Int('age').NotNull.Change;
alter table `users` modify `age` int not null

aceito

alter table "users" alter column "age" integer not null

sintaxe inválida — o banco recusa

Ou seja: o texto gerado é o que o teste espera, e o teste espera o texto errado para o PostgreSQL. Enquanto não houver emissão de dois comandos, escreva essa alteração como SQL cru numa migration .sql — veja Migrations.

Não há como informar o where do on conflict

O dialeto declara a capacidade (SupportsOnConflictWhere é True no PostgreSQL e False no MySQL), mas ILzNexOnConflict só tem Ignore, Merge e MergeValues — nenhum lugar para passar o predicado de um índice parcial.

function Ignore: ILzNexQueryon conflict (...) do nothing
function Merge: ILzNexQuerydo update set com todas as colunas do insert
function Merge(const AColumns: array of string): ILzNexQueryidem, só as colunas listadas
function MergeValues(const AValues: TLzNexNamedValues): ILzNexQuerydo update set com valores explícitos

A capacidade existe para o dia em que a interface ganhar esse ponto de entrada. Hoje, um upsert sobre índice parcial sai por Db.Raw.

Enum nativo do PostgreSQL

Enum não cria um tipo (create type ... as enum) no PostgreSQL: sai como text mais um check. 

Db.Schema.CreateTable('o').Enum('status', ['new', 'done']);
create table `o` (`status` enum('new', 'done') null)
create table "o" ("status" text null check ("status" in ('new', 'done')))

A restrição de domínio é equivalente; o tipo não. Um tipo enum de verdade precisaria ser criado antes da tabela, num comando próprio — e o DDL de coluna não tem como emitir um comando que o antecede. Se o tipo nativo importa, crie-o numa migration .sql e declare a coluna com Specific.

Seed em .sql não é executada

Aqui as migrations e as seeds divergem, e a assimetria morde: migration em .sql é lida do disco e aplicada, seed em .sql não. seed:make cria o arquivo — database/seeds/<slug>.sql — mas seed:run percorre apenas as classes passadas a RegisterSeed. O arquivo fica no disco sem nunca rodar, e sem aviso. 

lznex seed:make demo_users
lznex seed:run
saída
created: database/seeds/demo_users.sql
0 seed(s) executed

o arquivo foi criado e ignorado, sem erro

--only também só conhece nome registrado, e o erro lista o que existe: 

error: Seed "demo_users" is not registered. Registered: users, roles.

Até isso mudar, seed útil é classe Pascal registrada. Veja Seeds.

Sem método Jsonb em ILzNexTable

O tipo ctJsonb existe e o compilador de DDL do PostgreSQL emite jsonb para ele. Falta só o método na interface de colunas: ILzNexColumnDef tem Json, não Jsonb. Até aparecer, o caminho é Specific, que entrega o tipo direto ao banco: 

Db.Schema.CreateTable('docs').Specific('payload', 'jsonb');
SQL
create table "docs" ("payload" jsonb null)

Specific não é portável por definição — o texto vai como veio

DDL não é transacional no MySQL

Isso não é escolha da biblioteca: o MySQL dá commit implícito em create, alter e drop. Uma migration que falha no meio deixa atrás o que já executou, e o rollback não desfaz nada disso. O migrator avisa quando o dialeto não tem DDL transacional: 

2026-10-24 12:00:00 [lznex] warn  The mysql dialect commits implicitly on DDL: if
the migration fails midway, the rollback will NOT undo CREATE/ALTER/DROP already
executed. Keep one migration per structural change so the damage stays small.

A defesa é de escrita: uma mudança estrutural por migration, e cada passo reentrante. No PostgreSQL o problema não existe — DdlIsTransactional é True lá, o que, como todo o resto do dialeto, está provado por texto e não contra o banco.

Firebird: arquitetura, nenhum dialeto

Não existe LzNex.Client.Firebird nem LzNex.Schema.Firebird. O que existe é a separação que torna isso possível: dialeto é uma unit que se registra, e tanto o compilador de query quanto o de DDL consultam capacidades em vez de assumir o banco. Escrever o dialeto é trabalho real, não configuração. Veja Dialetos.

A coordenada do Boss é placeholder

boss.json ainda aponta para github.com/CHANGEME/lznex e github.com/CHANGEME/zeoslib, porque o repositório não foi publicado. Duas consequências:

  • boss install com a coordenada placeholder não resolve nada. Os Dockerfiles contornam clonando o espelho do Zeos direto em modules/<host>_<org>_<repo>, no mesmo layout que o Boss produziria.
  • Trocar a coordenada exige trocar também o nome da pasta nos .lpi — o Boss cria modules/github_com_ACME_lznex, com ponto e barra virando _, e esse caminho está escrito nos unit paths do projeto.

O fork do Zeos precisa ter boss.json: o Boss aborta quando uma dependência não traz o manifesto.

Troubleshooting

Sintoma à esquerda, causa e correção à direita. A maioria dos erros em tempo de execução aqui tem uma causa só, e quase sempre é linker do FPC ou conexão presa no pool.

Sintomas e correções

SintomaCausa e correção
Requested database driver was not found ao conectar Falta o uses da unit do dialeto. O FPC não linka unit que ninguém referencia, e é a seção initialization dessa unit que registra o driver — sem referência, o registro nunca acontece. Acrescente LzNex.Client.MySQL (ou LzNex.Client.Postgres) ao uses do programa, não só da unit que monta a query.
Migration em Pascal não aparece no migrate:status Mesma causa, outro disfarce: a classe se registra no initialization da sua unit. Acrescente a unit ao uses de database/Migrations.All.pas — o migrate:make faz isso automaticamente, então o caso aparece em migration criada à mão ou renomeada. Migration em .sql não sofre disso: é lida do disco.
seed:run diz 0 seed(s) executed Nenhuma classe foi passada a RegisterSeed — pela mesma razão de linker, ou porque a seed só existe como arquivo .sql. seed:make cria .sql, mas seed:run roda só classes registradas (veja Limitações). Converta para classe Pascal ou mova o conteúdo para uma migration .sql.
Seed "x" is not registered. Registered: ... O --only compara com SeedName, não com o nome do arquivo nem com o da classe. A própria mensagem lista os nomes válidos: use um deles.
Erro de biblioteca ao conectar, sem SQL nenhum ter rodado O auto-load do Zeos procura libmysqlclient, e no Ubuntu 26.04 só existe libmariadb.so.3. Informe o caminho explicitamente, por LibraryLocation na configuração ou pela variável LZNEX_LIBRARY=/usr/lib/x86_64-linux-gnu/libmariadb.so.3. Confira com ls /usr/lib/x86_64-linux-gnu/libmaria* — o sufixo da versão muda.
lazbuild para com directory lcl not found Falta o pacote lazarus-src. Vale mesmo sem usar LCL: o lazbuild resolve os pacotes base antes de olhar o que o projeto usa. apt-get install lazarus-src (além de fpc e lcl-utils) resolve.
Gate de vazamento sempre verde, até quando há vazamento O binário saiu sem heaptrc. A tag <UseHeaptrc> do .lpi é ignorada pelo lazbuild; o -gh tem que ir em <CustomOptions> do build mode. Sem heaptrc o processo nunca retorna 203 e o gate não existe. scripts/run-tests.sh detecta e imprime SEM -gh no lugar de [gh] — se você vê isso, o resultado daquele binário não diz nada sobre memória.
Migration falhou no meio e o banco ficou meio alterado (MySQL) O MySQL dá commit implícito em DDL: create, alter e drop já estão no disco quando o erro acontece, e o rollback não os desfaz. O migrator avisa antes de começar. Conserte à mão, depois quebre a migration em passos únicos e reentrantes (if not exists e checagem com HasColumn/HasTable).
ELzNexMigrationLock, CLI saindo com exit 3 A tabela de lock está tomada: ou outro processo está migrando agora, ou um processo morreu segurando o lock. O exit 3 é exclusivo desse erro, justamente para o CI distinguir "concorrência" de "migration quebrada" (erro comum é exit 1). Confirme que nada está rodando e então lznex migrate:unlock. Nunca solte o lock no escuro: duas migrations simultâneas na mesma base é como se corrompe o histórico.
ELzNexPool: Pool exhausted: N connections in total (max M), N in use Duas causas. (a) Alguma ILzNexConnection está viva além do escopo da requisição — cursor não consumido até o fim ou transação sem Commit/ Rollback segura o empréstimo até ser liberada. (b) O max é baixo para o número de threads: um servidor que atende N requisições em paralelo precisa de pelo menos N conexões se cada uma mantém cursor aberto. Diagnostique com Db.Pool.InUse e Db.Pool.Size (é o que o tests/DiagPool.lpr imprime a cada passo).
ELzNexTransaction: ... on an already completed transaction Commit e Rollback encerram a transação e devolvem a conexão ao pool; o objeto continua existindo, mas não tem mais conexão. Abra outra transação para o próximo bloco, ou use Savepoint se o que você quer é um bloco interno. A mesma mensagem com Connection on a transaction already completed é a versão que aparece ao pedir a conexão depois do fim.
ELzNexTransaction: ... with a savepoint still open Savepoint aberto dentro da transação que você está fechando. Eles fecham em ordem LIFO: termine o savepoint interno antes de dar Commit/Rollback no externo. A mensagem traz os dois níveis, o da transação e o da conexão.
ELzNexBuilder: ToSQL: there are N open predicate group(s) Faltou WhereClose (ou HavingClose). Como o FPC 3.2.2 não tem função anônima, o parêntese é fechado à mão e ninguém fecha por você. OpenGroupCount diz quantos faltam, e a mensagem separa where de having. Clone recusa pelo mesmo motivo — clonar builder com grupo aberto duplicaria o erro.
ELzNexBuilder: Group close without a matching open O inverso: WhereClose a mais. Levanta na hora da chamada, não no ToSQL, o que ajuda a achar a linha.
RETURNING is not supported by mysql. Use LastInsertId or a SELECT afterwards. Recurso que o dialeto não tem. Em MySQL, troque Returning por InsertGetId, que pega o id na mesma conexão do insert — é o que torna o resultado correto sob concorrência. O builder recusa Returning antes de compilar (Returning: dialect "mysql" does not support RETURNING), então o erro pode vir já na montagem.
DISTINCT ON is not supported by mysql. Use plain Distinct or group by. Mesma família. Use Distinct simples, ou group by com uma função de agregação escolhendo a linha. Consulte Dialetos antes de usar recurso específico de banco — a tabela de capacidades diz o que cada um aceita.
Log não aparece no container (aparece no terminal local) stdout redirecionado para pipe é bufferizado em bloco, não por linha: a saída fica presa no buffer até o processo encher ou terminar. O logger de console do LzNex já chama Flush(Output) depois de cada linha, e o CLI também — se o seu log desaparece, é um ILzNexLogger próprio que faz Writeln sem Flush. Acrescente o Flush(Output) no fim do seu Emit.
Servidor multi-thread travando sem mensagem nenhuma Duas causas clássicas. (a) Falta cthreads como primeira unit do uses do programa (Unix): sem ele o RTL não usa o gerenciador de memória com lock, e a seção crítica do pool não protege nada — o sintoma é travamento ou corrupção, não exceção. (b) Um ILzNexQuery ou ILzNexTransaction está sendo compartilhado entre threads. Eles não são thread-safe por projeto; cada thread monta o seu a partir da fachada, que é o único objeto compartilhável.

A ordem do cthreads

Tem que ser a primeira unit, antes de SysUtils, e protegida pelos defines — é assim em tests/LzNexTests.lpr: 

uses
  {$IFDEF UNIX}{$IFDEF UseCThreads}
  cthreads,
  {$ENDIF}{$ENDIF}
  SysUtils,
  LzNex,
  LzNex.Client.MySQL;

o define vem do compilador: -dUseCThreads em <CustomOptions> do .lpi

Isolando o problema

Quando não está claro se o erro é seu, da biblioteca ou do ambiente, vale subir um nível por vez: 

# 1. o SQL sai como esperado? (não toca no banco)
docker compose run --rm tests

# 2. o banco está de pé e aceita conexão?
docker compose run --rm cli migrate:status

# 3. a cadeia completa funciona sob concorrência?
docker compose run --rm tests-it

# 4. a aplicação de exemplo conecta?
docker compose up -d api && curl -s localhost:9000/health

Falhar no passo 1 é bug de montagem de SQL. Falhar só no 2 é ambiente — biblioteca, host, credencial. Falhar só no 3 é pool, thread ou transação. Veja Testes e Docker para o que cada serviço faz.
