Modificadores

Cada modificador age sobre a última coluna adicionada. Quem decide a ordem de emissão é o dialeto, não a ordem em que você chamou.

Os modificadores

function NotNull: ILzNexTableRemove a nulidade. Sai not null no DDL.
function Nullable: ILzNexTableVolta a permitir nulo (é o estado inicial de toda coluna). Sai null em MySQL e PostgreSQL; em Firebird e SQLite não sai nada, porque nenhum dos dois aceita null como restrição.
function Unsigned: ILzNexTableNumérico sem sinal. Só o MySQL tem o conceito; nos outros três é ignorado em silêncio.
function Default_(const AValue: TLzNexValue): ILzNexTableValor padrão interpolado no DDL (string escapada; booleano vira 1/0 no MySQL e no SQLite, true/false em PostgreSQL e Firebird, que recusam o inteiro numa coluna boolean). O underscore é só para escapar a palavra reservada. TLzNexValue.Unset levanta ELzNexSchema; para nulo explícito use TLzNexValue.Null.
function DefaultRaw(const ASQL: string): ILzNexTablePadrão que é expressão, não valor: entra cru, sem quote (CURRENT_TIMESTAMP, uuid_generate_v4()). SQL vazio levanta.
function Comment(const AText: string): ILzNexTableComentário da coluna. Inline no MySQL, comando separado em PostgreSQL e Firebird, descartado em silêncio no SQLite.
function Collate(const AName: string): ILzNexTableCollation da coluna. collate '<nome>' no MySQL (literal) e collate <nome> em Firebird e SQLite (identificador). O PostgreSQL não tem esse modificador na ordem dele.
function After(const AColumn: string): ILzNexTablePosiciona a coluna depois de outra (after `id`). Extensão do MySQL; nos outros não sai nada.
function Primary: ILzNexTableEntra a coluna atual na primary key. Chamado em duas colunas, monta uma PK composta. Veja Índices e chaves.
function Unique: ILzNexTableÍndice único de uma coluna. Vira comando no Post do plano, não cláusula do create table — exceto no SQLite, onde a restrição tem de nascer dentro do create table.
function Index: ILzNexTableÍndice comum de uma coluna. Também vira comando no Post.
function Change: ILzNexTableMarca a coluna como alteração em vez de adição. Só vale em alter table — veja Alterar tabela.
⚠
Modificador sem coluna levanta

Todos agem sobre a última coluna adicionada. Chamar qualquer um antes de ter coluna levanta ELzNexSchema com a mensagem apontando a forma correta (T.Str('email', 191).NotNull). Não há modificador "solto" acumulando estado no builder.

A ordem é do dialeto, não da chamada

O builder só registra quais modificadores a coluna tem. Na compilação, o dialeto percorre a sua lista fixa (ModifierOrder) e emite cada pedaço na posição onde aquele banco aceita. As duas chamadas abaixo saem byte a byte idênticas: 

T := Sch.CreateTable('mods');
T.Int('n').Default_(7).Unsigned.NotNull.Comment('qtd').Collate('utf8mb4_bin').After('id');

T2 := Sch.CreateTable('mods');
T2.Int('n').After('id').Collate('utf8mb4_bin').Comment('qtd').NotNull.Unsigned.Default_(7);
SQL
create table `mods` (`n` int unsigned not null default 7 comment 'qtd' collate 'utf8mb4_bin' after `id`)

o mesmo texto para as duas, em qualquer ordem de chamada

A ordem de emissão de cada dialeto:

DialetoOrdem
MySQLunsigned → null/not null → default → comment → collate → after
PostgreSQLnull/not null → default
Firebirddefault → not null → collate
SQLitenot null → default → collate

Seguir a ordem de chamada geraria DDL inválido: int not null unsigned ou int default 7 not null são erro de sintaxe no MySQL, que exige unsigned colado no tipo e default depois da nulidade. O Firebird é o espelho disso — lá o default tem de vir antes do not null, e not null default 0 é erro de sintaxe. É por isso que a ordem não é negociável. E por isso a lista do PostgreSQL é curta: o que aquele banco não tem como modificador de coluna simplesmente não entra na lista e nunca é emitido.

Em Firebird e SQLite a nulidade não é sempre explícita, ao contrário dos outros dois: nenhum dos dois aceita null como restrição, então coluna anulável não emite nada e só o not null aparece. E o collate dos dois é identificador, não literal entre aspas: collate UNICODE_CI, collate NOCASE.

⚠
Em Increments nenhum modificador sai

Increments e BigIncrements já carregam o texto completo do tipo (int unsigned not null auto_increment primary key no MySQL, serial primary key no PostgreSQL, integer generated by default as identity primary key no Firebird, integer primary key autoincrement no SQLite). O compilador pula o laço de modificadores nessas colunas, então um .NotNull ou .Default_(1) encadeado ali não levanta e também não aparece no DDL.

Nulidade

Coluna nasce Nullable. Em MySQL e PostgreSQL o DDL escreve qual dos dois é — nunca deixa a decisão para o default do servidor. Em Firebird e SQLite o null não existe como restrição, então a coluna anulável sai sem nada e só o not null aparece: 

T := Sch.CreateTable('nul');
T.Int('a').Nullable;
T.Int('b').NotNull;
create table `nul` (`a` int null, `b` int not null)
create table "nul" ("a" integer, "b" integer not null)

o Firebird escreve igual

Defaults

DDL não tem bind. O valor é interpolado e escapado pelo cliente do dialeto; Bindings.Count do statement é zero. DefaultRaw entra cru, sem quote nenhum, para o caso em que o padrão é expressão do banco. 

T := Sch.CreateTable('def');
T.Str('s', 10).Default_('abc');
T.Bool('b').Default_(TLzNexValue.FromBoolean(True));
T.Timestamp('ts').DefaultRaw('CURRENT_TIMESTAMP');
SQL
create table `def` (`s` varchar(10) null default 'abc', `b` tinyint(1) null default 1, `ts` timestamp null default CURRENT_TIMESTAMP)

binds: nenhum

Como o valor vai para dentro do texto, Default_ é o único ponto do schema builder onde entrada de usuário não passa por bind. Não monte default a partir de string vinda de fora; se o padrão é dinâmico, prefira preencher no insert.

ℹ
DEFAULT em TEXT, BLOB e JSON é omitido no MySQL

O MySQL rejeita default literal nesses tipos com o erro 1101 (BLOB, TEXT, GEOMETRY or JSON column can't have a default value) e derrubaria a migration inteira. O compilador do MySQL então descarta o default em silêncio em text, tinytext, mediumtext, longtext, blob, json e jsonb. Binary(n) com tamanho vira varbinary(n) e aceita default; sem tamanho vira blob e não aceita. 

T := Sch.CreateTable('txt');
T.Text('t').Default_('x');
SQL
create table `txt` (`t` text null)

o default não aparece, e nada é levantado

Diferenças por dialeto

Unsigned é a diferença que mais morde: só o MySQL tem o conceito, e levantar nos outros travaria toda migration escrita para MySQL. A escolha foi ignorar em silêncio para a migration continuar rodando nos quatro bancos. O mesmo vale para After, que é extensão do MySQL. 

T.Int('n').Unsigned.NotNull;
create table `u` (`n` int unsigned not null)
create table "u" ("n" integer not null)

se o domínio exige não-negativo, use Specific com um check

Comment existe em três dos quatro, com sintaxe diferente: o MySQL aceita inline na definição da coluna; PostgreSQL e Firebird só como comando comment on column, que vai para o Post do plano. O SQLite não tem comment on, e ali o comentário é descartado em silêncio — é documentação, e derrubar a migration por causa dele seria pior que perdê-lo. 

T.Str('email', 191).Comment('login of the user');
create table `users` (`email` varchar(191) null comment 'login of the user')

Post: 0 comandos

create table "users" ("email" varchar(191) null)
comment on column "users"."email" is 'login of the user'

Post: 1 comando

create table "users" ("email" varchar(191))
comment on column "users"."email" is 'login of the user'

Post: 1 comando

create table "users" ("email" varchar(191))

Post: 0 comandos — o comentário não sai em lugar nenhum
