Índices e chaves

Índice e constraint saem como comando próprio no Post do plano. A exceção é a primary key, que vai inline no create table.

Por que fora do create table

O create table é um único statement com as colunas. Todo índice, unique e chave estrangeira vira um comando separado na lista Post do plano DDL — um comando por índice. Isso mantém a mesma montagem funcionando em create e em alter, e faz um índice que falha não levar o create table junto. 

T := Sch.CreateTable('users');
T.Increments('id');
T.Str('email', 191).NotNull.Unique;
T.Str('name').Index;
P := T.ToSQL;
SQL
create table `users` (`id` int unsigned not null auto_increment primary key, `email` varchar(191) not null, `name` varchar(255) null)
alter table `users` add unique `users_email_unique`(`email`)
alter table `users` add index `users_name_index`(`name`)

Statements: 1 · Post: 2 · P.Count = 3

O nome automático

Sem ConstraintName, o nome é <tabela>_<colunas>_<tipo>: a tabela, cada coluna na ordem, e o sufixo do tipo (index, unique, primary, foreign). Tudo em caixa baixa, com . e - trocados por _ para o nome continuar sendo um identificador simples. Quem monta é IndexName no compilador do dialeto, e dá para chamar direto: 

Cmp := Db.Client.NewSchemaCompiler;
Cmp.IndexName('t', StringsToValues(['c']), ixUnique)         // t_c_unique
Cmp.IndexName('My.Tbl', StringsToValues(['A-B']), ixIndex)   // my_tbl_a_b_index

Unique e index

As formas de uma coluna (Unique, Index sem argumento) agem sobre a última coluna adicionada. As formas com lista montam índice composto, e o nome une as colunas na ordem em que você passou. 

T := Sch.CreateTable('comp');
T.Int('a').NotNull;
T.Int('b').NotNull;
T.Unique(['a', 'b']);
T.Index(['b', 'a']);
SQL
alter table `comp` add unique `comp_a_b_unique`(`a`, `b`)
alter table `comp` add index `comp_b_a_index`(`b`, `a`)

a ordem das colunas muda o nome e muda o índice

A sintaxe do comando difere por banco:

alter table `users` add unique `users_email_unique`(`email`)
alter table `users` add index `users_name_index`(`name`)
alter table "users" add constraint "users_email_unique" unique ("email")
create index "users_name_index" on "users" ("name")

unique é constraint; index comum é create index

Primary key

A primary key é a única que vai inline no create table, como cláusula primary key (…) depois das colunas. Não gera comando extra: índice de PK criado depois do fato custaria uma reescrita da tabela. 

T := Sch.CreateTable('pk1');
T.Int('a').NotNull;
T.Int('b').NotNull;
T.Primary(['a', 'b']);
SQL
create table `pk1` (`a` int not null, `b` int not null, primary key (`a`, `b`))

Post: 0 comandos

Primary sem argumento também compõe: a segunda chamada acrescenta a coluna à PK que já existe em vez de criar uma segunda. 

T := Sch.CreateTable('pk2');
T.Int('a').NotNull.Primary;
T.Int('b').NotNull.Primary;
SQL
create table `pk2` (`a` int not null, `b` int not null, primary key (`a`, `b`))

Increments e BigIncrements já embutem primary key no próprio tipo, então não precisam (nem devem) de Primary em cima.

Chave estrangeira

function References(const AColumn: string): ILzNexTableAbre a FK na última coluna, apontando para AColumn. Aceita 'tabela.coluna' e nesse caso já resolve a tabela.
function InTable(const ATable: string): ILzNexTableTabela referenciada. Dispensável se References veio qualificado.
function OnDelete(const AAction: string): ILzNexTableAção no delete. Normalizada: caixa baixa e _ vira espaço ('SET_NULL' → set null).
function OnUpdate(const AAction: string): ILzNexTableO mesmo, no update.
function ConstraintName(const AName: string): ILzNexTableSobrepõe o nome automático do último índice/FK declarado.
 
T := Sch.CreateTable('posts');
T.Increments('id');
T.Int('user_id').Unsigned.NotNull
  .References('id').InTable('users').OnDelete('cascade').OnUpdate('RESTRICT');
SQL
alter table `posts` add constraint `posts_user_id_foreign` foreign key (`user_id`) references `users` (`id`) on delete cascade on update restrict

a coluna sai normal no create: `user_id` int unsigned not null

A forma curta, com a tabela junto da coluna, dispensa InTable:

T := Sch.CreateTable('posts');
T.Int('user_id').NotNull.References('users.id');
SQL
alter table `posts` add constraint `posts_user_id_foreign` foreign key (`user_id`) references `users` (`id`)
T.Int('user_id').NotNull.References('users.id').ConstraintName('fk_posts_user');
SQL
alter table `posts` add constraint `fk_posts_user` foreign key (`user_id`) references `users` (`id`)

Ações aceitas

A lista é fechada: cascade, restrict, set null, no action, set default. Qualquer outra coisa levanta ELzNexSchema na hora da chamada. O motivo é direto: a ação é interpolada no DDL, não bindada, então tem que vir de uma lista conhecida. 

T.Int('a').References('id').InTable('y').OnDelete('drop table');
// ELzNexSchema: acao referencial fora da lista

O que levanta ELzNexSchema

SituaçãoQuando
InTable sem References antesna chamada — não há FK para completar
References sem coluna anteriorna chamada — e sem deixar FK órfã no builder
References sem InTable nem tabela qualificadana compilação (ToSQL), e o plano parcial é descartado inteiro
ação de FK fora da lista aceitana chamada de OnDelete/OnUpdate
índice sem colunas (Unique([]), Index([]), Primary([]))na chamada
Unique/Index/Primary sem coluna anteriorna chamada
ConstraintName sem índice ou FK declaradona chamada
create table sem nenhuma colunana compilação

Remover índices e chaves

Os quatro só valem em alter table (Db.Schema.Table(…)); em create levantam. Eles identificam o alvo pelo nome automático derivado das colunas, então passe as mesmas colunas usadas na criação — ou o nome que você deu com ConstraintName. 

T := Sch.Table('users');
T.DropPrimary;
T.DropForeign(['user_id']);
T.DropUnique(['email']);
T.DropIndex(['age']);
SQL
alter table `users` drop primary key
alter table `users` drop foreign key `users_user_id_foreign`
alter table `users` drop index `users_email_unique`
alter table `users` drop index `users_age_index`

Statements: 0 — alter só de índice não gera comando de coluna

ℹ
No MySQL, unique também é índice

O MySQL implementa unique como índice único, e drop index remove os dois. DropUnique e DropIndex portanto geram o mesmo comando — a única diferença é o sufixo do nome procurado (_unique contra _index). Primary e foreign key têm sintaxe própria (drop primary key, drop foreign key).

No PostgreSQL tudo que não é índice comum é constraint:

alter table `users` drop primary key
alter table `users` drop foreign key `users_user_id_foreign`
alter table `users` drop index `users_email_unique`
alter table `users` drop index `users_age_index`
alter table "users" drop constraint "users_primary"
alter table "users" drop constraint "users_user_id_foreign"
alter table "users" drop constraint "users_email_unique"
drop index "users_age_index"
