Alterar tabela

Db.Schema.Table(nome) entra em modo alter. O builder agrega as operações do mesmo tipo num comando só, em vez de emitir um alter table por coluna.

O que o builder agrega

Na compilação, as colunas do alter são separadas em três baldes e cada balde vira um statement. Rename de coluna sai em comando próprio, e índice vai para o Post como em create:

BaldeVira
todas as adições1 statement com os add separados por vírgula
todas as colunas marcadas com Change1 statement com os modify/alter column
todos os DropColumn1 statement com os drop
cada RenameColumn1 statement por rename
índices, uniques, FKs e drops delescomandos no Post

Agregar importa porque cada alter table no MySQL pode reescrever a tabela inteira: três comandos custam três reescritas, um comando custa uma. 

T := Sch.Table('users');
T.Str('nick', 50);
T.Int('age').NotNull;
T.Text('bio').Change;
T.DropColumn('old1');
T.DropColumn('old2');
T.RenameColumn('a', 'b');
T.Index(['nick']);
T.DropIndex(['age']);
P := T.ToSQL;
SQL
alter table `users` add `nick` varchar(50) null, add `age` int not null
alter table `users` modify `bio` text null
alter table `users` drop `old1`, drop `old2`
alter table `users` rename column `a` to `b`
alter table `users` add index `users_nick_index`(`nick`)
alter table `users` drop index `users_age_index`

Statements: 4 · Post: 2 — os dois últimos são o Post

A ordem dos statements é sempre essa: adições, alterações, drops, renames. Não é a ordem das chamadas — declarar o DropColumn antes do Str dá o mesmo plano.

Prefixos por dialeto

A diferença entre os dois bancos no alter é só o prefixo de cada operação. O MySQL usa a forma curta; o PostgreSQL exige a palavra column: 

T := Sch.Table('users');
T.Str('nick', 50);
T.Int('age').NotNull;

T := Sch.Table('users');
T.Int('age').NotNull.Change;

T := Sch.Table('users');
T.DropColumn('legacy');
alter table `users` add `nick` varchar(50) null, add `age` int not null
alter table `users` modify `age` int not null
alter table `users` drop `legacy`
alter table "users" add column "nick" varchar(50) null, add column "age" integer not null
alter table "users" alter column "age" integer not null
alter table "users" drop column "legacy"

RenameColumn usa a mesma forma nos dois: alter table … rename column … to ….

⚠
DropColumn e RenameColumn zeram a última coluna

Os dois não deixam coluna "atual" no builder — não haveria sentido em aplicar NotNull a uma coluna que está sendo removida ou renomeada. Um modificador encadeado depois deles levanta ELzNexSchema, a mesma exceção de modificador sem coluna anterior. É erro em tempo de montagem, não DDL torto chegando no banco. 

T := Sch.Table('x');
T.Int('a');
T.DropColumn('a');
T.NotNull;            // ELzNexSchema: nao ha coluna para aplicar

T := Sch.Table('x');
T.RenameColumn('a', 'b');
T.Nullable;           // ELzNexSchema: a mesma coisa

Um alter sem operação nenhuma também levanta na compilação: ToSQL de um Table(…) vazio é erro, não plano vazio.

Opções de tabela

Engine, Charset, TableCollate e TableComment valem só em create table — em alter levantam ELzNexSchema. No MySQL elas formam a cláusula depois do fecha-parênteses: 

T := Sch.CreateTable('opt');
T.Increments;
T.Engine('InnoDB').Charset('utf8mb4').TableCollate('utf8mb4_bin').TableComment('oi');
SQL
create table `opt` (`id` int unsigned not null auto_increment primary key) engine = InnoDB default character set utf8mb4 collate utf8mb4_bin comment = 'oi'
ℹ
No PostgreSQL a cláusula sai vazia

Nada de engine, character set ou collate de tabela existe lá, então a cláusula de opções é string vazia e as três chamadas são ignoradas em silêncio — a mesma escolha de Unsigned, para a migration rodar nos dois bancos. TableComment é a exceção: volta como comment on table "opt" is 'oi' no Post.

ILzNexSchema

function WithSchema(const AName: string): ILzNexSchemaQualifica as tabelas criadas daqui para frente (create table `outro`.`q` (…)) e o filtro de HasTable/HasColumn. Vale só nesta instância.
function CreateTable(const AName: string): ILzNexTableAbre um builder em modo create.
function Table(const AName: string): ILzNexTableAbre um builder em modo alter.
function HasTable(const AName: string): BooleanConsulta information_schema.tables. Executa na hora.
function HasColumn(const ATable, AColumn: string): BooleanConsulta information_schema.columns. Executa na hora.
procedure DropTable(const AName: string)drop table `users`. Sem if exists: se a tabela não existir, o erro vem do banco.
procedure DropTableIfExists(const AName: string)drop table if exists `users`.
procedure RenameTable(const AFrom, ATo: string)MySQL: rename table `a` to `b`. PostgreSQL: alter table "a" rename to "b".
procedure Truncate(const AName: string)MySQL: truncate `users`. PostgreSQL: truncate "users" restart identity — sem isso a sequência continuaria de onde parou, ao contrário do MySQL.
procedure Raw(const ASQL: string; const AArgs: array of const)Escapatória para DDL que o builder não cobre. Mesma gramática de SQL cru.

As quatro procedure de tabela e as duas consultas de existência executam na chamada — não devolvem plano. Todas exigem uma conexão: num builder criado em modo só-SQL (NewSchema(nil, Client)) elas levantam ELzNexSchema, enquanto ToSQL continua funcionando.

⚠
Db.Schema devolve uma instância nova

Cada Db.Schema cria um ILzNexSchema do zero, então Db.Schema.WithSchema('outro') seguido de Db.Schema.CreateTable(…) cria a tabela sem o schema. Guarde a instância numa variável quando usar WithSchema.

Consultas de existência

Sem WithSchema, o filtro do schema vem do banco corrente — e é aí que os dois dialetos divergem. O nome da tabela e da coluna vão como bind; só a função do schema é texto. 

Sch.HasTable('users');
Sch.HasColumn('users', 'email');
select count(*) from information_schema.tables where table_name = ? and table_schema = database()
select count(*) from information_schema.columns where table_name = ? and column_name = ? and table_schema = database()

binds: users · users | email

select count(*) from information_schema.tables where table_name = ? and table_schema = current_schema()
select count(*) from information_schema.columns where table_name = ? and column_name = ? and table_schema = current_schema()

binds: users · users | email

Com schema explícito, a função dá lugar a mais um bind nos dois bancos:

Sch := Db.Schema.WithSchema('public');
Sch.HasTable('users');
SQL
select count(*) from information_schema.tables where table_name = ? and table_schema = ?

binds: users | public

O uso típico é tornar a migration idempotente:

Sch := Db.Schema;

if not Sch.HasTable('users') then
begin
  T := Sch.CreateTable('users');
  T.Increments('id');
  T.Str('email', 191).NotNull.Unique;
  T.Timestamps;
  T.Execute;
end;

if not Sch.HasColumn('users', 'nick') then
  Sch.Table('users').Str('nick', 50).Execute;
SQL
create table `users` (`id` int unsigned not null auto_increment primary key, `email` varchar(191) not null, `created_at` timestamp not null default CURRENT_TIMESTAMP, `updated_at` timestamp not null default CURRENT_TIMESTAMP)
alter table `users` add unique `users_email_unique`(`email`)
alter table `users` add `nick` varchar(50) null

o primeiro Execute roda 2 comandos (statement + post), o segundo roda 1 — é isso que o retorno conta

⚠
DDL faz commit implícito no MySQL

No MySQL cada comando de DDL encerra a transação aberta. Um plano com vários comandos (create + índices, ou os quatro statements de um alter) não é atômico lá: se o terceiro falhar, os dois primeiros já estão aplicados. Escreva o down da migration supondo estado parcial. No PostgreSQL o DDL é transacional e o plano inteiro cabe num rollback.
