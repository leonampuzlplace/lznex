Alterar tabela

Db.Schema.Table(nome) entra em modo alter. O builder agrega as operações do mesmo tipo num comando só, em vez de emitir um alter table por coluna.

O que o builder agrega

Na compilação, as colunas do alter são separadas em três baldes e cada balde vira um statement. Rename de coluna sai em comando próprio, e índice vai para o Post como em create:

BaldeVira
todas as adições1 statement com os add separados por vírgula
todas as colunas marcadas com Change1 statement com os modify/alter column
todos os DropColumn1 statement com os drop
cada RenameColumn1 statement por rename
índices, uniques, FKs e drops delescomandos no Post

Agregar importa porque cada alter table no MySQL pode reescrever a tabela inteira: três comandos custam três reescritas, um comando custa uma. 

T := Sch.Table('users');
T.Str('nick', 50);
T.Int('age').NotNull;
T.Text('bio').Change;
T.DropColumn('old1');
T.DropColumn('old2');
T.RenameColumn('a', 'b');
T.Index(['nick']);
T.DropIndex(['age']);
P := T.ToSQL;
SQL
alter table `users` add `nick` varchar(50) null, add `age` int not null
alter table `users` modify `bio` text null
alter table `users` drop `old1`, drop `old2`
alter table `users` rename column `a` to `b`
alter table `users` add index `users_nick_index`(`nick`)
alter table `users` drop index `users_age_index`

Statements: 4 · Post: 2 — os dois últimos são o Post

A ordem dos statements é sempre essa: adições, alterações, drops, renames. Não é a ordem das chamadas — declarar o DropColumn antes do Str dá o mesmo plano.

⚠
No SQLite não há agregação: uma ação por statement

O ALTER TABLE do SQLite aceita uma ação por comando. Duas colunas novas e um DropColumn saem como três statements, não um por balde. O plano continua correto; o que muda é a contagem — e, no MySQL, o custo (lá cada alter table pode reescrever a tabela inteira, então agregar economiza reescritas).

Prefixos por dialeto

Em três dos quatro bancos, a diferença no alter é só o prefixo de cada operação. O MySQL usa a forma curta, o PostgreSQL exige a palavra column, e o Firebird é ainda mais curto — add e drop sem column: 

T := Sch.Table('users');
T.Str('nick', 50);
T.Int('age').NotNull;

T := Sch.Table('users');
T.Int('age').NotNull.Change;

T := Sch.Table('users');
T.DropColumn('legacy');
alter table `users` add `nick` varchar(50) null, add `age` int not null
alter table `users` modify `age` int not null
alter table `users` drop `legacy`
alter table "users" add column "nick" varchar(50) null, add column "age" integer not null
alter table "users" alter column "age" type integer, alter column "age" set not null
alter table "users" drop column "legacy"
alter table "users" add "nick" varchar(50), add "age" integer not null
alter table "users" alter column "age" type integer, alter column "age" set not null
alter table "users" drop "legacy"
alter table "users" add column "nick" varchar(50)
-- o segundo add levanta: not null sem default, veja abaixo.
-- com .Default_(0) sairia:
alter table "users" add column "age" integer not null default 0

-- Change levanta: nao existe ALTER COLUMN

alter table "users" drop column "legacy"

uma ação por statement, e nunca duas no mesmo alter table

RenameColumn é alter table … rename column … to … em MySQL, PostgreSQL e SQLite. O Firebird escreve alter table "users" alter column "nick" to "nickname".

O Change não tem a mesma forma em todos

No MySQL, modify aceita a definição inteira da coluna de uma vez. PostgreSQL e Firebird não: cada aspecto é uma ação própria — tipo, nulidade e default — e o LzNex emite uma para cada, todas dentro do mesmo alter table. No SQLite Change levanta: não existe ALTER COLUMN ali. 

T := Db.Schema.Table('users');
T.Int('hits').Nullable.Default_(0).Change;
SQL
-- MySQL
alter table `users` modify `hits` int null default 0

-- PostgreSQL
alter table "users" alter column "hits" type integer,
  alter column "hits" drop not null,
  alter column "hits" set default 0

-- Firebird: a mesma decomposicao
alter table "users" alter column "hits" type integer,
  alter column "hits" drop not null,
  alter column "hits" set default 0

-- SQLite: ELzNexSchema mencionando 'no ALTER COLUMN'
⚠
Duas restrições do SQLite que viram erro de montagem

add column … not null sem default levanta: as linhas que já existem não teriam valor, e é o próprio SQLite que recusa. E Primary ou chave estrangeira em tabela existente levanta citando a falta de ADD CONSTRAINT — ou a restrição nasce no create table, ou não nasce. Unique escapa, virando create unique index. A saída para o resto é recriar a tabela na migration: criar a nova, copiar, apagar, renomear.

⚠
DropColumn e RenameColumn zeram a última coluna

Os dois não deixam coluna "atual" no builder — não haveria sentido em aplicar NotNull a uma coluna que está sendo removida ou renomeada. Um modificador encadeado depois deles levanta ELzNexSchema, a mesma exceção de modificador sem coluna anterior. É erro em tempo de montagem, não DDL torto chegando no banco. 

T := Sch.Table('x');
T.Int('a');
T.DropColumn('a');
T.NotNull;            // ELzNexSchema: nao ha coluna para aplicar

T := Sch.Table('x');
T.RenameColumn('a', 'b');
T.Nullable;           // ELzNexSchema: a mesma coisa

Um alter sem operação nenhuma também levanta na compilação: ToSQL de um Table(…) vazio é erro, não plano vazio.

Opções de tabela

Engine, Charset, TableCollate e TableComment valem só em create table — em alter levantam ELzNexSchema. No MySQL elas formam a cláusula depois do fecha-parênteses: 

T := Sch.CreateTable('opt');
T.Increments;
T.Engine('InnoDB').Charset('utf8mb4').TableCollate('utf8mb4_bin').TableComment('oi');
SQL
create table `opt` (`id` int unsigned not null auto_increment primary key) engine = InnoDB default character set utf8mb4 collate utf8mb4_bin comment = 'oi'
ℹ
Fora do MySQL a cláusula sai vazia

Nada de engine, character set ou collate de tabela existe em PostgreSQL, Firebird ou SQLite, então a cláusula de opções é string vazia e as três chamadas são ignoradas em silêncio — a mesma escolha de Unsigned, para a migration rodar nos quatro bancos. TableComment é a exceção: volta como comment on table "opt" is 'oi' no Post em PostgreSQL e Firebird, e desaparece no SQLite, que não tem comment on.

ILzNexSchema

function WithSchema(const AName: string): ILzNexSchemaQualifica as tabelas criadas daqui para frente (create table `outro`.`q` (…)) e o filtro de HasTable/HasColumn. Vale só nesta instância.
function CreateTable(const AName: string): ILzNexTableAbre um builder em modo create.
function Table(const AName: string): ILzNexTableAbre um builder em modo alter.
function HasTable(const AName: string): BooleanConsulta information_schema.tables — ou rdb$relations no Firebird e sqlite_master no SQLite, que não têm information_schema. Executa na hora.
function HasColumn(const ATable, AColumn: string): BooleanConsulta information_schema.columns — rdb$relation_fields no Firebird, pragma_table_info(?) no SQLite. Executa na hora.
procedure DropTable(const AName: string)drop table `users`. Sem if exists: se a tabela não existir, o erro vem do banco.
procedure DropTableIfExists(const AName: string)drop table if exists `users`. O Firebird 3/5 não tem essa forma: ali sai um execute block que consulta rdb$relations antes de executar o drop.
procedure RenameTable(const AFrom, ATo: string)MySQL: rename table `a` to `b`. PostgreSQL e SQLite: alter table "a" rename to "b". Firebird: levanta ELzNexSchema — não existe no 3 nem no 5, a tabela tem de ser recriada, copiada e apagada.
procedure Truncate(const AName: string)MySQL: truncate `users`. PostgreSQL: truncate "users" restart identity — sem isso a sequência continuaria de onde parou, ao contrário do MySQL. Firebird e SQLite não têm truncate: sai delete from "users".
procedure Raw(const ASQL: string; const AArgs: array of const)Escapatória para DDL que o builder não cobre. Mesma gramática de SQL cru.

As quatro procedure de tabela e as duas consultas de existência executam na chamada — não devolvem plano. Todas exigem uma conexão: num builder criado em modo só-SQL (NewSchema(nil, Client)) elas levantam ELzNexSchema, enquanto ToSQL continua funcionando.

⚠
Db.Schema devolve uma instância nova

Cada Db.Schema cria um ILzNexSchema do zero, então Db.Schema.WithSchema('outro') seguido de Db.Schema.CreateTable(…) cria a tabela sem o schema. Guarde a instância numa variável quando usar WithSchema.

Consultas de existência

Sem WithSchema, o filtro do schema vem do banco corrente — e é aí que os dialetos divergem. O nome da tabela e da coluna vão como bind; só a função do schema é texto. 

Sch.HasTable('users');
Sch.HasColumn('users', 'email');
select count(*) from information_schema.tables where table_name = ? and table_schema = database()
select count(*) from information_schema.columns where table_name = ? and column_name = ? and table_schema = database()

binds: users · users | email

select count(*) from information_schema.tables where table_name = ? and table_schema = current_schema()
select count(*) from information_schema.columns where table_name = ? and column_name = ? and table_schema = current_schema()

binds: users · users | email

select count(*) from rdb$relations where trim(rdb$relation_name) = ?
select count(*) from rdb$relation_fields where trim(rdb$relation_name) = ? and trim(rdb$field_name) = ?

não há information_schema; o trim está ali porque o Firebird guarda o nome preenchido com espaços

select count(*) from sqlite_master where type in ('table', 'view') and name = ?
select count(*) from pragma_table_info(?) where name = ?

binds: users · users | email

Com schema explícito, a função dá lugar a mais um bind em MySQL e PostgreSQL. Firebird e SQLite não têm schema nesse sentido, e a consulta deles não muda. 

Sch := Db.Schema.WithSchema('public');
Sch.HasTable('users');
SQL
select count(*) from information_schema.tables where table_name = ? and table_schema = ?

binds: users | public

O uso típico é tornar a migration idempotente:

Sch := Db.Schema;

if not Sch.HasTable('users') then
begin
  T := Sch.CreateTable('users');
  T.Increments('id');
  T.Str('email', 191).NotNull.Unique;
  T.Timestamps;
  T.Execute;
end;

if not Sch.HasColumn('users', 'nick') then
  Sch.Table('users').Str('nick', 50).Execute;
SQL
create table `users` (`id` int unsigned not null auto_increment primary key, `email` varchar(191) not null, `created_at` timestamp not null default CURRENT_TIMESTAMP, `updated_at` timestamp not null default CURRENT_TIMESTAMP)
alter table `users` add unique `users_email_unique`(`email`)
alter table `users` add `nick` varchar(50) null

o primeiro Execute roda 2 comandos (statement + post), o segundo roda 1 — é isso que o retorno conta

⚠
DDL faz commit implícito no MySQL

No MySQL cada comando de DDL encerra a transação aberta. Um plano com vários comandos (create + índices, ou os quatro statements de um alter) não é atômico lá: se o terceiro falhar, os dois primeiros já estão aplicados. Escreva o down da migration supondo estado parcial. O MySQL é o único dos quatro assim: em PostgreSQL, Firebird e SQLite o DDL é transacional e o plano inteiro cabe num rollback.
