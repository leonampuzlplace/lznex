Resultados

Um cursor forward-only, uma linha materializada e um ToJSON. Nenhum TDataset no caminho.

O cursor

ILzNexResult é uma casca fina sobre o IZResultSet do ZeosLib: avança para frente, uma linha por vez, sem buffer de todas as linhas em memória e sem componente visual. Na abertura ele lê a metadata uma única vez — nome e tipo de cada coluna — e usa isso em toda leitura seguinte.

O cursor fecha sozinho quando a interface é liberada: o destrutor chama Close. Variável local de escopo curto já é suficiente; Close explícito serve para encerrar antes do fim do escopo. Chamar duas vezes não faz mal.

Close também devolve a conexão ao pool na hora, sem esperar a variável sair de escopo. Importa quando o pool é pequeno e o mesmo bloco abre vários cursores: 

A := Db.Table('users').Get;
// ... le
A.Close;                       // a conexao volta ao pool aqui

B := Db.Table('posts').Get;    // reusa a mesma vaga
B.Close;

Total := Db.Table('users').Count;   // ainda ha vaga, mesmo com A e B no escopo
Método de ILzNexResultO que faz
function Next: BooleanAvança uma linha. False no fim — e também se o cursor já estiver fechado, sem levantar.
function Field(const AName: string): TLzNexValueLê a coluna por nome na linha corrente.
function FieldAt(const AIndex: Integer): TLzNexValueO mesmo, por posição (base zero).
function FieldCount: IntegerQuantas colunas o resultado tem. Vale antes do primeiro Next.
function FieldName(const AIndex: Integer): stringNome da coluna na posição. Também vale antes do primeiro Next.
function CurrentRow: ILzNexRowMaterializa a linha corrente num objeto independente do cursor.
function ToRows: TLzNexRowArrayMaterializa todas as linhas restantes e esgota o cursor.
function ToJSON: stringArray JSON com todas as linhas restantes. Também esgota o cursor.
procedure CloseFecha o resultset do driver. Idempotente.
 
Rows := Db.Table('users').Select(['id', 'name']).Get;
while Rows.Next do
  Writeln(Rows.Field('id').AsInt64, ' ', Rows.Field('name').AsString);

Ler coluna antes do primeiro Next, ou depois do último, levanta ELzNexQuery — Cursor is not on a row. Call Next before reading a column. Depois de Close, a mensagem é Cursor already closed. O caso em que Next devolveu False e o código segue lendo é o mais comum dos dois.

O kind de cada coluna

O tipo vem da metadata do driver e é fixado na abertura, não deduzido valor por valor. A conversão é esta:

Tipo SQLKind
booleanovkBoolean
qualquer inteirovkInt64
float, doublevkFloat
currency, decimal/numericvkCurrency
date · time · timestampvkDate · vkTime · vkDateTime
binário e blobvkBytes
texto, GUID e o que não casarvkString

NULL no banco vira TLzNexValue.Null, qualquer que seja o tipo da coluna — então IsNull funciona uniformemente. A leitura do valor segue as regras de leitura tipada.

O nome da coluna é o label do driver, ou seja o alias quando existe, caindo para o nome real quando o label vem vazio. Select(['name as nick']) se lê com Field('nick').

A linha materializada

ILzNexRow é um retrato: nomes e valores já convertidos para TLzNexValue, copiados para fora do driver. Sobrevive ao cursor avançar e ao cursor fechar, e pode ser guardado, devolvido por função e colocado em array.

Método de ILzNexRowO que faz

function Has(const AName: string): BooleanA coluna existe nesta linha?
function FieldCount: IntegerQuantas colunas.
function FieldName(const AIndex: Integer): stringNome da coluna na posição.
function ToJSON: stringUm objeto JSON, não um array.

Cursor ou materializado

A escolha é entre memória e tempo de vida. O cursor não guarda linha nenhuma, mas só serve enquanto está aberto; a linha materializada custa uma cópia, mas é sua.

Precisa deUse
varrer muitas linhas e descartarwhile Rows.Next do Rows.Field(…)
guardar a linha além da iteraçãoRows.CurrentRow
a lista inteira de uma vezRows.ToRows
uma linha sóFirst no builder — já devolve ILzNexRow
devolver como resposta HTTPRows.ToJSON
 
// cursor: nada fica em memoria
Rows := Db.Table('logs').Get;
while Rows.Next do
  Process(Rows.Field('message').AsString);

// materializado: a linha sobrevive ao cursor
Rows := Db.Table('users').Where('id', 7).Get;
if Rows.Next then
  Row := Rows.CurrentRow;
Rows := nil;
Writeln(Row.Field('name').AsString);     // continua valendo

// tudo de uma vez
List := Db.Table('users').Get.ToRows;
for I := 0 to High(List) do
  Writeln(List[I].Field('name').AsString);
ℹ
ToRows e ToJSON consomem o cursor

Os dois varrem até o fim e deixam o cursor esgotado: a segunda chamada devolve array vazio e []. Os dois também incluem a linha corrente se você já tinha chamado Next — então Next seguido de ToRows não perde a primeira linha.

ToJSON

ToJSON serializa sem biblioteca externa e sem passar por TJSONObject. É o caminho mais curto entre um select e um corpo de resposta.

acento e emoji passam direto; o blob virou base64; NULL virou null

Numa rota Horse, a resposta inteira cabe em duas linhas:

procedure GetUsers(Req: THorseRequest; Res: THorseResponse);
var
  Rows: ILzNexResult;
begin
  Rows := Db.Table('users')
    .Select(['id', 'name', 'email'])
    .OrderBy('id')
    .Limit(20)
    .Get;
  Res.Status(200).ContentType('application/json').Send(Rows.ToJSON);
end;

Rows é local de propósito: ao sair do procedimento a interface é liberada, o cursor fecha e a conexão volta ao pool. Veja o empréstimo da conexão logo abaixo.

Para um objeto único, use ILzNexRow.ToJSON — Db.Table('users').Select(['id', 'name']).Where('id', 7).First.ToJSON devolve {"id":7,"name":"ana"}. Lembre que First devolve nil quando não há linha.

Coluna que não existe

Field levanta ELzNexQuery e a mensagem lista as colunas que existem — é o que transforma um erro de digitação em dois segundos de depuração em vez de dez minutos. 

Rows := Db.Table('users').Select(['id', 'name']).Get;
Rows.Next;
Rows.Field('nome');
// ELzNexQuery: Column "nome" does not exist in the result. Columns: id, name

A busca tenta primeiro o nome exato e depois sem distinguir caixa, então Field('NAME') acha name. Em ILzNexRow o comportamento é o mesmo, com in the row no texto.

Quando a coluna é opcional — select que varia, por exemplo — use TryField:

if Row.TryField('deleted_at', V) and not V.IsNull then
  Writeln('removido em ', V.AsDateTime);

TryField existe só em ILzNexRow. No cursor, a pergunta equivalente é varrer FieldName até FieldCount - 1, ou materializar a linha com CurrentRow e perguntar lá.

O empréstimo da conexão

⚠
O resultado segura a conexão, não a variável de conexão

Um resultado vindo do pool carrega dentro dele o empréstimo da conexão. O empréstimo termina no Close — ou, se ninguém chamar Close, no fim da vida do resultado; não no fim do escopo onde a conexão foi pedida.

Por isso Db.Fetch(…) e .Get funcionam sem você segurar nenhum ILzNexConnection: o resultado faz isso por você. E por isso guardar um ILzNexResult sem fechar em variável global, campo de objeto ou cache é vazamento de conexão disfarçado — ali o Close explícito deixa de ser opcional. 

// errado: Rows e campo do objeto, a conexao fica emprestada indefinidamente
FRows := Db.Table('users').Get;

// certo: variavel local, o emprestimo acaba com o escopo
procedure Handle;
var
  Rows: ILzNexResult;
begin
  Rows := Db.Table('users').Get;
  while Rows.Next do
    ...;
end;

// certo: devolver o emprestimo antes do fim do escopo
Rows := Db.Table('users').Get;
List := Rows.ToRows;
Rows.Close;               // aqui a conexao volta ao pool
Process(List);            // as linhas sao copias, nao precisam do cursor

Com o pool esgotado, Acquire espera o timeout configurado e levanta ELzNexPool — a mensagem termina em Either max is too low, or some ILzNexConnection is being kept alive beyond the request scope, que é exatamente este sintoma. Veja pool de conexões.

ℹ
Terminal que materializa não deixa cursor aberto

First, Value, Scalar, Pluck, Count, Exists e Aggregate consomem o cursor internamente e devolvem dado copiado — nenhum deles prende conexão. Só Get e Db.Fetch devolvem o cursor em si.
