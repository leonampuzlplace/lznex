SQL cru

Um template com marcadores. O valor continua indo como bind, o identificador sai quotado pelo dialeto, e o resto do texto é seu.

A gramática do template

São seis marcadores, e só eles. Qualquer outro caractere passa intacto para o SQL final.

MarcadorConsomeSai comoGera bind
?um argumento posicional?sim
??um argumento posicionalidentificador quotadonão
\?nada? literalnão
:nomeo valor nomeado nome?sim
:nome:o valor nomeado nomeidentificador quotadonão
\:nada: literalnão

Nome de parâmetro aceita letra, dígito e _, e casa sem distinguir caixa. O mesmo :nome pode aparecer várias vezes: cada ocorrência vira um bind próprio, com o mesmo valor. Um : que não é seguido de caractere de nome passa como literal, sem virar marcador.

Posicional e nomeado não se misturam no mesmo template: o construtor escolhido define qual dos dois você está usando.

Os três construtores

function LzNexRaw(const ASQL: string; const AArgs: array of const): ILzNexRawPosicional, com conversão automática dos argumentos. É o que Db.Raw chama.
function LzNexRawValues(const ASQL: string; const AValues: TLzNexValues): ILzNexRawPosicional, com os valores já montados — o caminho para passar Identifier, Raw ou SubQuery, que não cabem em array of const.
function LzNexRawNamed(const ASQL: string; const ANamed: TLzNexNamedValues): ILzNexRawNomeado, alimentado por Vals(['nome', valor, …]).

Os três vivem em LzNex.Raw; acrescente a unit ao uses se o compilador não as encontrar. Para o caso posicional comum, Db.Raw(SQL, Args) é o mesmo com menos digitação.

Posicional

LzNexRaw('select * from t where id = ?', [7]).Build(Db.Client);
SQL
select * from t where id = ?

binds: 7

LzNexRaw('select ?? from ??', ['name', 'users']).Build(Db.Client);
SQL
select `name` from `users`

binds: nenhum — ?? consome o argumento mas não vira parâmetro

Misturando os dois, e com nome qualificado:

R := LzNexRaw('?? = ? and ?? <> ?', ['a.b', 1, 'c', 'x']);
R.Build(Db.Client);
SQL
`a`.`b` = ? and `c` <> ?

binds: 1 | x — na ordem do texto

R := LzNexRaw('?? = ? and ?? <> ?', ['a.b', 1, 'c', 'x']);
R.Build(Db.Client);
SQL
"a"."b" = ? and "c" <> ?

binds: 1 | x — na ordem do texto

O marcador literal existe porque ? aparece em SQL legítimo — caminho de JSON, por exemplo: 

LzNexRaw('json_extract(data, ''$.a\?b'') = ?', ['v']).Build(Db.Client);
SQL
json_extract(data, '$.a?b') = ?

binds: v — o \? não consumiu argumento nenhum

Template sem marcador nenhum é válido e devolve zero bind:

LzNexRaw('now()', []).Build(Db.Client);
SQL
now()

binds: nenhum

Nomeado

Nomeado paga a si mesmo quando o template é grande ou quando o mesmo valor aparece em mais de um lugar: você informa o valor uma vez e o LzNex gera um bind por ocorrência. 

LzNexRawNamed('select * from :table: where id = :id and owner_id = :id',
  Vals(['table', 'users', 'id', 42])).Build(Db.Client);
SQL
select * from `users` where id = ? and owner_id = ?

binds: 42 | 42 — :table: virou identificador, sem bind

i
O cast :: do PostgreSQL passa intacto

:: é reconhecido antes de :nome e sai literal, então id::text e (payload->>'n')::int funcionam sem escape. O que o parser trata como parâmetro é :nome com um dois-pontos, e como identificador é :nome: — com nome entre os dois pontos. O escape :\: continua valendo, e cast(id as text) segue sendo a forma portável entre os cinco dialetos.

Build devolve texto e binds juntos

ILzNexRaw é um template guardado, não SQL pronto: ele só sabe o texto final depois de receber um dialeto. Daí a assinatura.

function Build(const AClient: ILzNexClient): TLzNexFragmentResolve os marcadores contra o dialeto e devolve o fragmento. nil levanta ELzNexBuilder.
function Template: stringO SQL original, com os marcadores. Útil em log e mensagem de erro.

TLzNexFragment carrega os dois lados em um só record — é o que impede texto e parâmetro de se separarem no caminho: 

F := Db.Raw('age > ? and city = ?', [18, 'Recife']).Build(Db.Client);
Writeln(F.Text);                // age > ? and city = ?
Writeln(F.Bindings.Count);      // 2
Writeln(F.Bindings.Describe);   // [integer(18), string('Recife')]

Concatenar fragmentos (Concat, Wrap, Prefix) junta os binds na mesma ordem do texto. O compilador do query builder é construído sobre isso, e é a razão pela qual um raw no meio de uma query grande não desalinha os parâmetros.

Contagem validada antes de montar

Build conta os marcadores posicionais do template e compara com a quantidade de argumentos antes de emitir um caractere. Discrepância nos dois sentidos levanta ELzNex, com os dois números e o template na mensagem. 

LzNexRaw('? and ?', [1]).Build(Db.Client);
// ELzNexBuilder: Raw: the template expected 2 positional argument(s) and got 1.
// Remember that "\?" is a literal and does not consume an argument. SQL: ? and ?

LzNexRaw('?', [1, 2]).Build(Db.Client);
// ELzNexBuilder: Raw: the template expected 1 positional argument(s) and got 2. ...

No caso nomeado, a checagem é por nome, nas duas direções:

LzNexRawNamed('id = :id', Vals(['other', 1])).Build(Db.Client);
// ELzNexBuilder: Raw: parameter ":id" was not given (1 named value(s) received).
// SQL: id = :id

LzNexRawNamed('id = :id', Vals(['id', 1, 'extra', 2])).Build(Db.Client);
// ELzNexBuilder: Raw: named parameter ":extra" does not appear in the template.
// SQL: id = :id

Valor nomeado sobrando é erro de propósito: quase sempre significa nome digitado diferente dos dois lados, e o silêncio sairia como um filtro que nunca foi aplicado.

ℹ
Dois momentos de erro

Argumento de tipo não suportado levanta já na construção, em LzNexRaw — é a conversão de array of const reclamando (um ponteiro, um record). Contagem e nome errados levantam no Build, que é quando o template é lido. Veja a restrição do array of const.

Onde entra raw

Todo ponto abaixo aceita o par (ASQL, AArgs) e monta o ILzNexRaw internamente — você não precisa chamar LzNexRaw na mão.

function Execute(const ASQL: string; const AArgs: array of const): Int64No ILzNex: executa e devolve linhas afetadas.
function Fetch(const ASQL: string; const AArgs: array of const): ILzNexResultNo ILzNex: executa e devolve o cursor.
function Raw(const ASQL: string; const AArgs: array of const): ILzNexRawNo ILzNex: só monta o template, para usar como valor.
function WhereRaw(const ASQL: string; const AArgs: array of const): ILzNexQueryPredicado cru. Também OrWhereRaw.
function SelectRaw(const ASQL: string; const AArgs: array of const): ILzNexQueryExpressão na lista de colunas.
function OrderByRaw(const ASQL: string; const AArgs: array of const): ILzNexQueryOrdenação por expressão.
function GroupByRaw(const ASQL: string; const AArgs: array of const): ILzNexQueryAgrupamento por expressão.
function HavingRaw(const ASQL: string; const AArgs: array of const): ILzNexQueryPredicado cru no having.
function JoinRaw(const ASQL: string; const AArgs: array of const): ILzNexQueryA cláusula de join inteira, incluindo o verbo.
function OnRaw(const ASQL: string; const AArgs: array of const): ILzNexJoinCondição crua dentro de um join montado.
function FromRaw(const ARaw: ILzNexRaw): ILzNexQueryOrigem crua — aqui o ILzNexRaw já montado é o argumento.
class function TLzNexValue.Raw(const ARaw: IInterface): TLzNexValueExpressão crua como valor de coluna em insert e update.
procedure Raw(const ASQL: string; const AArgs: array of const)No ILzNexSchema: DDL que o builder de schema não cobre.
 
Db.Execute('update users set hits = hits + ? where id = ?', [1, 7]);
Rows := Db.Fetch('select * from users where id = ?', [7]);
Db.Table('t').SelectRaw('count(*) as n', []);
Db.Table('t').OrderByRaw('field(id, ?)', [1]);
Db.Table('a').JoinRaw('join b on b.id = ?', [1]);
Db.Schema.Raw('create fulltext index ?? on ??(??)', ['ix_body', 'posts', 'body']);
Db.Table('t').WhereRaw('age > ? and active = ?', [18, True]);
Db.Table('users').WhereRaw('json_extract(??, ?) = ?', ['d', '$.a', 5]);
SQL
select * from `t` where age > ? and active = ?
select * from `users` where json_extract(`d`, ?) = ?

binds: 18 | True · $.a | 5

Note o json_extract(??, ?): o nome da coluna chega quotado pelo dialeto e o caminho JSON vai como bind. É o padrão a seguir — nunca concatene nome de coluna ou valor no texto do template.

Raw dentro de raw

Um ? que recebe um valor de kind vkRaw não gera bind: o template interno é construído na hora e o texto dele entra no lugar, com os binds dele acrescentados na posição certa da lista. É o que permite compor um pedaço de SQL reaproveitável. 

Inner := LzNexRaw('coalesce(??, ?)', ['x', 0]);
R := LzNexRawValues('select ? + ?',
  [TLzNexValue.Raw(Inner), TLzNexValue.FromInteger(5)]);
R.Build(Db.Client);
SQL
select coalesce(`x`, ?) + ?

binds: 0 | 5 — o bind do interno vem antes, porque o texto dele vem antes

O mesmo ? também aceita identificador e subquery, pelo kind do valor — e nos dois casos sai como texto, sem bind: 

LzNexRawValues('order by ?', [TLzNexValue.Identifier('u.name')]).Build(Db.Client);
SQL
order by `u`.`name`

binds: nenhum

Com TLzNexValue.SubQuery, a subquery sai entre parênteses e os binds dela entram na mesma posição. Por isso LzNexRawValues existe: array of const não transporta record, então LzNexRaw nunca receberia um TLzNexValue montado.

⚠
Raw é a porta que o LzNex não tranca

Valor e identificador seguem protegidos pelos marcadores, mas o texto do template é literal: o que você escrever vai para o banco. Nunca construa o template por concatenação com entrada externa — é isso que transforma raw em injeção. Veja segurança.
