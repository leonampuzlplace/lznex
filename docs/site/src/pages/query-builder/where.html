Where e grupos

Valor entra sempre como bind. Números, strings e booleanos convertem sozinhos.

Comparação

Dois overloads: sem operador (assume =) e com operador explícito.

Db.Table('users').Where('id', 1)
Db.Table('users').Where('age', '>=', 18)
Db.Table('users').Where('a', 1).Where('b', 'x')        // and
Db.Table('t').Where('a', 1).OrWhere('b', 2).Where('c', 3)
Db.Table('t').WhereNot('a', 1)
SQL
select * from `users` where `id` = ?
select * from `users` where `age` >= ?
select * from `users` where `a` = ? and `b` = ?
select * from `t` where `a` = ? or `b` = ? and `c` = ?
select * from `t` where not `a` = ?
ℹ
O OR não contamina o resto

O conector é parâmetro de cada statement, não um estado do builder: OrWhere afeta só o predicado que ele introduz, como mostra o quarto exemplo acima.

A lista é fechada. Operador fora dela levanta ELzNexBuilder — é o que fecha a porta para injeção via operador vindo de entrada do usuário.

Coluna contra coluna

Db.Table('t').WhereColumn('a.id', '=', 'b.a_id')
SQL
select * from `t` where `a`.`id` = `b`.`a_id`

binds: nenhum — os dois lados são identificadores

Listas

Db.Table('t').WhereIn('id', ValueList([1, 2, 3]))
Db.Table('t').WhereNotIn('id', ValueList([1, 2]))
Db.Table('t').WhereIn('id', nil)       // lista vazia
Db.Table('t').WhereNotIn('id', nil)
SQL
select * from `t` where `id` in (?, ?, ?)
select * from `t` where `id` not in (?, ?)
select * from `t` where 1 = 0
select * from `t` where 1 = 1

Lista vazia vira 1 = 0 (e not in vazio vira 1 = 1) por duas razões: in () não é SQL válido, e um filtro sem candidatos não deve casar com nada. 

Sub := Db.Query.Table('t').Select(['id']).Where('z', 9);
Db.Table('users').Where('a', 1).WhereInSub('id', Sub);
SQL
select * from `users` where `a` = ? and `id` in (select `id` from `t` where `z` = ?)

binds: 1 | 9 — na ordem do texto

Nulidade, faixa e padrão

Db.Table('t').WhereNull('a')
Db.Table('t').WhereNotNull('a')
Db.Table('t').WhereBetween('age', 18, 65)
Db.Table('t').WhereNotBetween('age', 18, 65)
Db.Table('t').WhereLike('name', '%jo%')
Db.Table('t').WhereNotLike('name', '%jo%')
SQL
select * from `t` where `a` is null
select * from `t` where `a` is not null
select * from `t` where `age` between ? and ?
select * from `t` where `age` not between ? and ?
select * from `t` where `name` like ?
select * from `t` where `name` not like ?

WhereILike usa ilike nativo onde existe — e só o PostgreSQL tem. Nos outros três o dialeto resolve de forma diferente, porque a razão é diferente em cada um. 

select * from `users` where `name` like ?

a comparação já é insensível a caixa por collation

select * from "users" where "name" ilike ?
select * from "users" where upper("name") like upper(?)

não há ilike: o upper vai nos dois lados — e o índice de "name" não serve mais

select * from "users" where "name" like ?

o like do SQLite já ignora caixa em ASCII — e só em ASCII, então acento continua diferenciando

Partes de data

Comparar "o dia 2024-01-02" com uma coluna datetime não funciona com =: a hora entra na comparação. A família WhereDate extrai a parte que interessa — e cada banco extrai de um jeito, então o texto muda e o resultado não. 

Db.Table('orders').WhereDate('created_at', EncodeDate(2024, 1, 2))
Db.Table('orders').WhereYear('created_at', 2024)
Db.Table('orders').WhereMonth('created_at', '>=', 6)
Db.Table('orders').WhereDatePart('created_at', dpMinute, '=', 30)
select * from `orders` where date(`created_at`) = ?
select * from `orders` where year(`created_at`) = ?
select * from `orders` where month(`created_at`) >= ?
select * from `orders` where minute(`created_at`) = ?
select * from "orders" where cast("created_at" as date) = ?
select * from "orders" where extract(year from "created_at") = ?
select * from "orders" where extract(month from "created_at") >= ?
select * from "orders" where extract(minute from "created_at") = ?
select * from "orders" where cast("created_at" as date) = ?
select * from "orders" where extract(year from "created_at") = ?
select * from "orders" where extract(month from "created_at") >= ?
select * from "orders" where extract(minute from "created_at") = ?
select * from "orders" where cast(extract(second from "created_at") as integer) = ?

só o segundo leva cast: no Firebird extract(second …) devolve numeric(*,4) — 28.7630, não 28 —, e sem o cast a igualdade com um inteiro nunca casaria. Verificado no isql do 3 e do 5. 

select * from "orders" where date("created_at") = ?
select * from "orders" where cast(strftime('%Y', "created_at") as integer) = ?
select * from "orders" where cast(strftime('%m', "created_at") as integer) >= ?
select * from "orders" where cast(strftime('%M', "created_at") as integer) = ?

o cast não é enfeite: strftime devolve texto, e sem ele a comparação com inteiro nunca casaria

Há WhereDate, WhereTime, WhereYear, WhereMonth, WhereDay e WhereHour, cada um com overload de operador; WhereDatePart é a forma geral e cobre também dpMinute e dpSecond.

ℹ
Função na coluna atrapalha o índice

where year(created_at) = 2024 impede o banco de usar um índice comum em created_at — ele teria de calcular a função para cada linha. Para intervalo grande em tabela grande, prefira a faixa: WhereBetween('created_at', Inicio, Fim), que usa o índice.

JSON

Três perguntas, três métodos: o valor no caminho, se o documento contém um valor, e o tamanho do array. O caminho é escrito em notação de ponto ('address.city', 'tags[0]') e cada dialeto o traduz. 

Db.Table('users').WhereJsonPath('meta', 'address.city', '=', 'Recife')
Db.Table('users').WhereJsonContains('meta', 'tags', 2)
Db.Table('users').WhereJsonLength('meta', 'tags', '>', 3)
select * from `users` where json_unquote(json_extract(`meta`, '$.address.city')) = ?
select * from `users` where json_contains(`meta`, cast(? as json), '$.tags')
select * from `users` where json_length(`meta`, '$.tags') > ?

o cast(? as json) é necessário: um bind chega com tipo SQL, e json_contains recusa o que não é JSON

select * from "users" where "meta" #>> '{address,city}' = ?
select * from "users" where ("meta" #> '{tags}')::jsonb @> to_jsonb(?)
select * from "users" where jsonb_array_length(("meta" #> '{tags}')::jsonb) > ?

valor de texto vira ?::jsonb (e o conteúdo é lido como documento); escalar nativo vira to_jsonb(?), que converte sem tentar interpretar texto

select * from "users" where cast(json_extract("meta", '$.address.city') as text) = ?
select * from "users" where exists (select 1 from json_each("meta", '$.tags') where value = ?)
select * from "users" where json_array_length("meta", '$.tags') > ?

json_extract devolve o tipo nativo do documento (42 fica inteiro), e no SQLite 42 = '42' é falso — o cast … as text alinha a comparação com os outros dialetos, que já devolvem texto. E não há json_contains: a pergunta vira um exists sobre json_each, que responde por valor escalar dentro do array/objeto; comparar um sub-documento inteiro é recusado com mensagem, em vez de devolver zero linhas em silêncio. 

ELzNexCompile: Dialect "firebird" has no JSON support …

não há tipo nem função de JSON no 3 nem no 5; o builder recusa antes de gerar SQL

⚠
O caminho vai no texto do SQL, não como bind

Nenhum dos bancos aceita o caminho como parâmetro. Por isso o builder valida o caminho contra uma lista fechada — letra, dígito, _, $, . e índice entre colchetes — e levanta ELzNexBuilder em qualquer outro caractere. Sem essa checagem, caminho vindo de requisição seria injeção de SQL. O valor continua sendo bind, sempre.

Texto completo

WhereFullText depende de um índice criado por ILzNexTable.FullText — sem ele o MySQL recusa a query e o PostgreSQL faz varredura completa. Existe em dois dos quatro bancos. 

Db.Schema.CreateTable('articles')
  .Increments('id').Str('title', 200).Text('body')
  .FullText(['title', 'body'])
  .Execute;

Db.Table('articles').WhereFullText(['title', 'body'], 'pascal lazarus')
select * from `articles` where match (`title`, `body`) against (? in natural language mode)

com ftBoolean sai in boolean mode, que habilita +obrigatorio -excluido

select * from "articles" where to_tsvector('simple', coalesce("title", '') || ' ' || coalesce("body", '')) @@ plainto_tsquery('simple', ?)

a expressão é igual à do índice GIN que FullText cria — se divergisse, o índice não seria usado

Exists e SQL cru

Sub := Db.Query.Table('p').SelectRaw('1', []).WhereColumn('p.u', '=', 'users.id');
Db.Table('users').WhereExists(Sub);
Db.Table('users').WhereNotExists(Sub);

Db.Table('t').WhereRaw('age > ? and active = ?', [18, True]);
Db.Table('users').WhereRaw('json_extract(??, ?) = ?', ['d', '$.a', 5]);
SQL
select * from `users` where exists (select 1 from `p` where `p`.`u` = `users`.`id`)
select * from `users` where not exists (select 1 from `p` where `p`.`u` = `users`.`id`)
select * from `t` where age > ? and active = ?
select * from `users` where json_extract(`d`, ?) = ?

binds: 18 | True · $.a | 5

Grupos de predicado

Como o FPC 3.2.2 não tem função anônima, o parêntese é aberto e fechado explicitamente. O builder mantém uma pilha de grupos. 

Db.Table('users')
  .Where('active', True)
  .WhereOpen
    .Where('role', 'admin')
    .OrWhere('role', 'owner')
  .WhereClose
SQL
select * from `users` where `active` = ? and (`role` = ? or `role` = ?)

binds: True | admin | owner

Grupos aninham, e um grupo pode abrir a cláusula:

Db.Table('t').Where('a', 1)
  .WhereOpen
    .Where('b', 2)
    .OrWhereOpen.Where('c', 3).Where('d', 4).WhereClose
  .WhereClose;

Db.Table('t')
  .WhereOpen.Where('a', 1).OrWhere('b', 2).WhereClose
  .Where('c', 3);
SQL
select * from `t` where `a` = ? and (`b` = ? or (`c` = ? and `d` = ?))
select * from `t` where (`a` = ? or `b` = ?) and `c` = ?

O mesmo teste em várias colunas

O caso mais comum de grupo é "procure este valor em qualquer uma destas colunas". WhereAny monta o grupo de or e WhereAll o de and — já fechados, então não contaminam o que vem depois. 

Db.Table('users')
  .WhereAny(['name', 'email', 'phone'], 'like', '%ana%')
  .Where('active', True);

Db.Table('posts').WhereAll(['title', 'body'], '<>', '');
SQL
select * from `users` where (`name` like ? or `email` like ? or `phone` like ?) and `active` = ?
select * from `posts` where (`title` <> ? and `body` <> ?)

o valor é repetido como bind, um por coluna

O operador passa pela mesma lista fechada de operadores aceitos, e lista de colunas vazia levanta ELzNexBuilder — um grupo vazio mudaria o sentido do where em silêncio.
