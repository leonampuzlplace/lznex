Insert, upsert e update

Vals(['coluna', valor, …]) monta os pares, e a ordem informada é a ordem do SQL.

Insert

N  := Db.Table('users').Insert(Vals(['name', 'ana', 'age', 30]));
Id := Db.Table('users').InsertGetId(Vals(['name', 'Leonam', 'email', 'l@x.com']));
SQL
insert into `users` (`name`, `age`) values (?, ?)

binds: ana | 30 · Insert devolve linhas afetadas; InsertGetId, o id gerado

Onde o banco tem RETURNING, o id vem do próprio insert — é o caminho do PostgreSQL. Onde não tem, o LzNex pergunta ao banco qual foi o último id, sempre na mesma conexão do insert. A coluna da chave é id por convenção; quando não for, informe: 

Id := Db.Table('orders').InsertGetId(Vals(['total', 10]), 'order_id');
SQL
-- PostgreSQL e Firebird: o id sai do proprio insert
insert into "orders" ("total") values (?) returning "order_id"

-- MySQL: insert e, na mesma conexao, a pergunta
insert into `orders` (`total`) values (?)
select last_insert_id()

-- SQLite: mesma ideia, outra funcao
insert into "orders" ("total") values (?)
select last_insert_rowid()
ℹ
Por que a mesma conexão importa

Com pool, duas chamadas independentes poderiam cair em conexões diferentes e devolver o id de outra thread. Isso está testado com 8 threads, cada id conferido contra a linha daquela thread, em cada banco. O caminho do RETURNING é imune a esse problema por construção, e também não se confunde com sequência que um gatilho tenha avançado noutra tabela. No Firebird não há "último id da sessão" — o gerador é por tabela, e LastInsertId levanta: ali só o RETURNING serve.

InsertMany

Várias linhas num único comando. Coluna ausente em uma das linhas vira default, não NULL — é o vkUnset de TLzNexValue em ação. Coluna que aparece só numa linha posterior entra no fim da lista de colunas. 

Db.Table('users').InsertMany([
  Vals(['name', 'ana', 'age', 30]),
  Vals(['name', 'bob'])
]);

Db.Table('users').InsertMany([
  Vals(['name', 'ana']),
  Vals(['name', 'bob', 'age', 40])
]);
SQL
insert into `users` (`name`, `age`) values (?, ?), (?, default)
insert into `users` (`name`, `age`) values (?, default), (?, ?)

binds: ana | 30 | bob · ana | bob | 40

Valor cru numa coluna do insert:

V := Vals(['name', 'ana']);
V[0].Value := TLzNexValue.Raw(Db.Raw('upper(?)', ['ana']));
Db.Table('users').Insert(V);
SQL
insert into `users` (`name`) values (upper(?))

Returning

Db.Table('users').Returning(['id']);
// ELzNexCompile: MySQL nao suporta RETURNING. Use InsertGetId.
Db.Table('users').Returning(['id', 'created_at']).Insert(Vals(['name', 'ana']));
Db.Table('users').Where('id', 7).Returning(['id']).Update(Vals(['name', 'x']));
Db.Table('users').Where('id', 7).Returning(['id']).Delete;
SQL
insert into "users" ("name") values (?) returning "id", "created_at"
update "users" set "name" = ? where "id" = ? returning "id"
delete from "users" where "id" = ? returning "id"

Upsert

OnConflict devolve ILzNexOnConflict, que só tem Ignore, Merge e MergeValues. Esquecer de completar a cláusula não compila. 

Db.Table('users').OnConflict(['email']).Ignore
  .Insert(Vals(['name', 'ana']));

Db.Table('users').OnConflict(['email']).Merge
  .Insert(Vals(['name', 'ana', 'age', 30]));

Db.Table('users').OnConflict(['email']).Merge(['age'])
  .Insert(Vals(['name', 'ana', 'age', 30]));

Db.Table('users').OnConflict(['email']).MergeValues(Vals(['age', 99]))
  .Insert(Vals(['name', 'ana', 'age', 30]));
SQL
insert ignore into `users` (`name`) values (?)
insert into `users` (`name`, `age`) values (?, ?) on duplicate key update `name` = values(`name`), `age` = values(`age`)
insert into `users` (`name`, `age`) values (?, ?) on duplicate key update `age` = values(`age`)
insert into `users` (`name`, `age`) values (?, ?) on duplicate key update `age` = ?

no insert ignore a coluna de conflito não aparece: o MySQL resolve no verbo

Db.Table('users').OnConflict(['email']).Ignore
  .Insert(Vals(['name', 'ana']));

Db.Table('users').OnConflict([]).Ignore
  .Insert(Vals(['name', 'ana']));

Db.Table('users').OnConflict(['email']).Merge
  .Insert(Vals(['name', 'ana', 'age', 30]));

Db.Table('users').OnConflict(['email']).MergeValues(Vals(['name', 'fixed']))
  .Insert(Vals(['name', 'ana']));
SQL
insert into "users" ("name") values (?) on conflict ("email") do nothing
insert into "users" ("name") values (?) on conflict do nothing
insert into "users" ("name", "age") values (?, ?) on conflict ("email") do update set "name" = excluded."name", "age" = excluded."age"
insert into "users" ("name") values (?) on conflict ("email") do update set "name" = ?

no Postgres, do update exige a coluna de conflito: Merge sem OnConflict([...]) levanta ELzNexCompile

Db.Table('users').OnConflict(['email']).Merge
  .Insert(Vals(['name', 'ana', 'email', 'a@b.c']));

Db.Table('users').OnConflict([]).Merge
  .Insert(Vals(['id', 1, 'name', 'ana']));
SQL
update or insert into "users" ("name", "email") values (?, ?) matching ("email")
update or insert into "users" ("id", "name") values (?, ?)

sem matching o Firebird casa pela chave primária — o oposto do Postgres, onde Merge sem coluna levanta

Db.Table('users').OnConflict(['email']).Ignore
  .Insert(Vals(['name', 'ana']));

Db.Table('users').OnConflict(['email']).Merge
  .Insert(Vals(['name', 'ana', 'age', 30]));
SQL
insert into "users" ("name") values (?) on conflict ("email") do nothing
insert into "users" ("name", "age") values (?, ?) on conflict ("email") do update set "name" = excluded."name", "age" = excluded."age"

forma do Postgres, inclusive o where no upsert

No Firebird o upsert é update or insert … matching, que atualiza todas as colunas da linha e leva uma linha por chamada. Três coisas levantam ali: Ignore (não há do nothing; use Merge ou cheque com Exists), Merge com lista de colunas ou MergeValues, e upsert de mais de uma linha. Veja Dialetos.

Em MergeValues, um valor TLzNexValue.Unset reaproveita o valor que veio no insert em vez de gerar bind — útil para misturar colunas fixas e colunas copiadas.

Upsert em uma chamada

Upsert é açúcar para OnConflict(...).Merge(...) seguido de InsertMany: recebe as linhas, as colunas de conflito e as colunas a atualizar numa só chamada. Lista de atualização vazia atualiza todas as colunas da linha. 

N := Db.Table('prices').Upsert(
  [Vals(['sku', 'A1', 'cents', 1990]),
   Vals(['sku', 'B2', 'cents', 2990])],
  ['sku'],          // colunas de conflito
  ['cents']);       // o que atualizar quando colidir
SQL · MySQL
insert into `prices` (`sku`, `cents`) values (?, ?), (?, ?) on duplicate key update `cents` = values(`cents`)

Sem as colunas de conflito, Upsert levanta ELzNexBuilder — elas são o que diz ao banco qual linha existente atualizar. No Firebird vale o limite do update or insert: uma linha por chamada.

UpdateOrInsert

Quando não existe chave única para o banco resolver o conflito, resta decidir na aplicação. UpdateOrInsert atualiza a linha que casa com as colunas de busca e, se nenhuma casar, insere busca + valores. Devolve True quando inseriu. 

Inserted := Db.Table('settings').UpdateOrInsert(
  Vals(['user_id', 7, 'key', 'theme']),   // como achar a linha
  Vals(['value', 'dark']));               // o que gravar
SQL · existência primeiro, depois a escrita
select * from `settings` where `user_id` = ? and `key` = ? limit ?
update `settings` set `value` = ? where `user_id` = ? and `key` = ?

quando o select não acha nada, a segunda query é insert into `settings` (`user_id`, `key`, `value`) values (?, ?, ?)

⚠
A ordem é existência → escrita, e não "update e vê quantas linhas mudaram"

No MySQL um update que grava o mesmo valor que já estava lá devolve zero linhas afetadas. Uma implementação que decidisse por esse número concluiria "não existe" e inseriria uma linha duplicada. Por isso o UpdateOrInsert consulta antes.

Isso deixa uma janela entre o select e o insert: dois processos simultâneos podem inserir os dois. Onde houver chave única, prefira Upsert — lá a atomicidade é do banco. Onde não houver, chame dentro de uma transação.

Update, increment e delete

N := Db.Table('users').Where('id', 7).Update(Vals(['name', 'x', 'email', 'y']));
Db.Table('users').Where('id', 7).Increment('hits');          // +1
Db.Table('users').Increment('hits', 10);
Db.Table('users').Decrement('stock', 2);
N := Db.Table('users').Where('id', 3).Delete;
Db.Table('logs').Truncate;
SQL
update `users` set `name` = ?, `email` = ? where `id` = ?
update `users` set `hits` = `hits` + ? where `id` = ?
update `users` set `hits` = `hits` + ?
update `users` set `stock` = `stock` + ?
delete from `users` where `id` = ?
truncate `logs`

o bind de Decrement é -2: o delta negativo vai no valor, não no SQL

Increment e Decrement geram col = col + ? — a soma acontece no banco, sem o ciclo ler-somar-gravar e sem a corrida que ele traz. Update sem colunas levanta ELzNexBuilder; AST de update sem set levanta ELzNexCompile.

Particularidades por dialeto

-- update com join, alias e limit
update `users` as `u` inner join `tenants` as `t` on `t`.`id` = `u`.`tenant_id` set `name` = ? limit ?

-- delete com limit
delete from `users` where `id` = ? limit ?

-- delete com join repete o alvo antes do from
delete `u` from `users` as `u` inner join `tenants` as `t` on `t`.`id` = `u`.`tenant_id`

-- truncate sem reiniciar a sequencia
truncate `users`
-- limit em delete nao e aceito: levanta ELzNexCompile mencionando 'limit'

-- truncate reinicia a identidade
truncate "users" restart identity
-- join e limit em update/delete levantam ELzNexCompile

-- nao existe TRUNCATE: vira um delete sem where
delete from "users"
-- join e limit em update/delete levantam ELzNexCompile

-- nao existe TRUNCATE: vira um delete sem where
delete from "users"

Truncate virando delete from não é só texto: o custo passa a ser linha por linha, dentro da transação, e a sequência de identidade não reinicia.
