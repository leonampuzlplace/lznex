Paginação

Três formas de paginar — com total, sem total e por cursor — mais a varredura em lotes.

Limit e Offset são o primitivo; em cima deles o LzNex oferece três paginações prontas, que executam a query e devolvem a janela com os metadados no lugar. A escolha entre elas é a escolha entre saber o total, ser rápido e ser estável — não dá para ter os três ao mesmo tempo.

MétodoQueriesSabe o total?Aguenta o conjunto mudar?Vai para a página 7?
Paginate 2 (count + janela) sim não sim
SimplePaginate 1 não, só "há próxima" não sim
CursorPaginate 1 não, só "há próxima" sim não, só adiante e atrás

Regra prática: tela administrativa com numeração pede Paginate; botão "carregar mais" pede SimplePaginate; feed, API pública ou lista que recebe inserção enquanto é lida pede CursorPaginate. Para processar a tabela inteira em memória limitada, nenhuma das três: use Chunk.

Paginate — a janela com total

var
  Page: TLzNexPage;
begin
  Page := Db.Table('users').Where('active', True).OrderBy('name').Paginate(2, 10);

  Writeln(Page.Total);          // 57   -- linhas que o filtro deixa
  Writeln(Page.LastPage);       // 6    -- ceil(57 / 10)
  Writeln(Page.CurrentPage);    // 2
  Writeln(Page.Count);          // 10   -- linhas nesta janela
  Writeln(Page.HasMorePages);   // True

  for I := 0 to Page.Count - 1 do
    Writeln(Page.Rows[I].Field('name').AsString);
end;
SQL · duas queries, nesta ordem
select count(*) from `users` where `active` = ?
select * from `users` where `active` = ? order by `name` asc limit ? offset ?

o count não leva o order by (não muda o total e custa sort) nem a janela

O count roda num clone da query: a sua continua intacta, com as colunas que você pediu. E quando há group by, having, union ou Distinct, o count vai por fora, numa subquery — senão count(*) entraria no agrupamento e devolveria o tamanho do primeiro grupo em vez da quantidade de grupos. 

Db.Table('orders').Select(['user_id']).GroupBy(['user_id']).OrderBy('user_id').Paginate(1, 10)
SQL · o count da query agrupada
select count(*) from (select `user_id` from `orders` group by `user_id`) as `lznex_agg`
select `user_id` from `orders` group by `user_id` order by `user_id` asc limit ? offset ?
⚠
Fora de transação, o total e a janela vêm de conexões diferentes

São duas queries, e cada uma pega sua conexão do pool. Entre elas outra sessão pode inserir ou apagar, e aí o total é de uma foto e as linhas de outra — Total 57 com uma página que devolve 9 linhas, por exemplo. Em tela de listagem isso é inofensivo; quando os dois números precisam fechar, abra uma transação: Trx.Table('users').…Paginate(2, 10).

SimplePaginate — sem o count

O count é a parte cara da paginação: em tabela grande ele varre tudo o que o filtro deixa, a cada página. SimplePaginate não o roda — pede uma linha além da página e usa a presença dela como resposta para "há próxima". 

var
  Page: TLzNexSimplePage;
begin
  Page := Db.Table('posts').OrderByDesc('id').SimplePaginate(1, 10);

  Writeln(Page.Count);          // 10  -- a 11a linha foi descartada
  Writeln(Page.HasMorePages);   // True
end;
SQL · uma query só
select * from `posts` order by `id` desc limit ? offset ?

binds: 11 | 0 — o limite é APerPage + 1, e a linha extra nunca chega a quem chamou

CursorPaginate — por cursor (keyset)

As duas primeiras usam offset, e offset conta posições: se uma linha for inserida antes da janela entre a página 1 e a 2, tudo escorrega uma casa e a última linha da página 1 aparece de novo na página 2. O cursor não conta posição — ele guarda os valores da ordenação da última linha lida e continua de > aqueles valores. 

var
  Page: TLzNexCursorPage;
  Cursor: string;
begin
  Cursor := '';                 // vazio = primeira pagina
  repeat
    Page := Db.Table('posts').OrderBy('id').CursorPaginate(50, Cursor);

    for I := 0 to Page.Count - 1 do
      Process(Page.Rows[I]);

    Cursor := Page.NextCursor;  // vazio quando acabou
  until Cursor = '';
end;
SQL · primeira página e seguinte
select * from `posts` order by `id` asc limit ?
select * from `posts` where ((`id` > ?)) order by `id` asc limit ?

nenhum offset: o banco salta direto pelo índice da chave, e o custo não cresce com a página

Com mais de uma coluna na ordenação, o corte precisa empatar nas anteriores para desempatar na seguinte. O LzNex escreve isso na forma expandida — e não como (a, b) > (?, ?), que o Firebird não tem —, então o texto é o mesmo nos cinco bancos: 

Db.Table('posts').OrderBy('score').OrderBy('id').CursorPaginate(20, Cursor)
SQL
select * from `posts`
where ((`score` > ?) or (`score` = ? and `id` > ?))
order by `score` asc, `id` asc limit ?

binds: score | score | id | 21 — o valor da primeira chave aparece duas vezes, uma por comparação

Ir e voltar

NextCursor e PrevCursor vêm preenchidos quando existe para onde ir — string vazia significa fim (ou começo). Para trás, o LzNex inverte os operadores e a ordenação, lê a janela e devolve as linhas na ordem original, para quem chamou não ter de reverter nada. 

First  := Db.Table('posts').OrderBy('id').CursorPaginate(5);
// First.PrevCursor = ''  -- nao ha pagina anterior a primeira

Second := Db.Table('posts').OrderBy('id').CursorPaginate(5, First.NextCursor);
Back   := Db.Table('posts').OrderBy('id').CursorPaginate(5, Second.PrevCursor);
// Back.Rows traz as mesmas 5 linhas de First.Rows, na mesma ordem
SQL · a página anterior
select * from `posts` where ((`id` < ?)) order by `id` desc limit ?

operador e ordem invertidos para o limite pegar as linhas imediatamente anteriores; as linhas voltam revertidas em memória

O cursor é um texto opaco, em base64 url-safe sem =, + ou / — viaja em query string sem escape. Ele carrega os valores tipados (inteiro, texto, data com milissegundos, booleano) e o sentido da navegação. Cursor adulterado ou de outra ordenação não é ignorado em silêncio: levanta ELzNexBuilder.

⚠
O que o cursor exige da ordenação

Pelo menos um OrderBy — é a ordem que define o corte. A última coluna da ordenação tem de ser única (normalmente a chave primária): se duas linhas empatarem em todas as chaves, o corte não sabe separá-las e uma delas é pulada. E as colunas de ordenação têm de estar no Select, porque é de lá que o cursor tira os valores — pedir Select(['name']) e ordenar por id levanta, com a mensagem dizendo o que falta.

Recusados de propósito: OrderByRaw (não há coluna para comparar) e ordem de nulos explícita (nlFirst/nlLast), porque no MySQL ela é emulada com uma expressão extra de ordenação que o where do cursor não reproduz — a página sairia furada. Coluna nula na chave também levanta: comparação com null nunca é verdadeira, e a próxima página voltaria vazia.

Chunk, ChunkById e Each — varrer tudo

Paginação é para mostrar; varredura é para processar. Chunk lê a tabela em lotes, materializa um lote por vez e fecha o cursor antes de devolver — nenhuma conexão do pool fica presa entre dois lotes, o que importa quando o processamento de cada lote é demorado. 

var
  Chunks: ILzNexChunks;
  I: Integer;
begin
  Chunks := Db.Table('users').ChunkById(500);
  while Chunks.Next do
  begin
    for I := 0 to High(Chunks.Rows) do
      Export(Chunks.Rows[I]);

    Writeln(Format('lote %d, %d linhas ate agora',
      [Chunks.ChunkIndex, Chunks.RowsSeen]));
  end;
end;
SQL · um por lote
select * from `users` order by `id` asc limit ?
select * from `users` where `id` > ? order by `id` asc limit ?
select * from `users` where `id` > ? order by `id` asc limit ?
FormaComo andaQuando usar
ChunkById(N) chave > última lida; ignora o OrderBy da query, porque a ordem passa a ser a da chave o default. Imune a inserção e remoção durante a varredura
Chunk(N) limit/offset, lote a lote; exige OrderBy quando a ordem do processamento importa e não pode ser a da chave
Each(handler, N) ChunkById por baixo, chamando o handler linha por linha quando o laço é sempre o mesmo; devolve quantas linhas visitou

Each recebe ponteiro de método, não função anônima — o FPC 3.2 não tem closure. O handler ganha um var AStop: colocar True interrompe a varredura no meio do lote. 

type
  TExporter = class
    FCount: Integer;
    procedure Visit(const ARow: ILzNexRow; var AStop: Boolean);
  end;

procedure TExporter.Visit(const ARow: ILzNexRow; var AStop: Boolean);
begin
  Inc(FCount);
  Write(ARow.ToJSON);
  AStop := FCount >= 1000;      // para no milesimo
end;

// ...
Total := Db.Table('users').Each(Exporter.Visit, 200);
ℹ
Chunk por offset cobra o preço do offset

Chunk(N) pede ao banco para contar e descartar as linhas anteriores a cada lote, então o lote 1000 custa mais que o lote 1 — e, se o conjunto mudar no meio, a janela escorrega do mesmo jeito que em Paginate. ChunkById não tem nenhum dos dois problemas; só peça uma chave NOT NULL e crescente.

Como cada banco escreve a janela

As três paginações são construídas sobre Limit/Offset, então herdam de graça o que cada dialeto já resolve — veja Offset sem Limit para o detalhe. 

select * from `posts` order by `id` asc limit ? offset ?
select * from "posts" order by "id" asc limit ? offset ?
select * from "posts" order by "id" asc offset ? rows fetch next ? rows only

não há limit: a ordem das cláusulas é a inversa, e os binds seguem o texto

select * from "posts" order by "id" asc limit ? offset ?

O where do cursor é idêntico nos cinco bancos — é só comparação de coluna com parâmetro, sem nenhuma função de dialeto. Nada a conferir por banco.
