O cursor de paginação não serve para toda ordenação

CursorPaginate corta o conjunto comparando os valores da ordenação, e isso impõe condições que o offset não impõe. O builder recusa o que não consegue reproduzir, em vez de devolver página errada em silêncio:

CasoO que acontecePor quê
sem OrderBylevantasem ordem não há o que comparar
OrderByRawlevantaexpressão crua não dá o nome da coluna
nlFirst / nlLastlevantano MySQL a ordem de nulos é emulada com uma expressão extra que o where do cursor não repete
coluna de ordenação fora do Selectlevantao cursor carrega o valor dela, e não há de onde ler
valor nulo na chavelevantacomparação com null nunca é verdadeira; a página seguinte voltaria vazia
última chave não únicanão é detectadoexigiria ler o schema; linhas empatadas em todas as chaves podem ser puladas

A última linha é a única que não dá erro: ordene sempre por uma coluna única no fim — em geral a chave primária.

Réplica de leitura não tem sticky

Com ReadReplica configurada, toda leitura fora de transação vai para a réplica — inclusive a leitura que acontece logo depois de uma escrita sua. Se a replicação estiver atrasada, o dado recém-inserido pode não aparecer. O LzNex não implementa o sticky por requisição que alguns frameworks têm: a decisão fica explícita, com UsePrimary ou com uma transação. Veja Réplica de leitura.

O que a suíte de integração não cobre

A suíte de integração roda nos cinco bancos (MySQL, PostgreSQL, Firebird 3, Firebird 5 e SQLite) e cobre CRUD, InsertGetId, transações (commit e rollback), round-trip de UTF-8, pool sob carga, oito threads concorrentes e o runner de migrations — tests/Test.It.Migrator.pas aplica, confere as tabelas de controle, roda de novo para provar idempotência, desfaz, acompanha Status/Pending e prova que o lock recusa a segunda rodada e que Unlock o libera.

Ficam fora da suíte automatizada duas coisas, as duas por natureza:

  • O CLI em si — o binário lznex e o parsing de subcomando. O migrator por baixo está testado; o despacho de linha de comando, não.
  • As migrations em .sql. A migration de teste é definida na própria unit, pelo schema builder, justamente porque é portável: um arquivo .sql é escrito para um dialeto só e não poderia rodar nos cinco bancos.

A config do teste do migrator usa MigrationsTable('it_migrations') e MigrationsDir('') — a fonte é só o registro de código, para a suíte não puxar o .sql de exemplo do repositório, que é MySQL.

Não há como informar o where do on conflict

O dialeto declara a capacidade (SupportsOnConflictWhere é True no PostgreSQL e no SQLite, False no MySQL e no Firebird), mas ILzNexOnConflict só tem Ignore, Merge e MergeValues — nenhum lugar para passar o predicado de um índice parcial.

function Ignore: ILzNexQueryon conflict (...) do nothing
function Merge: ILzNexQuerydo update set com todas as colunas do insert
function Merge(const AColumns: array of string): ILzNexQueryidem, só as colunas listadas
function MergeValues(const AValues: TLzNexNamedValues): ILzNexQuerydo update set com valores explícitos

A capacidade existe para o dia em que a interface ganhar esse ponto de entrada. Hoje, um upsert sobre índice parcial sai por Db.Raw.

Enum nativo do PostgreSQL

Enum não cria um tipo (create type ... as enum) no PostgreSQL: sai como text mais um check. 

Db.Schema.CreateTable('o').Enum('status', ['new', 'done']);
create table `o` (`status` enum('new', 'done') null)
create table "o" ("status" text null check ("status" in ('new', 'done')))
create table "o" ("status" varchar(255) check ("status" in ('new', 'done')))
create table "o" ("status" varchar(255) check ("status" in ('new', 'done')))

A restrição de domínio é equivalente; o tipo não. Um tipo enum de verdade precisaria ser criado antes da tabela, num comando próprio — e o DDL de coluna não tem como emitir um comando que o antecede. Se o tipo nativo importa, crie-o numa migration .sql e declare a coluna com Specific.

Seed em .sql não é executada

Aqui as migrations e as seeds divergem, e a assimetria morde: migration em .sql é lida do disco e aplicada, seed em .sql não. seed:make cria o arquivo — database/seeds/<slug>.sql — mas seed:run percorre apenas as classes passadas a RegisterSeed. O arquivo fica no disco sem nunca rodar, e sem aviso. 

lznex seed:make demo_users
lznex seed:run
saída
created: database/seeds/demo_users.sql
0 seed(s) executed

o arquivo foi criado e ignorado, sem erro

--only também só conhece nome registrado, e o erro lista o que existe: 

error: Seed "demo_users" is not registered. Registered: users, roles.

Até isso mudar, seed útil é classe Pascal registrada. Veja Seeds.

Sem método Jsonb em ILzNexTable

O tipo ctJsonb existe e o compilador de DDL do PostgreSQL emite jsonb para ele. Falta só o método na interface de colunas: ILzNexColumnDef tem Json, não Jsonb. Até aparecer, o caminho é Specific, que entrega o tipo direto ao banco: 

Db.Schema.CreateTable('docs').Specific('payload', 'jsonb');
SQL
create table "docs" ("payload" jsonb null)

Specific não é portável por definição — o texto vai como veio

DDL não é transacional no MySQL

Isso não é escolha da biblioteca: o MySQL dá commit implícito em create, alter e drop. Uma migration que falha no meio deixa atrás o que já executou, e o rollback não desfaz nada disso. O migrator avisa quando o dialeto não tem DDL transacional: 

2026-10-24 12:00:00 [lznex] warn  The mysql dialect commits implicitly on DDL: if
the migration fails midway, the rollback will NOT undo CREATE/ALTER/DROP already
executed. Keep one migration per structural change so the damage stays small.

A defesa é de escrita: uma mudança estrutural por migration, e cada passo reentrante. O MySQL é o único dos quatro nessa situação: DdlIsTransactional é True em PostgreSQL, Firebird e SQLite.

Firebird: o que levanta erro

LzNex.Client.Firebird cobre Firebird 3 e 5 com o mesmo SQL. O que o banco não tem, o compilador recusa com ELzNexCompile (ou ELzNexSchema no DDL) e a mensagem diz a saída — nunca gera SQL que o servidor vai rejeitar:

  • Intersect e Except_ — não existem no Firebird 3 nem no 5. A reescrita é WhereInSub ou WhereNotExists.
  • OnConflict(…).Ignore — não há do nothing. Use Merge (que vira update or insert … matching) ou cheque com Exists antes.
  • Merge com lista de colunas ou com MergeValues — o update or insert atualiza todas as colunas da linha; honrar um subconjunto seria mentira.
  • Upsert de mais de uma linha — update or insert leva uma linha por chamada.
  • NoWait — esperar é atributo da transação no Firebird, não cláusula do lock.
  • ForShare — with lock é sempre exclusivo.
  • DistinctOn, e Limit/Join em update/delete.
  • LastInsertId — o gerador é por tabela, não há "último id da sessão". InsertGetId funciona: lê o id do insert … returning.
  • Renomear tabela — não existe no 3 nem no 5. O erro diz que a tabela tem de ser recriada, copiada e apagada na migration.

Duas coisas que não levantam, mas mudam o texto, e vale saber:

  • Truncate vira delete from — não há truncate, e o custo é outro: linha por linha, dentro da transação.
  • Nome de índice e de constraint é cortado em 31 bytes (limite do Firebird 3), com um hash do nome inteiro no fim. O nome no banco não é o que você leria no código.

SkipLocked compila para with lock skip locked, sintaxe que só existe a partir do Firebird 5: no 3 o SQL sai e o servidor recusa. O dialeto é um só, então essa é a única construção em que a versão importa. Veja Dialetos.

SQLite: o que levanta erro

O SQLite é o banco com mais recorte: é um arquivo, não um servidor, e o ALTER TABLE dele faz quase nada.

  • ForUpdate e ForShare — não há lock de linha; uma transação de escrita tranca o banco inteiro. Tire a cláusula, ou serialize os escritores na aplicação.
  • Returning — recusado pelo builder. InsertGetId usa last_insert_rowid(), que é por conexão (e o pool garante que seja a mesma).
  • Change (alterar coluna) — não há alter column. A saída é recriar a tabela na migration: criar a nova, copiar, apagar, renomear.
  • add column … not null sem Default_ — restrição do próprio SQLite: as linhas que já existem não teriam valor.
  • Primary e chave estrangeira em tabela existente — não há ALTER TABLE ADD CONSTRAINT. Ou a restrição nasce com a tabela, ou não nasce. Unique escapa: vira create unique index.
  • DistinctOn, e Limit/Join em update/delete.
⚠
Comment é ignorado em silêncio

Não existe comment on no SQLite. O comentário é documentação, e derrubar uma migration por causa dele seria pior que perdê-lo: o DDL sai sem o comentário, sem erro e sem aviso. É a única coisa no DDL do SQLite que desaparece calada.

Mais três diferenças sem erro: Truncate vira delete from; WhereILike sai igual a WhereLike, porque o like do SQLite já ignora caixa em ASCII — e só em ASCII, então acento continua diferenciando; e BigIncrements sai igual a Increments (integer primary key autoincrement), porque só integer primary key é apelido do rowid, que já é de 64 bits.

O ZeosLib não vem pelo Boss

A coordenada do LzNex é real — github.com/leonampuzlplace/lznex — e a versão sai das tags que a Action publica. O Zeos não tem coordenada: o Boss aborta quando uma dependência não traz boss.json, e o repositório oficial do Zeos não tem o manifesto. Por isso o boss.json do pacote não declara o Zeos: ele é dependência de quem instala, não do pacote. Três consequências:

  • boss install não traz o Zeos. O projeto que consome escolhe a fonte — pacote zdbc na IDE, um fork com manifesto no boss.json dele, ou um clone no unit path.
  • Vendorizar um clone em modules/ junto com o pacote resolveria o caso vazio, mas custa mais caro no caso comum: quem já tem o Zeos instalado na IDE ficaria com as mesmas units em dois caminhos, e o build para em Duplicate unit ou num .ppu incompatível. O erro de unit faltando é mais honesto que o de unit duplicada.
  • Os Dockerfiles daqui não têm IDE nenhuma, então clonam o espelho oficial em modules/zeoslib — é para lá que os .lpi deste repositório apontam.
