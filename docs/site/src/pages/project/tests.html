Testes e Docker

Tudo roda em container: a suíte sem banco, a suíte com MySQL de verdade, o CLI e a API de exemplo. O docker-compose.yml do repositório é a única configuração necessária.

Os quatro comandos

docker compose run --rm tests          # unitários, sem banco
docker compose run --rm tests-it       # integração + concorrência (MySQL real)
docker compose run --rm cli migrate:latest
docker compose up -d api && curl localhost:9000/health

tests e tests-it rodam o mesmo binário (./bin/lznex-tests-debug, build mode Debug). A diferença é a variável LZNEX_IT: sem ela, Test.Integration e Test.Concurrency chamam Ignore e os casos aparecem como ignorados — não como falha. Só tests-it define LZNEX_IT=1 e declara depends_on: mysql (service_healthy).

Serviços do compose

ServiçoO que é
mysqlmysql:8.4 com utf8mb4 / utf8mb4_0900_ai_ci, publicado em 3307:3306 para não colidir com um MySQL local. Healthcheck por mysqladmin ping; dados no volume mysql-data.
testsEstágio builder do Dockerfile, working_dir: /src. Só HEAPTRC=haltonnotreleased no ambiente — nenhuma variável de banco, nenhum depends_on.
tests-itMesma imagem, mais as variáveis LZNEX_* e DB_*, LZNEX_IT=1 e HEAPTRC=haltonnotreleased. Espera o healthcheck do MySQL antes de subir.

spikeContainer de bancada: monta o repositório em /work e fica em sleep infinity. Serve para compilar sonda por sonda à mão.

Os serviços que falam com o banco compartilham o mesmo bloco de ambiente (a âncora x-db-env no topo do compose): 

LZNEX_CLIENT=mysql
LZNEX_HOST=mysql
LZNEX_PORT=3306
LZNEX_DATABASE=lznex
LZNEX_USER=root
LZNEX_PASSWORD=secret
LZNEX_LIBRARY=/usr/lib/x86_64-linux-gnu/libmariadb.so.3

LZNEX_LIBRARY está ali porque a imagem é Ubuntu 26.04, onde só existe libmariadb.so.3 — veja Troubleshooting.

ℹ
O host do banco é mysql, não localhost

Dentro da rede do compose o banco responde pelo nome do serviço. Da sua máquina, é localhost:3307. Rodar a suíte de integração fora do container exige apontar DB_HOST/DB_PORT para essa porta publicada.

Organização dos testes

Duas camadas: a suíte FPCUnit (um binário, tests/LzNexTests.lpr) e as sondas, programas .lpr independentes que compilam e rodam sozinhos. A sonda existe para isolar um subsistema sem arrastar o resto do framework de teste — quando o linker do FPC reclama, dá para saber de qual unit veio.

ArquivoCobre
Test.CoreTLzNexValue (conversão implícita, Unset não bindável, precisão de Int64), Vals/ValueList, ordem dos bindings e composição de fragmentos.
Test.QuerySelect e alias, where e operadores, grupos de predicado, join, ordenação e paginação, SQL cru, clone. Registra também as áreas security (operador fora da lista, valor nunca interpolado, backtick escapado) e dialect.
Test.PostgresO dialeto PostgreSQL por texto: identificador com aspas duplas, limit/offset ANSI, returning, on conflict, distinct on, nulls first/last, truncate e o DDL. Quase todo caso compara com o MySQL para a mesma entrada, e os dois lados são asserções — inclusive o que o MySQL tem que recusar.
Test.IntegrationMySQL real: InsertGetId (id próprio, ids crescentes, dentro de transação commitada e revertida), CRUD completo e ida-e-volta de UTF-8.
Test.ConcurrencyCarga paralela: operações mistas que não se misturam, pool que devolve toda conexão, transações isoladas entre threads, mais threads que conexões e cursor aberto segurando o empréstimo.
Test.HelperBase das suítes unitárias: AssertSQL, AssertBindings e AssertQuery, que comparam texto gerado e lista de binds de uma vez.
Probe*.lprProbeValue (valor), ProbeAst (AST), ProbeQuery (builder), ProbeCompiler (compilador de query), ProbeSchema (DDL), ProbeMigration (migrator e seeder), ProbeEndToEnd (fachada até o SQL) e ProbeZeos (conexão, pool e transação contra o Zeos).
DiagPool.lprDiagnóstico, não teste: imprime InUse e Size do pool a cada passo. Serve para ver uma conexão presa.

Gate de vazamento

scripts/run-tests.sh coleta bin/Probe* e bin/Test*, exporta HEAPTRC=haltonnotreleased (default do script) e roda um por um. Como os binários são compilados com -gh, o heaptrc aborta o processo com exit 203 se sobrar bloco não liberado. Resultado: um único critério — exit != 0 — cobre asserção quebrada e memória não liberada. 

bash scripts/run-tests.sh                    # tudo em bin/
bash scripts/run-tests.sh bin/ProbeCompiler  # um binário só
saída
run-tests: HEAPTRC=haltonnotreleased
run-tests: 8 binario(s)

  PASS  ProbeAst                     [gh]
  PASS  ProbeCompiler                [gh]
  LEAK  ProbeSchema                  exit=203
          24 unfreed memory blocks

run-tests: pass=7 fail=0 leak=1
run-tests: FALHOU
  - ProbeSchema (vazamento)

formato do relatório, com um binário vazando — na última execução registrada foram todos PASS

A coluna entre colchetes não é enfeite: o script procura a string Heap dump by heaptrc unit dentro do binário. Não achando, marca SEM -gh e avisa que o gate não vale para aquele binário. É o que impede um verde falso.

⚠
O -gh tem que ir em CustomOptions

A tag <UseHeaptrc Value="True"/> do .lpi é ignorada pelo lazbuild: o binário sai sem heaptrc, o processo nunca retorna 203 e o gate fica inerte — passando sempre, inclusive com vazamento. Por isso o build mode Debug de tests/LzNexTests.lpi traz <CustomOptions Value="-dUseCThreads -gh -gl"/>. Ao criar um novo .lpi de teste, copie essa linha; conferir é só rodar o script e ver se a marca [gh] aparece.

CLI e API no compose

O serviço cli usa a imagem runtime, que é Ubuntu enxuto com libmariadb3 e o binário em /usr/local/bin/lznex. Qualquer subcomando vai depois do nome do serviço: 

docker compose run --rm cli migrate:status
docker compose run --rm cli migrate:latest
docker compose run --rm cli seed:run --only=users
docker compose run --rm cli migrate:rollback --all

A API de exemplo expõe GET /health (ping no banco) e GET /users (20 primeiras linhas). O /health é o teste de fumaça mais barato que existe aqui: se ele responde, a cadeia config → pool → Zeos → libmariadb está inteira. 

docker compose up -d api
curl -s localhost:9000/health
saída
{"status":"ok","dialect":"mysql"}

O que o build faz

O estágio builder instala fpc, lcl-utils, lazarus-src e libmariadb3, baixa o Boss e resolve o ZeosLib. Enquanto a coordenada for o placeholder github.com/CHANGEME/zeoslib, ele clona o espelho direto em modules/<host>_<org>_<repo>, reproduzindo à mão o layout que o Boss produziria; com uma coordenada real, chama scripts/boss-install.sh. Esse script existe porque o Boss imprime ruído de Delphi (rsvars.bat, no Delphi installation) e pode sair com código diferente de zero mesmo tendo instalado: o sucesso é decidido pela linha Installation completed successfully, não pelo exit code.

Depois, lazbuild compila tools/LzNexCli.lpi e tests/LzNexTests.lpi nos dois build modes. O lazarus-src entra mesmo sem nenhum uso de LCL — sem ele o lazbuild para com directory lcl not found.
