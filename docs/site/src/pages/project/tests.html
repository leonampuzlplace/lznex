Testes e Docker

Tudo roda em container: a suíte sem banco, a mesma suíte contra cinco bancos de verdade, o CLI e a API de exemplo. O docker-compose.yml do repositório é a única configuração necessária.

Os comandos

docker compose run --rm tests             # unitários, sem banco
docker compose run --rm tests-it          # integração + concorrência (MySQL real)
docker compose run --rm tests-it-pg       # a mesma suíte, contra PostgreSQL real
docker compose run --rm tests-it-fb3      # idem, Firebird 3
docker compose run --rm tests-it-fb5      # idem, Firebird 5
docker compose run --rm tests-it-sqlite   # idem, SQLite (arquivo no container)
docker compose run --rm cli migrate:latest
docker compose up -d api && curl localhost:9000/health

Os seis primeiros rodam o mesmo binário (./bin/lznex-tests-debug, build mode Debug). O que muda é o ambiente: sem LZNEX_IT, as quatro suítes que precisam de banco (Test.Integration, Test.It.Features, Test.It.Migrator e Test.Concurrency) chamam Ignore e os 54 casos aparecem como ignorados — não como falha. Com ela, o dialeto sai de LZNEX_CLIENT e cada serviço declara depends_on do seu banco com condition: service_healthy. O tests-it-sqlite é a exceção: não tem depends_on porque o banco é um arquivo que nasce dentro do próprio container e morre com ele.

As tabelas de teste nascem pelo schema builder, não por DDL cru — é o que permite a mesma suíte rodar nos cinco bancos e, de quebra, põe o DDL de cada dialeto sob teste a cada execução.

Serviços do compose

ServiçoO que é
mysqlmysql:8.4 com utf8mb4 / utf8mb4_0900_ai_ci, publicado em 3307:3306 para não colidir com um MySQL local. Healthcheck por mysqladmin ping; dados no volume mysql-data.
testsEstágio builder do Dockerfile, working_dir: /src. Só HEAPTRC=haltonnotreleased no ambiente — nenhuma variável de banco, nenhum depends_on.
postgrespostgres:17, publicado em 5433:5432. Healthcheck por pg_isready; dados no volume pg-data.
firebird3 · firebird5firebirdsql/firebird:3 e :5 lado a lado, em 3051:3050 e 3053:3050, com FIREBIRD_DATABASE_DEFAULT_CHARSET: UTF8. O healthcheck é um select 1 from rdb$database por isql, não um teste de porta: o processo sobe antes de o arquivo do banco existir, e "porta aberta" deixaria a suíte conectar cedo demais.
tests-itMesma imagem, mais as variáveis LZNEX_* e DB_*, LZNEX_IT=1 e HEAPTRC=haltonnotreleased. Espera o healthcheck do MySQL antes de subir.
tests-it-pg · tests-it-fb3 · tests-it-fb5O mesmo binário com outro bloco de ambiente (x-pg-env, x-fb-env) e o depends_on do seu servidor. Nos dois de Firebird só o LZNEX_HOST difere — o dialeto é um só para as duas versões.
tests-it-sqliteSem depends_on e sem servidor: LZNEX_DATABASE é um caminho de arquivo dentro do próprio container, que nasce e morre com ele.
cliImagem runtime (as quatro bibliotecas cliente, nenhuma ferramenta de build), entrypoint no binário lznex. Monta ./database em /home/lznex/database:ro, então as migrations e seeds do host valem dentro do container.
apiExemplo Horse de example/api/Dockerfile, porta 9000, restart: unless-stopped e healthcheck por curl /health.
spikeContainer de bancada: monta o repositório em /work e fica em sleep infinity. Serve para compilar sonda por sonda à mão.

Cada família de serviço herda um bloco de ambiente declarado como âncora no topo do compose — x-db-env, x-pg-env, x-fb-env, x-sqlite-env: 

# x-db-env
LZNEX_CLIENT=mysql
LZNEX_HOST=mysql
LZNEX_PORT=3306
LZNEX_DATABASE=lznex
LZNEX_USER=root
LZNEX_PASSWORD=secret
LZNEX_LIBRARY=/usr/lib/x86_64-linux-gnu/libmariadb.so.3

# x-fb-env — LZNEX_HOST fica de fora: cada suite aponta para o seu servidor
LZNEX_CLIENT=firebird
LZNEX_PORT=3050
LZNEX_DATABASE=/var/lib/firebird/data/lznex.fdb
LZNEX_USER=SYSDBA
LZNEX_PASSWORD=secret
LZNEX_LIBRARY=/usr/lib/x86_64-linux-gnu/libfbclient.so.2
LZNEX_CHARSET=UTF8

# x-sqlite-env — nao ha servidor nem host
LZNEX_CLIENT=sqlite
LZNEX_DATABASE=/tmp/lznex-it.sqlite
LZNEX_LIBRARY=/usr/lib/x86_64-linux-gnu/libsqlite3.so.0
LZNEX_CHARSET=UTF-8

LZNEX_LIBRARY está em todos porque o auto-load do Zeos não acerta o nome da biblioteca no Ubuntu — veja Troubleshooting. O LZNEX_DATABASE de Firebird e SQLite é um caminho de arquivo, não um nome lógico.

ℹ
O host do banco é mysql, não localhost

Dentro da rede do compose o banco responde pelo nome do serviço. Da sua máquina, são as portas publicadas: 3307 (MySQL), 5433 (PostgreSQL), 3051 (Firebird 3) e 3053 (Firebird 5) — todas deslocadas para não colidir com um servidor local. Rodar a suíte de integração fora do container exige apontar DB_HOST/DB_PORT para a porta publicada.

Exit 0 é a parte que mais importa: com HEAPTRC=haltonnotreleased o processo sairia 203 se sobrasse um bloco não liberado, então exit 0 nas seis execuções é a prova de que nada vazou — inclusive nos caminhos de erro, que são os que costumam esquecer de devolver a conexão.

Os ignorados são declarados por capacidade do dialeto, nunca por banco não estar disponível: os 8 do Firebird são JSON (5), texto completo (2) e upsert de várias linhas (1); os 4 do SQLite são texto completo (2), índice de texto completo (1) e lock de linha (1); o único do MySQL e do PostgreSQL é o teste que prova a recusa do Firebird. As tabelas de teste nascem pelo schema builder de cada dialeto, então cada execução também põe o DDL daquele banco sob teste: it_users, it_features, it_paging, it_sugar, it_sugar_child, it_dialect, it_inspect, it_infra, it_lease, ct_load e as do migrator.

Organização dos testes

Duas camadas: a suíte FPCUnit (um binário, tests/LzNexTests.lpr) e as sondas, programas .lpr independentes que compilam e rodam sozinhos. A sonda existe para isolar um subsistema sem arrastar o resto do framework de teste — quando o linker do FPC reclama, dá para saber de qual unit veio.

ArquivoCobre
Test.CoreTLzNexValue (conversão implícita, Unset não bindável, precisão de Int64), Vals/ValueList, ordem dos bindings e composição de fragmentos.
Test.QuerySelect e alias, where e operadores, grupos de predicado, join, ordenação e paginação, SQL cru, clone. Registra também as áreas security (operador fora da lista, valor nunca interpolado, backtick escapado) e dialect.
Test.PostgresO dialeto PostgreSQL por texto: identificador com aspas duplas, limit/offset ANSI, returning, on conflict, distinct on, nulls first/last, truncate e o DDL. Quase todo caso compara com o MySQL para a mesma entrada, e os dois lados são asserções — inclusive o que o MySQL tem que recusar.
Test.FirebirdO dialeto Firebird por texto, sem banco: identificador, offset … rows fetch next … rows only na ordem certa, with lock e skip locked, update or insert … matching, upper() like upper(), e o DDL — identity, ordem default/not null, blob sub_type, execute block no drop, catálogo rdb$relations e corte do nome de índice em 31 bytes. Também assertam o que o dialeto recusa.
Test.SQLiteO dialeto SQLite por texto: os dois nomes registrados, limit -1 offset ?, upsert com excluded., like no lugar do ilike, e o DDL — integer primary key autoincrement, restrição dentro do create table, um statement por ação no alter, sqlite_master e pragma_table_info. Mais o que levanta: Returning, lock de linha, Change, not null sem default e ADD CONSTRAINT.
Test.IntegrationBanco real, qualquer um dos cinco (o dialeto vem de LZNEX_CLIENT): InsertGetId (id próprio, ids crescentes, dentro de transação commitada e revertida), CRUD completo e ida-e-volta de UTF-8.
Test.It.FeaturesOs recursos que o dialeto escreve de forma diferente, checados pelo resultado e não pelo texto: paginação com janela no meio, offset sozinho, nulls first/last, like sem caixa, upsert que insere e upsert que atualiza, e Truncate esvaziando a tabela. É o que prova que a emulação de um banco dá a mesma resposta que a cláusula nativa de outro.
Test.It.MigratorO runner de migrations contra banco de verdade: Latest cria as tabelas de controle e aplica, roda de novo e devolve 0 sem ficar presa no lock, Rollback desfaz e devolve CurrentVersion a none, Pending/Status/Batch acompanham, e lock tomado à mão faz Latest levantar ELzNexMigrationLock até o Unlock. A migration de teste é definida na própria unit, pelo schema builder, para ser portável aos cinco.
Test.ConcurrencyCarga paralela: operações mistas que não se misturam, pool que devolve toda conexão, transações isoladas entre threads, mais threads que conexões e cursor aberto segurando o empréstimo.
Test.PaginatePaginação por texto: o corte do cursor (uma chave, duas chaves, descendente, navegação para trás), o que o keyset recusa (OrderByRaw, ordem de nulos, sem ordem, valor nulo), o codec do cursor (ida e volta de inteiro, texto com separadores, data com milissegundos, float sem depender de locale, cursor truncado e adulterado, e a garantia de ser url-safe) e as validações de Chunk/ClearPaging.
Test.SugarO açúcar do builder por texto: WhereAny/WhereAll (grupo fechado que não contamina o where seguinte), SelectCount/SelectAggregate, WithCount (inclusive a prova de que a subquery de quem chamou não é alterada), ClearPaging, Dump e o que Upsert/UpdateOrInsert recusam.
Test.Features.MySQL · .Postgres · .SQLite · .FirebirdAs variações novas por dialeto, por texto: cada parte de data, JSON nos três modos, texto completo nos dois modos, ordem aleatória — e, em cada dialeto, o que ele recusa com mensagem.
Test.Schema.InspectO SQL de inspeção de catálogo de cada dialeto: Tables, Columns e HasIndex em information_schema, pg_index, pragma_index_list e rdb$indices.
Test.It.PaginatePaginação contra banco real, nos cinco: total e janela, última página curta, página além do fim, count com group by e com distinct, SimplePaginate, a caminhada completa do cursor para frente e para trás, o cursor que não repete linha quando uma é inserida no meio da leitura, empate desempatado pela segunda chave, e Chunk/ChunkById/Each.
Test.It.SugarFirstOrFail, Sole, DoesntExist, Upsert e UpdateOrInsert contra banco real — incluindo o caso em que o update grava o mesmo valor e o MySQL devolve zero linhas afetadas, que quebraria uma implementação que decidisse por esse número.
Test.It.DialectPartes de data, JSON, ordem aleatória e texto completo contra banco real, decidindo por capacidade do dialeto e não por nome de banco.
Test.It.SchemaInspeção contra banco real: a tabela criada aparece em Tables, Columns vem na ordem declarada, HasIndex acha a unique composta e não acha um conjunto sem índice.
Test.It.LeaseA conexão volta ao pool em todo caminho de saída: commit, rollback, transação abandonada (quem desfaz é o destrutor), Transact que comita, Transact que falha e desfaz, e Transact que repete três vezes. Mede Pool.InUse, que é observável — não depende do heaptrc para acusar lease preso.
Test.It.InfraQuery log (logger espião contando LogQuery/LogError e o tempo medido), retry de transação (Transact com ILzNexWork) e roteamento de leitura para a réplica.
Test.HelperBase das suítes unitárias: AssertSQL, AssertBindings e AssertQuery, que comparam texto gerado e lista de binds de uma vez.
Probe*.lprProbeValue (valor), ProbeAst (AST), ProbeQuery (builder), ProbeCompiler (compilador de query), ProbeSchema (DDL), ProbeMigration (migrator e seeder), ProbeEndToEnd (fachada até o SQL) e ProbeZeos (conexão, pool e transação contra o Zeos).
DiagPool.lprDiagnóstico, não teste: imprime InUse e Size do pool a cada passo. Serve para ver uma conexão presa.

Gate de vazamento

scripts/run-tests.sh coleta bin/Probe* e bin/Test*, exporta HEAPTRC=haltonnotreleased (default do script) e roda um por um. Como os binários são compilados com -gh, o heaptrc aborta o processo com exit 203 se sobrar bloco não liberado. Resultado: um único critério — exit != 0 — cobre asserção quebrada e memória não liberada. 

bash scripts/run-tests.sh                    # tudo em bin/
bash scripts/run-tests.sh bin/ProbeCompiler  # um binário só
saída
run-tests: HEAPTRC=haltonnotreleased
run-tests: 8 binario(s)

  PASS  ProbeAst                     [gh]
  PASS  ProbeCompiler                [gh]
  LEAK  ProbeSchema                  exit=203
          24 unfreed memory blocks

run-tests: pass=7 fail=0 leak=1
run-tests: FALHOU
  - ProbeSchema (vazamento)

formato do relatório, com um binário vazando — na última execução registrada foram todos PASS

A coluna entre colchetes não é enfeite: o script procura a string Heap dump by heaptrc unit dentro do binário. Não achando, marca SEM -gh e avisa que o gate não vale para aquele binário. É o que impede um verde falso.

⚠
O -gh tem que ir em CustomOptions

A tag <UseHeaptrc Value="True"/> do .lpi é ignorada pelo lazbuild: o binário sai sem heaptrc, o processo nunca retorna 203 e o gate fica inerte — passando sempre, inclusive com vazamento. Por isso o build mode Debug de tests/LzNexTests.lpi traz <CustomOptions Value="-dUseCThreads -gh -gl"/>. Ao criar um novo .lpi de teste, copie essa linha; conferir é só rodar o script e ver se a marca [gh] aparece.

CLI e API no compose

O serviço cli usa a imagem runtime, que é Ubuntu enxuto com as quatro bibliotecas cliente e o binário em /usr/local/bin/lznex. Qualquer subcomando vai depois do nome do serviço: 

docker compose run --rm cli migrate:status
docker compose run --rm cli migrate:latest
docker compose run --rm cli seed:run --only=users
docker compose run --rm cli migrate:rollback --all

A API de exemplo expõe GET /health (ping no banco) e GET /users (20 primeiras linhas). O /health é o teste de fumaça mais barato que existe aqui: se ele responde, a cadeia config → pool → Zeos → libmariadb está inteira. 

docker compose up -d api
curl -s localhost:9000/health
saída
{"status":"ok","dialect":"mysql"}

O que o build faz

O estágio builder instala fpc, lcl-utils, lazarus-src e as quatro bibliotecas cliente (libmariadb3, libpq5, libfbclient2, libsqlite3-0), e clona o ZeosLib do espelho oficial em modules/zeoslib. Clona porque o pacote não vendoriza o Zeos — é dependência de quem instala — e aqui não existe IDE para fornecê-lo. Boss só entra na imagem do exemplo em example/api, que instala o Horse de verdade, e sempre via scripts/boss-install.sh: o Boss imprime ruído de Delphi (rsvars.bat, no Delphi installation) e pode sair com código diferente de zero mesmo tendo instalado, então o sucesso é decidido pela linha Installation completed successfully, não pelo exit code.

Depois, lazbuild compila tools/LzNexCli.lpi e tests/LzNexTests.lpi nos dois build modes. O lazarus-src entra mesmo sem nenhum uso de LCL — sem ele o lazbuild para com directory lcl not found.
