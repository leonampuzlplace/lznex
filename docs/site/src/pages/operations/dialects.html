Dialetos

Toda diferença entre bancos está num só lugar: o ILzNexClient. O builder não sabe em que banco está.

O que o ILzNexClient concentra

O query builder monta uma árvore e o compilador percorre essa árvore. Nenhum dos dois pergunta "qual é o banco?" — eles perguntam ao cliente. É o cliente que responde como se escreve um identificador, se o banco tem returning, quais seções entram em cada verbo e qual compilador usar. Em quatro blocos:

TLzNexClientBase implementa tudo isso com padrões ANSI; as duas fábricas são abstratas. Um dialeto é uma classe que herda da base, sobrescreve o que difere e se registra.

Capacidades

As capacidades não são informativas: o compilador consulta cada uma e, quando o recurso não existe, ou emula ou levanta ELzNexCompile dizendo o que fazer em vez disso. Nunca gera SQL que o banco vai recusar.

CapacidadeMySQLPostgreSQLFirebirdSQLiteEfeito prático
SupportsReturning não sim sim não Em PostgreSQL e Firebird, Returning(['id']) acrescenta returning "id" a insert, update e delete, e InsertGetId lê o id do próprio INSERT. Em MySQL e SQLite a chamada de Returning já levanta ELzNexCompile — ali InsertGetId consulta a conexão (last_insert_id() no MySQL, last_insert_rowid() no SQLite).
SupportsOnConflictWhere não sim não sim Predicado no alvo do upsert (on conflict (…) where …). MySQL resolve conflito com insert ignore into e on duplicate key update, e o Firebird com update or insert … matching — formas que não aceitam condição; o filtro tem de ir para a lógica da aplicação.
SupportsNullsOrdering não sim sim sim nulls first / nulls last nativos (no SQLite desde a 3.30). Em MySQL o compilador emula: emite uma chave de ordenação extra (coluna is null) antes da coluna. O resultado é o mesmo, o texto não.
SupportsDistinctOn não sim não não DistinctOn(['x']) vira distinct on ("x"). Onde não existe levanta ELzNexCompile mandando usar Distinct simples ou group by, porque não há emulação honesta.
SupportsSavepoints sim sim sim sim Savepoint aninha blocos dentro de uma transação. Num dialeto sem savepoint, a chamada levantaria em vez de simular aninhamento que não existe.
DdlIsTransactional não sim sim sim Em PostgreSQL um create table dentro de transação desaparece no Rollback. Em MySQL cada DDL faz commit implícito: uma migration que falha no meio deixa as tabelas já criadas, e o Down é a única forma de voltar.
SupportsJson sim sim não sim WhereJsonPath, WhereJsonContains e WhereJsonLength existem nos três primeiros, cada um com a sua função (json_extract, operadores #>>/@>, json_extract de novo). No Firebird não há tipo nem função de JSON, e o builder recusa antes de gerar SQL.
SupportsFullText sim sim não não WhereFullText e ILzNexTable.FullText valem em MySQL (fulltext + match … against) e PostgreSQL (GIN sobre to_tsvector + @@). No SQLite seria tabela virtual FTS5, que é outro desenho de schema; no Firebird não há equivalente.
IsRetryableError códigos próprios de cada um, mais os SQLSTATE 40001/40P01 na base É o que Transact consulta para decidir entre repetir a transação e propagar o erro. Deadlock e lock timeout são repetidos; violação de chave, não.
⚠
DdlIsTransactional = não muda como você escreve migration

Em MySQL não existe migration atômica. Escreva Up de forma que uma falha no meio deixe um estado de que o Down consegue sair, e evite misturar DDL com DML no mesmo passo: o commit implícito do DDL fecha a transação que o DML achava que estava aberta.

Isolamento de abertura

DefaultIsolation é a sétima pergunta, e a única que não é booleana: diz em que nível a conexão nasce. A base devolve ilDefault — deixa o default do servidor em paz. Só o Firebird sobrescreve, para ilReadCommitted: o default do servidor lá é snapshot, e snapshot num pool significa que a conexão fica presa na foto tirada no início da transação e não vê o commit das outras. O sintoma seria leitura velha intermitente, dependendo de qual conexão o pool entregou.

O * nunca é citado, e identificador vazio passa intacto. O placeholder é ? nos quatro porque quem numera os parâmetros é o Zeos, não o LzNex — o dialeto que precisasse de $1, $2 sobrescreveria Placeholder, que já recebe o índice.

EscapeForLog tem dois usos, e só dois. É o que o log mostra no lugar de cada bind — SQL legível com os valores interpolados, nunca o texto que vai ao banco. E é o que vira literal de DEFAULT no DDL, que é interpolado e não bindado. É por isso que PostgreSQL e Firebird sobrescrevem o booleano para true/false: o 1/0 da base é recusado numa coluna boolean.

A mesma cadeia, dois dialetos

Este é o teste SameQueryCompilesDifferentlyPerDialect: a mesma sequência de chamadas, dois clientes, e três divergências aparecendo de uma vez. 

Q.Table('users').Select(['id', 'name'])
  .Where('active', True)
  .OrderBy('name', odAsc, nlLast)
  .Offset(5)
  .ToSQL
select `id`, `name` from `users` where `active` = ? order by (`name` is null) asc, `name` asc limit 18446744073709551615 offset ?

binds: True | 5

select "id", "name" from "users" where "active" = ? order by "name" asc nulls last offset ?

binds: True | 5

Três diferenças, três mecanismos distintos:

  1. Quoting — acento grave contra aspa dupla. Vem de uma única sobrescrita de QuoteChar; nenhum método do compilador trata disso.
  2. Ordenação de NULL — PostgreSQL diz nulls last; MySQL, que não tem a cláusula, recebe a chave extra (`name` is null) asc antes da coluna. É SupportsNullsOrdering escolhendo entre cláusula nativa e emulação.
  3. Limite artificial — Offset(5) sozinho. MySQL não aceita offset sem limit, então o compilador do dialeto injeta limit 18446744073709551615 (o maior bigint unsigned), que é a forma canônica de dizer "sem limite". PostgreSQL aceita offset sozinho e não ganha nada.

O mesmo vale para DDL: Increments é int unsigned not null auto_increment primary key em MySQL e serial primary key em PostgreSQL. Veja Tipos de coluna.

Firebird e SQLite divergem bem mais que esses dois entre si: as duas seções a seguir listam, por dialeto, cada construção que muda de forma — e cada uma que levanta em vez de sair torta.

Firebird: o que muda

Um dialeto só — LzNex.Client.Firebird, registrado como firebird — e o mesmo SQL serve ao Firebird 3 e ao 5. A suíte de integração roda nos dois servidores. A única construção que exige o 5 está marcada abaixo.

ChamadaO que sai
Limit(10) fetch next ? rows only — não existe limit
Offset(20) offset ? rows, sozinho, sem precisar de limite artificial
OrderBy(…).Limit(10).Offset(20) order by "id" asc offset ? rows fetch next ? rows only — o offset vem antes do fetch, e é por isso que o cliente troca cpOffset com cpLimit em Components
WhereILike('name', 'ana%') upper("name") like upper(?) — não há ilike
ForUpdate with lock
ForUpdate.SkipLocked with lock skip locked — sintaxe que só existe a partir do Firebird 5
Truncate delete from "users" — não existe truncate
OnConflict(['email']).Merge update or insert into … matching ("email")
OnConflict.Merge sem coluna update or insert into … sem matching: o Firebird casa pela chave primária. No PostgreSQL a mesma chamada levanta, porque o on conflict exige a coluna 
Q.Table('t').OrderBy('id').Limit(10).Offset(20).ToSQL
SQL
select * from "t" order by "id" asc offset ? rows fetch next ? rows only

binds: 20 | 10 — na ordem em que aparecem no texto, não na da cadeia

O que levanta no Firebird

  • OnConflict(…).Ignore — não há do nothing, e o merge pediria cast em cada parâmetro. A mensagem manda usar Merge ou checar com Exists antes.
  • Merge com lista de colunas ou com MergeValues — o update or insert atualiza todas as colunas da linha, então não tem como honrar um subconjunto.
  • Upsert de mais de uma linha — update or insert leva uma linha por chamada.
  • Intersect e Except_ — não existem no Firebird 3 nem no 5. A mensagem sugere WhereInSub ou WhereNotExists.
  • NoWait — no Firebird esperar é atributo da transação, não cláusula do lock.
  • ForShare — with lock é sempre exclusivo.
  • Limit e Join em update/delete.
  • LastInsertId — o gerador é por tabela, não há "último id da sessão". Use InsertGetId, que lê o id do insert … returning.

Renomear tabela não existe no Firebird 3/5

RenameTableSQL levanta ELzNexSchema dizendo que a tabela tem de ser recriada, copiada e apagada — três passos na migration, não um alter.

SQLite: o que muda

LzNex.Client.SQLite registra dois nomes, sqlite e sqlite3, e ambos resolvem para o dialeto sqlite. É o único banco em arquivo da lista: Database é o caminho do arquivo e Host não se aplica. Veja Configuração.

ChamadaO que sai
Limit(10).Offset(20) limit ? offset ? — ANSI
Offset(20) sozinho limit -1 offset ? — o SQLite recusa offset sem limit, e -1 é o "sem limite" dele
OnConflict(['email']).Ignore on conflict ("email") do nothing, nativo
OnConflict(['email']).Merge on conflict ("email") do update set "name" = excluded."name", … — igual ao PostgreSQL, inclusive o where no upsert
WhereILike sai igual a WhereLike: não há ilike, e o like do SQLite já ignora caixa em ASCII — e só em ASCII
Truncate delete from "users" — não existe truncate
InsertGetId last_insert_rowid(), que é por conexão — e o pool garante que o insert e a leitura do id usam a mesma

O que levanta no SQLite

  • Returning — recusado pelo builder. O insert roda por ExecuteUpdatePrepared, que não devolve cursor; InsertGetId não depende disso.
  • ForUpdate e ForShare — não há lock de linha: uma transação de escrita tranca o banco inteiro. A mensagem manda tirar a cláusula ou serializar os escritores na aplicação.
  • DistinctOn.
  • Limit e Join em update/delete.

Três casos do DDL merecem nome próprio, porque são restrições do banco e não da lib:

  • Change levanta: não há alter column no SQLite. A saída é recriar a tabela na migration — criar a nova, copiar, apagar a antiga, renomear.
  • add column … not null sem default levanta: as linhas que já existem não teriam valor. Com Default_ passa: alter table "users" add column "age" integer not null default 0.
  • Primary e chave estrangeira em tabela existente levantam, citando a falta de ADD CONSTRAINT. Declare na criação da tabela.
⚠
Comment é ignorado em silêncio no SQLite

Não existe comment on no SQLite, e o comentário é documentação: não vale derrubar a migration por causa dele. O create table sai sem o comentário e sem statement extra. No Firebird o Comment sai como comment on column "users"."email" is '…', um statement depois da tabela.

Implementar um dialeto novo

Um dialeto são duas classes — um TLzNexClientBase e um TLzNexSchemaCompilerBase — mais, se o banco precisar, um TLzNexCompilerBase. Na ordem em que vale atacar:

  1. DialectName e ZeosProtocol. Os dois são abstratos. DialectName é o que aparece nas mensagens de erro; ZeosProtocol é o que entra na URL do Zeos e precisa casar com um driver realmente registrado.
  2. ColumnTypeSQL e ModifierOrder, no compilador de schema. ColumnTypeSQL traduz cada TLzNexColumnType para o tipo nativo; ModifierOrder diz em que sequência os modificadores saem. A ordem importa: MySQL exige mdUnsigned, mdNullable, mdDefault, mdComment, mdCollate, mdAfter; PostgreSQL só reconhece mdNullable, mdDefault e ignora o resto; o Firebird exige mdDefault antes de mdNullable, porque not null default 0 é erro de sintaxe lá.
  3. As capacidades. Sobrescreva apenas as que diferem dos padrões da base — que são conservadores: sem returning, sem on conflict … where, sem ordenação de NULL, sem distinct on, com savepoint, com DDL transacional e com DefaultIsolation em ilDefault.
  4. WrapIdentifier, Alias, Placeholder. Na prática, quase sempre basta sobrescrever o QuoteChar protegido: o WrapIdentifier da base já cita e duplica a aspa interna sozinho. Sobrescreva os métodos inteiros só se a forma do alias ou do placeholder for diferente.
  5. Components e InvalidComponents. Quais seções cada verbo emite, e em que ordem; e quais são proibidas. Veja a seção abaixo.
  6. O resto do compilador de schema. Prefixos do alter table (AddColumnPrefix, ChangeColumnPrefix, DropColumnPrefix — a base usa add column , alter column , drop column ; MySQL encurta para add , modify , drop ), IndexSQL e DropIndexSQL, TableOptionsSQL (vazio na base; MySQL emite engine, default character set, collate, comment) e HasTableSQL/HasColumnSQL se a consulta ao catálogo não for a de information_schema da base.
  7. RegisterClient no initialization. Uma linha por nome aceito. 
initialization
  RegisterClient('postgresql', TLzNexPostgresClient);
  RegisterClient('postgres', TLzNexPostgresClient);
⚠
O registro só acontece se a unit for linkada

RegisterClient roda no initialization, e o FPC não linka unit que ninguém referencia. Se o dialeto não estiver no uses do programa, Connect levanta ELzNexConfig dizendo que o dialeto não está registrado e listando os disponíveis.

Por que Components é virtual

Components devolve, para cada verbo, a lista ordenada de seções que o compilador vai emitir. Para select é cpHints, cpColumns, cpFrom, cpJoin, cpWhere, cpGroup, cpHaving, cpUnion, cpOrder, cpLimit, cpOffset, cpLock; para insert, só cpFrom. O compilador não tem essa ordem escrita em lugar nenhum — ele lê a lista e percorre.

InvalidComponents é o espelho: as seções proibidas naquele verbo. Seção presente na árvore e proibida pelo dialeto levanta ELzNexCompile na compilação, com mensagem dizendo a seção, o verbo e o dialeto.

Os dois são virtuais porque é aqui que mora a classe de diferença mais chata entre bancos: a gramática do verbo. Um banco em que a ordem das seções difere, ou em que um verbo aceita algo que os outros não aceitam, sobrescreve só isso — não precisa duplicar o compilador para mudar uma linha de gramática.

O exemplo real é delete … limit. A base proíbe cpLimit em delete, porque não é SQL padrão. MySQL aceita, então o cliente MySQL sobrescreve InvalidComponents para qmDelete removendo cpLimit da lista de proibidos — e nada mais: 

delete from `users` limit ?

binds: 5

ELzNexCompile: Section "limit" is not valid in delete on dialect postgresql.
Remove the clause or change the verb.

Note que o erro é ELzNexCompile, não ELzNexBuilder: a cadeia de chamadas está coerente, o que falta é suporte no banco. Veja Erros para a distinção.
