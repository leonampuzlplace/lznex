Seeds

Popular dados. Sem histórico, sem lock e sem transação — a idempotência é responsabilidade da própria seed.

O que uma seed não tem

Seed não é migration. A comparação direta é o jeito mais rápido de entender o que esperar:

MigrationSeed
tabela de controlesimnão
batch e rollbacksimnão
lock entre processossimnão
transação em voltasim (UseTransaction)não
roda duas vezes?não: já aplicada é puladasim: roda sempre, toda vez
ordempelo Id (timestamp)alfabética pelo nome

Rodar seed:run duas vezes executa Run duas vezes. Nada guarda que ela já rodou, então a seed é que precisa ser idempotente: apagar antes de inserir, ou inserir com OnConflict. Isso não é falta de recurso, é o que permite o padrão "zera e popula" no começo de cada suíte de testes — chamar o seeder sem limpar o banco na mão e sem pedir permissão a uma tabela de controle. 

// apaga e insere: estado final identico toda vez
ADb.Table('users').Delete;
ADb.Table('users').InsertMany([
  Vals(['email', 'ana@x.dev',  'name', 'Ana']),
  Vals(['email', 'bia@x.dev',  'name', 'Bia'])
]);

// ou upsert, quando nao se pode apagar o que ja existe
ADb.Table('settings')
  .OnConflict(['key']).Merge
  .Insert(Vals(['key', 'theme', 'value', 'dark']));

Sem transação em volta, uma seed que morre no meio deixa o que já escreveu. Para um bloco tudo-ou-nada, abra a transação dentro do Run.

Ordem é alfabética

O registry ordena por SeedName, não por timestamp e não pela ordem em que as units foram registradas. Como a dependência entre seeds é real (não existe post antes de existir user), a convenção é prefixo numérico: 

'01_users'
'02_posts'
'03_comments'

a comparação ignora caixa; nome duplicado levanta ELzNex no registro

Escrever uma seed

unit Seeds.Users;

{$MODE DELPHI}{$H+}

interface

uses
  LzNex.Intf,
  LzNex.Value,
  LzNex.Seed;

type
  TUsersSeed = class(TLzNexSeed)
  public
    class function SeedName: string; override;
    procedure Run(const ADb: ILzNex); override;
  end;

implementation

class function TUsersSeed.SeedName: string;
begin
  Result := '01_users';
end;

procedure TUsersSeed.Run(const ADb: ILzNex);
begin
  // idempotente: o estado final nao depende de quantas vezes rodou
  ADb.Table('users').Delete;
  ADb.Table('users').InsertMany([
    Vals(['email', 'ana@x.dev', 'name', 'Ana', 'active', True]),
    Vals(['email', 'bia@x.dev', 'name', 'Bia', 'active', True])
  ]);
end;

initialization
  RegisterSeed(TUsersSeed);

end.

SeedName é class function pelo mesmo motivo que em migration: o registry ordena e detecta nome repetido no initialization, sem instanciar. Não sobrescrever levanta ELzNex.

ℹ
TLzNexSeed é TObject, não TInterfacedObject

Não existe ILzNexSeed no contrato — o seeder trabalha com a classe, não com uma interface. Então não há refcount para gerenciar: o seeder instancia, chama Run e libera no finally, inclusive quando Run levanta. Nenhum objeto vaza e nenhuma seed sobrevive à própria execução.

Rodar

lznex seed:run                 # todas, em ordem alfabetica
lznex seed:run --only=01_users # so uma
lznex seed:make demo_users     # cria um rascunho .sql
saída
3 seed(s) executed

Pelo código, via Db.Seeder:

Db.Seeder.Run;                    // devolve quantas rodaram
Db.Seeder.RunOne('02_posts');     // devolve 1

Names := Db.Seeder.Names;         // ['01_users', '02_posts'] -- ja ordenado
for I := 0 to High(Names) do

Quando uma seed falha

O erro é reembalado em ELzNex preservando a mensagem original e acrescentando qual seed e qual classe falharam. Sem isso, um erro de coluna no meio de dez seeds não diria de onde veio. 

Db.Seeder.RunOne('99_boom');
// ELzNex: Seed "99_boom" (TSeedBoom) failed: coluna email nao existe

a parada é imediata: Run não continua para as seguintes

⚠
Unit fora do uses: a seed não existe

Mesma armadilha das migrations. Se nenhum uses alcança a unit da seed, o FPC não a linka, o initialization não roda e o RegisterSeed nunca acontece — seed:run reporta 0 seed(s) executed e vai embora feliz. Com --only a mensagem de erro lista as seeds registradas, o que é o jeito mais rápido de confirmar o diagnóstico: 

error: Seed "01_users" is not registered. Registered: (none -- is the seed unit in the aggregator uses clause?).

A cura é um agregador, igual ao das migrations: uma unit Seeds.All cujo uses lista todas as seeds, e o programa dá uses Seeds.All.

ℹ
seed:make cria .sql, mas seed:run não lê .sql

seed:make grava um arquivo .sql de rascunho no diretório de seeds — é um bloco de notas para você montar o insert. seed:run executa somente classes registradas: seed em .sql não é lida do disco, ao contrário das migrations, que têm fonte .sql de verdade. Deixar o arquivo lá e esperar que rode é o erro mais fácil de cometer aqui. Passe o SQL para dentro de um Run (ADb.Execute resolve, se for SQL cru mesmo) e registre a classe.
