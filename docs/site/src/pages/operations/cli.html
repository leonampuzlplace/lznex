CLI

O binário lznex roda migrations e seeds. Por dentro é só um dispatcher sobre ILzNexMigrator e ILzNexSeeder.

O que é o binário

tools/LzNexCli.lpi compila o lznex. Ele não tem lógica de migração nenhuma: lê os argumentos, chama o método correspondente de ILzNexMigrator ou ILzNexSeeder, imprime o resultado e devolve um exit code. Toda a decisão de o que aplicar, em que ordem e sob qual lock está no migrator, que é o mesmo usado por programa.

O dispatcher vive em LzNex.Cli, uma unit separada do .lpr, por duas razões práticas:

  • testável — TLzNexCli.Run(ACommand, AArgs) recebe comando e argumentos como parâmetros, não via ParamStr. Dá para exercitar cada comando e conferir o exit code sem lançar processo;
  • embutível — a sua aplicação pode expor os mesmos comandos (um modo --migrate, um endpoint administrativo) instanciando TLzNexCli.Create(Db). RunFromCommandLine é só o atalho que lê ParamStr e chama Run. 
Cli := TLzNexCli.Create(Db);
try
  ExitCode := Cli.Run('migrate:latest', []);
finally
  Cli.Free;
end;
⚠
O binário é por projeto, não global

O uses do .lpr inclui o agregador de migrations (Migrations.All) e a unit do dialeto. Migration em Pascal só existe no binário se a unit dela foi linkada; logo, cada projeto compila o seu lznex. Migrations em .sql são lidas em tempo de execução e não pedem rebuild.

Comandos

ComandoAliasO que faz
migrate:latest—Aplica todas as pendentes num lote novo.
migrate:rollback [--all]—Desfaz o último lote; com --all, desfaz tudo.
migrate:up [nome]—Aplica a próxima pendente, ou a indicada.
migrate:down [nome]—Desfaz a última aplicada, ou a indicada.
migrate:to <nome>—Aplica as pendentes até a indicada, inclusive.
migrate:statusmigrate:listLista aplicadas e pendentes.
migrate:versionmigrate:currentversionImprime a versão atual e nada mais.
migrate:unlock—Libera o lock deixado por um processo que morreu.
migrate:make <desc> [--sql]—Cria a migration: unit Pascal, ou o par .up.sql/.down.sql.
seed:run [--only=nome]—Roda os seeds; com --only, roda só um.
seed:make <desc>—Cria um seed .sql.
helpsem comandoImprime a ajuda.

O comando é comparado em minúsculas, com Trim. Comando desconhecido imprime a ajuda e sai com 2. Antes de qualquer comando de migração, o CLI chama EnsureTables — a tabela de histórico e a de lock são criadas na primeira execução.

Flags gerais

--quietSó erros na saída. O relatório de sucesso é suprimido; mensagens de erro continuam saindo.
--helpImprime a ajuda e sai, em qualquer posição e com qualquer comando.

Argumentos posicionais e flags não se misturam: qualquer token começando com -- é ignorado na contagem de posição. lznex migrate:up --quiet create_users e lznex migrate:up create_users --quiet são a mesma coisa.

A saída do migrate:status

lznex migrate:status
saída
  state    batch source migration
  -------  ----- ------ ---------
    ok        1  code   20260210091500_create_users
    ok        1  sql    20260211143000_seed_roles
    ok        2  code   20260218120000_add_users_email_index
  pending      -  sql    20260224143012_create_orders

3 applied, 1 pending. Current version: 20260218120000

Quatro colunas: state é ok ou pending; batch é o número do lote em que a migration foi aplicada, ou - se ainda não foi; source é code (unit Pascal registrada) ou sql (par de arquivos no diretório); migration é o nome completo. A linha final resume e imprime a versão atual, que é none quando nada foi aplicado.

migrate:version imprime só a versão — é o formato para consumir em script: 

VERSION=$(lznex migrate:version --quiet 2>/dev/null)
ℹ
Migration aplicada que não existe em nenhuma fonte é erro

A comparação é por nome. Se um arquivo foi renomeado ou apagado depois de aplicado, ou se a unit saiu do uses do agregador e não foi linkada, o status levanta ELzNexMigration listando o que ficou órfão, em vez de fingir que o histórico está limpo.

Exit codes

CódigoQuando
0Sucesso. Inclui "nada a fazer": já estar na última versão não é erro.
1Erro do LzNex (ELzNex e descendentes) ou exceção inesperada. A mensagem sai como error: … ou unexpected error (Classe): ….
2Uso inválido: comando desconhecido, ou argumento obrigatório ausente (migrate:to sem nome, migrate:make sem descrição). Também é o código de erro de configuração na abertura do banco.
3Disputa de lock: ELzNexMigrationLock. Sai como lock error: ….

O lock tem código próprio porque não é a mesma coisa que uma migration quebrada. 3 significa "outro processo está migrando agora" — em deploy com várias instâncias subindo em paralelo, isso é o comportamento correto: uma aplica, as outras recuam. Com código próprio o script decide sozinho se espera e tenta de novo, ou se segue em frente, sem precisar casar texto de mensagem. Já 1 é o caso em que a migration realmente falhou e a intervenção é humana. 

lznex migrate:latest
case $? in
  0) echo "ok" ;;
  3) echo "outro processo esta migrando; seguindo" ;;
  *) echo "falhou"; exit 1 ;;
esac

Se o lock ficou preso porque o processo morreu no meio (sinal, OOM, container derrubado), migrate:unlock libera. Ele não roda EnsureTables e não aplica nada: só apaga o lock e imprime lock released.

Como o nome da migration é gerado

O nome é <carimbo>_<slug>. O carimbo tem 14 dígitos no formato YYYYMMDDHHMMSS e é UTC, não hora local. Isso é de propósito: o nome é a chave de ordenação do histórico, e dois desenvolvedores em fusos diferentes criando migrations no mesmo minuto precisam gerar carimbos que ordenem igual em qualquer máquina. Com hora local, a ordem de aplicação dependeria de onde o arquivo nasceu.

A descrição passa por Slugify: caixa baixa, só a-z0-9, qualquer outro byte vira _, sequências de _ colapsam em um e os _ do fim são removidos. O resultado é snake_case ASCII — o que cabe como nome de unit Pascal e de arquivo em qualquer sistema de arquivos. Descrição que esvazia depois do processo vira migration.

ComandoArquivo gerado
lznex migrate:make create_usersM20260224143012_create_users.pas
lznex migrate:make "create users"M20260224143012_create_users.pas
lznex migrate:make "add index: users.email"M20260224143012_add_index_users_email.pas
lznex migrate:make CreateUsersM20260224143012_createusers.pas
lznex migrate:make "criar índice"M20260224143012_criar_ndice.pas
lznex migrate:make create_orders --sql20260224143012_create_orders.up.sql e .down.sql
⚠
Acento é descartado, não transliterado

Slugify trabalha byte a byte e só mantém a-z0-9: em índice os bytes do í caem fora e sobra ndice. CreateUsers também não ganha _ — não há quebra de camelCase. Escreva a descrição já em snake_case ASCII e o nome sai exatamente como você escreveu.

Note o prefixo M no arquivo Pascal: a unit se chama M20260224143012_create_users porque identificador Pascal não pode começar com dígito. O par .sql não tem esse problema e fica com o carimbo na frente. 

lznex migrate:make create_orders
saída
created: database/migrations/M20260224143012_create_orders.pas

WARNING: add "M20260224143012_create_orders" to the `uses` clause of the migrations aggregator.
A unit nobody references is not linked by FPC, so its initialization
never runs and the migration never registers itself.
lznex migrate:make create_orders --sql
saída
created: database/migrations/20260224143012_create_orders.up.sql
created: database/migrations/20260224143012_create_orders.down.sql
.sql migrations are read at runtime: no rebuild needed.

O aviso do caminho Pascal não é decorativo: o registro da migration acontece no initialization da unit, e o FPC não linka unit que ninguém referencia. Sem entrada no agregador a migration simplesmente não existe para o migrator — e a falha é silenciosa. Veja Migrations.

Configuração do CLI

O binário procura database/lznex.json no diretório corrente. Se o arquivo existe, conecta com ele; se não existe, cai para configuração só por variáveis de ambiente. Dois envelopes mudam esse comportamento:

LZNEX_CONFIGCaminho do JSON, no lugar de database/lznex.json.
LZNEX_ENVQual bloco de ambiente do JSON usar (development se nada for dito).

As variáveis LZNEX_* de conexão sobrescrevem o que vier do JSON — útil para apontar o mesmo binário a outro banco sem editar arquivo: 

# tudo por ambiente, sem arquivo nenhum
LZNEX_CLIENT=mysql \
LZNEX_HOST=db.internal LZNEX_DATABASE=app \
LZNEX_USER=root LZNEX_PASSWORD=secret \
LZNEX_LIBRARY=/usr/lib/x86_64-linux-gnu/libmariadb.so.3 \
  lznex migrate:latest

# JSON do projeto, bloco de producao
LZNEX_ENV=production lznex migrate:status

# JSON em outro lugar, e so a senha por ambiente
LZNEX_CONFIG=/etc/app/lznex.json LZNEX_PASSWORD=$DB_PASS lznex migrate:latest

# apontar o diretorio das migrations .sql sem tocar no JSON
LZNEX_MIGRATIONS_DIR=db/migrations lznex migrate:status

Falta de configuração aparece na abertura do banco, antes de qualquer comando, com exit 2: 

configuration error: <mensagem>
Provide it through database/lznex.json or the LZNEX_HOST, LZNEX_DATABASE, LZNEX_USER, LZNEX_PASSWORD.

A lista completa das chaves do JSON e das variáveis está em Configuração.
